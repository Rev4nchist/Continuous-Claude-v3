# Frontier refresh: memory (2026-07-24)

Component: CCv3 PostgreSQL+pgvector memory (BGE daemon, per-user-prompt recall hook).
Known state: 57.6% hit rate; ~48% of ready-daemon recalls misrouted to a 12s python-subprocess fallback because a 3s client timeout undercuts ~2.3s median daemon latency (design target ~136ms). Planned today: failure reason codes, timeout 3000→6000ms, telemetry re-baseline.

## What changed / what the frontier says (adoption-weighted, cited)

**Vendor (Anthropic) — high weight**
- Native Auto Memory is GA and active on this machine: per-repo `~/.claude/projects/<project>/memory/` with a MEMORY.md index (first 200 lines / 25KB loaded at session start), topic files read on demand; hygiene enforced (size-cap nag v2.1.210+, `modified` timestamps v2.1.214+). [docs](https://code.claude.com/docs/en/memory)
- Anthropic's retrieval architecture is explicitly agentic/file-based, NOT vector RAG. Boris Cherny: early Claude Code used RAG + a local vector DB and abandoned it — "agentic search generally works better... simpler and doesn't have the same issues around security, privacy, staleness, and reliability." Canonical pattern is "just-in-time context loading": lightweight index in context, full content via tools on demand. [engineering blog](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- No vendor latency target exists for retrieval hooks. UserPromptSubmit has a 30s default timeout, is meant for "lightweight context injection, not heavy computation", output capped at 10,000 chars, and a timed-out hook's context is silently discarded. [hooks docs](https://code.claude.com/docs/en/hooks)
- The memory tool API (`memory_20250818`, GA) is pure file CRUD — no search/embedding/ranking primitive. pgvector recall remains differentiated vs anything vendor-supplied. [memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Vendor success metric is context efficiency, not recall rate: 84% token savings / 39% perf improvement on a 100-turn benchmark. [context management](https://www.anthropic.com/news/context-management)
- Subagent isolation: main-conversation auto memory does NOT flow into Task-spawned subagents (per-agent `memory` frontmatter exists but has an open bug, [#57507](https://github.com/anthropics/claude-code/issues/57507)). CCv3's recall CLI is still the only cross-agent memory channel.

**Industry latency + fallback practice — high/medium weight**
- Production memory systems treat per-turn retrieval as sub-second: Mem0 p95 search 0.200s ([paper](https://arxiv.org/abs/2504.19413)); Zep 150–300ms P95 for the full retrieval pipeline ([paper](https://arxiv.org/abs/2501.13956), [scaling blog](https://blog.getzep.com/scaling-agent-memory-zep-30x/)). CCv3's 2.3s median is ~10x the norm; the 136ms design target was reasonable, so the daemon latency is a real defect, not an unrealistic goal.
- Timeouts are set from the observed distribution (≥ dependency p99 + margin), not the design target ([InfoQ hedging](https://www.infoq.com/articles/adaptive-hedged-requests-p99-latency/), [Envoy](https://oneuptime.com/blog/post/2026-02-09-envoy-request-hedging/view)). A 3s timeout under a 2.3s median is the textbook anti-pattern; 6000ms is defensible only if it clears daemon p99.
- Fallback should degrade to CHEAPER, never slower: documented production RAG uses a ~250ms vector budget → BM25/keyword fallback with a machine-readable reason code (`rag.fallback.reason=<dep>-timeout`) per event ([production RAG](https://aboullaite.me/production-rag-java-k8s-part1/), [failure handling](https://learnwithparam.com/blog/production-rag-handling-failures)). No surveyed system falls back to a slower path; CCv3's 12s subprocess inverts the pattern (all three research angles found zero comparable cases — treat it as an error state, not a peer path).
- No adopted OSS memory system uses per-call subprocess retrieval — all are in-process libraries or long-lived services (mem0, Zep/Graphiti, Letta). Heavy/LLM work happens at write time or in background, never on the read path ([mem0 paper](https://arxiv.org/html/2504.19413v1), [Zep search docs](https://help.getzep.com/graphiti/working-with-data/searching)).
- Hedged requests (fire the cheap path at ~p95 of the primary's latency, take first response) are the standard tail-latency technique for idempotent reads — a concrete upgrade beyond a single long timeout.
- Ecosystem confirmation of the failure class: community Claude Code memory plugins report UserPromptSubmit hooks blowing 3–5s budgets from Node process-spawn overhead, ~20s cumulative worst case ([oh-my-claudecode #3377](https://github.com/Yeachan-Heo/oh-my-claudecode/issues/3377), [ruflo #1530](https://github.com/ruvnet/ruflo/issues/1530)). Spawn/connect tax, not embedding compute, commonly dominates — reason codes must distinguish them.

**Reranker — high/medium weight**
- Cross-encoder rerank over small candidate sets is cheap (~60ms for MiniLM top-100→top-20; sbert guidance for small corpora is to skip retrieval and cross-encode directly) ([sbert](https://sbert.net/examples/applications/retrieve_rerank/README.html), [TDS](https://towardsdatascience.com/rerankers-arent-magic-either-when-the-cross-encoder-layer-is-worth-the-cost-enterprise-document-intelligence-vol-1-2bis/)). Dormancy is not justified by compute cost at CCv3's corpus size — only by unmeasured precision lift.
- Rerankers earn their cost only when first-stage recall is good but top-k precision is poor; typical lift 5–15 NDCG@10. CCv3's 57.6% hit rate is contaminated by the routing defect, so ranking quality is currently unmeasurable — fix routing and re-baseline BEFORE any reranker decision. Zep keeps only cheap non-neural rerankers (RRF/MMR) on-path; the ZeroEntropy recipe (small K, full-batch, overlap with prefill) is the future re-activation path ([playbook](https://zeroentropy.dev/playbooks/reranker-on-the-request-path/)).
- Published memory-benchmark numbers (mem0 vs Zep LoCoMo wars) are discredited as selection signals — the standard judge accepts 62.8% of wrong-but-topical answers ([judge stress test](https://essays.bloo-mind.ai/posts/2026-05-20-mem-eval/), [Zep critique](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). CCv3's local telemetry re-baseline is the more trustworthy signal.

## Implications for today's build

1. **Failure reason codes — PROCEED, with two refinements.** Make codes enumerable (timeout / conn-refused / daemon-cold / spawn-overhead / empty-result) so "daemon slow" vs "daemon down" vs "client spawn tax" are separable — the 48% misroute was invisible precisely because these were conflated. Add a hot-path/background dimension (LangMem's vocabulary) to every memory-op log row.
2. **Timeout 3000→6000ms — PROCEED as a stopgap, but reframe.** 6s is well inside the 30s platform envelope, and the raise is the right unblocking move. Codify the durable rule as `timeout = daemon p99 + margin` derived from the new telemetry, not a hardcoded constant. If daemon p99 is near 6s, the raise only halves misroutes.
3. **Re-baseline — PROCEED; it is the load-bearing step.** Measure daemon-INTERNAL latency separately from client-observed latency (spawn tax likely dominates). Target 150–300ms P95 (Zep/mem0 bar), not just "under the timeout". Also track token cost of injected context per prompt (the vendor's success metric), not hit rate alone.
4. **ADJUST the fallback target (small, high-leverage addition today):** on daemon timeout, route to `--text-only` Postgres search (already exists) instead of the 12s python-subprocess embedding path. This is the one place today's plan diverges from universal practice — a 12s fallback on a prompt-blocking hook is worse than returning nothing. If trivial to wire, do it with the timeout change; otherwise make it the first follow-up.
5. **Reranker stays dormant — PROCEED (async/manual-only), but record the revised rationale:** the blocker is unmeasured precision lift on contaminated data, not compute cost (~60ms at this corpus size). Re-visit only if post-fix telemetry shows precision (right entry retrieved, ranked below k) is the residual failure mode.
6. **SKIP (today): any move toward native Auto Memory replacement or synchronous rerank.** But log the strategic question for the watch list — Anthropic abandoned exactly this per-prompt local-vector pattern.

## Watch list (not for today)

- **Index-injection architecture:** distill top learnings into a size-capped (200-line-discipline) hot index injected at SessionStart, keep pgvector for explicit `/recall` — aligns with vendor JIT-context pattern and would take recall off the per-prompt hot path entirely. Weigh against Phase 2.
- **Hedged daemon-vs-text race** (fire text search at daemon p95, first response wins) — bounds worst case at max(text) instead of 6s+fallback; check for shared-Postgres contention first.
- **Sleep-time consolidation** (Letta pattern): scheduled offline pass to dedupe/rewrite/re-score archival_memory — incremental fit with existing L0–L3 hooks + memory-curate skill.
- **Subagent memory:** native per-agent memory is buggy ([#57507](https://github.com/anthropics/claude-code/issues/57507)); CCv3's agent-memory-recall rule fills a real gap — keep it.
- **Temporal validity:** Zep's `valid_at`/`invalid_at` edge model vs CCv3's `/supersede` `valid_until` — near-parity already; Graphiti-as-MCP is the low-cost experiment if relationship-aware recall is ever wanted.
- **RRF-style cheap fusion** (vector + trigram/BM25, no neural rerank) as the adoption-proven middle ground before waking the cross-encoder — note hybrid-RRF is already CCv3's default; verify it survives the fallback path.
