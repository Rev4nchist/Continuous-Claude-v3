# Skills System — Next-Evolution Proposal (2026-07-20)

## 1. Where CCv3 is today

**Catalog.** 150 skill directories in the repo (`.claude/skills/`, counted 2026-07-20); the live session lists ~200+ installable skills once plugins are included. Trigger metadata lives in `.claude/skills/skill-rules.json` (73 KB), one entry per skill with `promptTriggers.keywords` (substring match) and `intentPatterns` (regex), plus `enforcement` (block/suggest/warn), `priority`, and per-skill eval stamps (`evalScore`/`evalTier`/`evalDate`, e.g. `skill-rules.json:36-38`).

**Activation pipeline.** A UserPromptSubmit hook, `.claude/hooks/src/skill-activation-prompt.ts`, does the matching on every prompt:
- lowercased substring keyword match (`skill-activation-prompt.ts:406-409`) and regex intent-pattern match (`:434-443`) over every entry;
- a hardcoded list of 7 high-confidence workflow triggers with anti-patterns (`:74-120`);
- ambiguous-keyword flagging that asks the model to self-validate before activating (AMBIGUOUS_KEYWORDS set — commit, push, build, plan, etc. — `.claude/hooks/src/skill-validation-prompt.ts:41-63`);
- graph resolution for prerequisites/co-activation via `.claude/hooks/src/skill-router.ts` (`skill-activation-prompt.ts:571-592`);
- `enforcement: block` skills return a blocking hook response (`:654-666`);
- a zero-match fallback that suggests `npx skills find "<topic>"` when technical intent is detected but nothing matched (`:673-703`).

This whole layer is *supplementary*: Claude Code's native skill mechanism (descriptions in context, model picks) still operates underneath. The hook is a deterministic nudge on top of it.

**Eval harness.** `.claude/skills/_eval/` holds `eval-harness.js`, `collision-test.js`, `eval-sets.json`, and results. Last full run **2026-03-07**: 97 skills / 1,179 cases / 99.1% trigger accuracy (`_eval/eval-results.json:3-13`) and a 39.5% prompt-collision rate (274 of 694 prompts matched 2+ skills, 278 unique colliding pairs — `_eval/collision-results.json:2-8`), down from 76.1% before the 2026-03-07 broad-keyword fix.

**Known limitations (already named in the system review).**
- Registration drift: 28 ghost entries (~85 dead keywords) fired "SKILL ACTIVATION CHECK" for nonexistent skills (`docs/system-update/CURRENT-STATE.md:54`); removed in QW-08 (86→58 entries, `docs/system-update/BACKLOG.md:32,44`), with real-skill follow-ups D7b-02/D7b-07/D8c-06 still open (`BACKLOG.md:37`) and per-item skill deletions (DEL-12) deferred to the SG-03 pruning program (`BACKLOG.md:96,105`).
- Eval staleness + coverage gap: the eval covers 97 skills vs 150 repo dirs, and is 4+ months old — every skill added since (codex, grok, game-plan, workroom, harness-update, reporting, notion-dashboard, project-card, ...) has no `evalScore` verification.
- The trigger data is hand-maintained and duplicates each SKILL.md description; nothing mechanically ties `skill-rules.json` to the frontmatter it paraphrases, which is exactly how the ghost-entry class arose.
- Skill-usage telemetry exists in the hook layer (`.claude/hooks/src/shared/skill-usage.ts`) but whether it feeds any pruning/quality decision is unverified — an open question below.

## 2. Frontier scan

All sources fetched and verified directly this run (post-cutoff arXiv IDs confirmed to exist and to state the attributed claims).

1. **Anthropic Agent Skills — 3-tier progressive disclosure remains the first-party mechanism.** Startup loads only name+description per skill; full SKILL.md loads on activation; bundled resources load on execution. Triggering is LLM judgment reading the description — not keywords, not embeddings. https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview and https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills
2. **Agent Skills became an open cross-vendor standard (agentskills.io, Dec 2025).** Adopters at launch: OpenCode, Cursor, Amp, Letta, Goose, GitHub, VS Code; OpenAI added Skills to Codex docs within ~2 days. https://simonwillison.net/2025/Dec/19/agent-skills/
3. **OpenAI Codex skills use the same description-match pattern.** Official docs: skills activate explicitly or "implicitly" when "your task matches the skill description"; author guidance is to front-load trigger words and define clear scope — prompt-engineering discipline on the description field, not an embedding router. https://learn.chatgpt.com/docs/build-skills (redirect target of developers.openai.com/codex/skills)
4. **Tool Search Tool / `defer_loading` is GA on the Claude API.** Deferred tool definitions stay out of context; Claude searches the catalog (regex or BM25 variants shipped; custom embedding-based search supported via `tool_reference` blocks) and only matching definitions expand. Anthropic's docs state a typical multiserver setup consumes ~55k tokens up front and tool search "typically reduces this by over 85 percent," and that selection accuracy "degrades once you exceed 30–50 available tools." https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool (companion: https://www.anthropic.com/engineering/advanced-tool-use)
5. **Routing degrades measurably at our catalog scale.** "Scaling Enterprise Agent Routing: Degradation, Diagnosis, and Recovery" (arXiv:2606.17519, June 2026, verified): on a production 110-agent / 584-tool system, routing F1 on under-specified requests drops 16–23 percentage points across three frontier models; the loss decomposes into a retrieval gap and a ~10pp "confusion gap" that persists even with perfect retrieval. **Embedding-based shortlisting recovered +10–11pp F1** at full scale, confirmed +10–17pp on 1,435 human-labeled live utterances. https://arxiv.org/abs/2606.17519
6. **Skill-description collisions can be fixed cheaply and automatically.** "A Single Rewrite Suffices: Empirical Lessons from Production Skill Description Optimization" (arXiv:2606.30775, June 2026, verified): a pipeline that feeds false-positive/false-negative routing cases into a **single targeted LLM rewrite** of the skill description matched manually-tuned F1 (79.2% vs 79.4%) while cutting per-skill tuning from 120 min to 3.8 min. It also distinguishes description-level collisions (rewritable) from genuine scope overlap (architectural). https://arxiv.org/abs/2606.30775
7. **RAG-over-tool-metadata is the established pattern for big catalogs.** RAG-MCP (arXiv:2505.03275, verified): semantic retrieval over an indexed tool-metadata store before the LLM sees anything more than top-k candidates; reports tool-selection accuracy more than tripling (13.62%→43.13%) and >50% prompt-token reduction on its benchmark. https://arxiv.org/abs/2505.03275
8. **Ecosystem note:** no primary source was found showing any major harness (Cursor, Amp, Goose, LangGraph, CrewAI) shipping a first-party *embedding-based* skill router; the shared agentskills spec they adopted inherits the description-match-by-LLM pattern. [Speculation: per-vendor custom layers may exist unannounced.]

## 3. Gap analysis

**Where we're ahead.**
- We have an eval harness with per-skill accuracy scores and a collision test — the "Single Rewrite" paper's whole premise (FP/FN regression cases as the optimization signal) presumes exactly the asset we already built in `_eval/`. Most harnesses have nothing like it.
- We already do progressive disclosure by construction (SKILL.md bodies load only on invocation), plus graph co-activation and enforcement tiers the first-party spec doesn't have.
- The ambiguous-keyword LLM-validation layer (`skill-validation-prompt.ts`) is a homegrown version of the "confusion gap" mitigation the routing paper describes.

**Where we're even.** Description-driven activation: the field converged on "LLM reads good descriptions" (Anthropic, OpenAI, the agentskills spec). Our native layer does this too; our keyword hook is an extra deterministic nudge, which is defensible but not differentiating.

**Where we're behind.**
1. **The trigger layer is unmeasured at current scale and stale.** 99.1% accuracy was measured over curated eval sets in March on 97 skills. The routing paper's core finding is that degradation shows up on *under-specified* requests as catalog size grows past ~100 — precisely what curated keyword eval sets under-test. Our collision rate (39.5% of prompts matching 2+ skills) is the visible symptom of that confusion gap.
2. **Trigger metadata is hand-maintained and drift-prone.** skill-rules.json duplicates SKILL.md descriptions with no mechanical link; the ghost-entry incident (QW-08) is the proof of cost. Codex's docs push all of this discipline into the description field itself — one artifact, no parallel registry to rot.
3. **No retrieval arm.** When keywords miss, our fallback is a generic "npx skills find" suggestion (`skill-activation-prompt.ts:673-703`) rather than an actual shortlist. The two strongest empirical results in this scan (RAG-MCP; +10–11pp F1 from embedding shortlisting) are both retrieval-over-metadata — and we already run a resident BGE embedding daemon and pgvector for the memory pillar, so the substrate exists.
4. **Catalog size is itself a cost we're not managing by evidence.** Anthropic's own docs put the accuracy knee at 30–50 in-context tools; every session carries ~200+ skill descriptions. We have usage telemetry files but no verified usage→prune loop (SG-03/DEL-12 remain open).

## 4. Recommendations

1. **ADOPT — FP/FN-driven single-rewrite description optimization in `_eval/`.** Extend the existing harness: for each skill whose eval or collision run produces failures, feed the FP/FN cases into one LLM rewrite of the SKILL.md description + trigger entry, re-run the eval, keep the rewrite if F1 improves. Directly replicates arXiv:2606.30775's verified result (matched manual tuning at 32x less effort) on infrastructure we already own. Cheapest high-confidence win in this scan.
2. **ADOPT — frontmatter→skill-rules drift guard (and partial generation).** A script (run in `/health-check` and as a pre-commit check) that asserts every skill-rules.json entry has a live SKILL.md, every SKILL.md has an entry (or an explicit opt-out), and descriptions haven't diverged; optionally seed keyword lists from frontmatter description terms. Kills the QW-08 ghost-entry class permanently instead of episodically, and covers the D7b-02/D7b-07/D8c-06 follow-up territory.
3. **ADOPT — eval refresh as a scheduled invariant.** Re-run `eval-harness.js` + `collision-test.js` now (53 uncovered skills), stamp results, and wire a staleness check ("eval older than 90 days or coverage < catalog") into `/health-check`. Without this, recommendations 1–2 have no measurement loop.
4. **WATCH — embedding shortlist arm in the activation hook.** Replace the zero-match fallback with a top-k similarity query over skill descriptions via the resident BGE daemon (post-ST-05), injecting "closest skills: X, Y, Z" instead of a generic search suggestion. Evidence is strong (arXiv:2606.17519's +10–11pp; RAG-MCP), but: hook latency budget on every prompt is a real constraint here (the pageindex-navigator per-prompt hook was killed for exactly this — `docs/system-update/CURRENT-STATE.md:38`), and the native LLM-reads-descriptions layer already provides a semantic arm. Prototype offline against the eval sets first; promote only if it beats keywords on under-specified prompts at <500ms.
5. **WATCH — deferred skill loading / skill catalog search.** The Tool Search Tool pattern (defer + BM25 search) is the right long-term shape for a 200+ catalog, but skill-description loading is controlled by the Claude Code harness, not by us; we can't defer it from userland today. Track harness releases for skill-level deferral; meanwhile the lever we do own is catalog pruning (SG-03/DEL-12) informed by usage telemetry.
6. **SKIP — adopting an external routing framework or a full RAG-MCP-style vector router.** Our activation problem is supplementary-nudge quality, not primary routing; the native layer and the eval/collision harness cover the core. A second full routing system would add a parallel registry to rot (the exact failure mode of skill-rules.json) for unproven marginal lift at our scale.

## 6. Benefits

- **Fewer wrong-skill activations in daily use.** The 39.5% collision rate means roughly 2 in 5 trigger-bearing prompts surface competing skills Dave then pays context and attention for; the rewrite loop attacks exactly the pairs at the top of `collision-results.json` (debug-agent|systematic-debugging, fix|systematic-debugging, code-review|describe_pr...).
- **Cheap maintenance instead of episodic cleanup.** The drift guard converts a recurring audit-and-purge chore (QW-08 took a dedicated wave) into a failing check, and keeps new skills (7+ added since March) from shipping untriggerable or double-triggering.
- **Trustworthy numbers.** A refreshed, scheduled eval makes "skills system is healthy" a measured claim in `/health-check` instead of a March snapshot.
- **A measured path to semantic routing, not a leap.** The offline shortlist prototype gives a go/no-go number on our own prompts before any per-prompt latency is spent — the discipline that the pageindex-navigator experience taught.
