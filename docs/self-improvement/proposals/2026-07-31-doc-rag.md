# Doc-RAG (PageIndex) — Next-Evolution Proposal (2026-07-31)

> **Relationship to the 2026-07-19 scan.** This component was reviewed 12 days ago
> ([`2026-07-19-doc-rag.md`](2026-07-19-doc-rag.md), verdict `skip`). That scan's architectural
> conclusion still holds and is not re-litigated here. This pass adds what it did not have:
> **measured index state**, a **live write-path cost it missed**, and a frontier that has
> hardened considerably since. It also records that the prior scan's single ADOPT item **did
> not land** — see §3.4.

## 1. Where CCv3 is today

Verified this session against the repo and the live database.

**The stack.** ~4.8K LOC of vendored VectifyAI PageIndex in `opc/scripts/pageindex/` (4,838 lines
across non-test `.py` files, `wc -l`) plus Postgres `pageindex_trees`. The CLI's default search
mode is **`hybrid` — FTS + pgvector RRF, no LLM** (`opc/scripts/pageindex/cli/pageindex_cli.py:338-339`,
`fast_search.py:1-6`). LLM tree-reasoning is opt-in `--mode llm`.

**The read path is dormant.** The per-prompt `pageindex-navigator` hook was disabled 2026-06-01
after 0/16 query-hits at up to 15.8s/prompt (`docs/system-update/CURRENT-STATE.md:38`). That line
describes the pillar as **"On-demand only"**.

**"On-demand only" is incomplete — the write path is live and automatic.** This is the finding
this scan adds:

1. **`pageindex-watch` is registered and firing.** It runs as a PostToolUse `Write|Edit` hook
   (`.claude/settings.json:632-636`, `hooks/dist/pageindex-watch.mjs`, 5s timeout).
2. **Its trigger surface is broad.** `INDEXED_PATTERNS` (`.claude/hooks/src/pageindex-watch.ts:28-36`)
   matches `ROADMAP.md`, `README.md`, **`docs/**/*.md`**, `.claude/docs/**/*.md`,
   **`.claude/skills/*/SKILL.md`**, **`.claude/agents/*.md`**, and `ARCHITECTURE.md` — a large
   fraction of the edits this repo actually makes. Writing *this proposal* matches it.
3. **But the reindex it fires is `--tier 1` only** (`pageindex-watch.ts:98-101`), and Tier 1 is
   **five files** (`doc_inventory.py:37-43`): `ROADMAP.md`, `README.md`, `docs/ARCHITECTURE.md`,
   `.claude/CONTINUOUS-CLAUDE-GUIDE.md`, `.claude/CONTINUOUS-CLAUDE-CHEATSHEET.md`.
   **The trigger surface and the reindex scope are mismatched:** editing any `docs/**/*.md`,
   `SKILL.md`, or agent file spawns a detached `uv run python -m scripts.pageindex.batch_index`
   that *cannot* reindex the file that triggered it. Tiers 2–4 (architecture docs, skills >300
   lines, agents) are in the trigger patterns but never in the automatic reindex scope.
4. **The debounce does not debounce bursts down to one — it fires on roughly every second
   matching edit.** Tracing `pageindex-watch.ts:164-196`: the first matching edit creates the
   pending batch with `timestamp: now`, so `elapsed = 0 < 2000` and nothing fires. The next
   matching edit ≥2s later computes `elapsed ≥ 2000`, triggers the reindex, and clears state —
   then the cycle restarts. Since normal edits are >2s apart, the steady-state behaviour is
   **one detached `uv run python` spawn per ~2 matching doc edits**. *(Code trace, not a
   measured spawn count.)* On this machine that is not free — spawn latency is a documented
   pathology (`.claude/rules/windows-platform.md`, "degraded process-spawn latency").

**Measured index state** (read-only query against `continuous_claude.pageindex_trees`, this session):

| Metric | Value |
|---|---|
| Total trees | **180** |
| Updated <7 days ago | **5** (2.8%) |
| Updated 7–30 days ago | 3 |
| Updated 30–90 days ago | 36 |
| Updated **>90 days ago** | **136 (76%)** |

By type, only `ROADMAP` (64 trees) and `README` (18) have any 2026-07-30 rows. `OTHER` (93 trees)
tops out at 2026-05-19; `ARCHITECTURE` (4) at 2026-05-07; `DOCUMENTATION` (1) at 2026-04-27.
**96% of the index is more than a week stale.**

**One hypothesis I formed and then refuted — recorded because the refutation matters.** Three of
the five Tier-1 docs stopped refreshing ~85–95 days ago despite all five existing on disk, which
looked like a reindex bug. It is not: `docs/ARCHITECTURE.md` last changed 2026-03-07 and both
`.claude/CONTINUOUS-CLAUDE-*.md` last changed 2026-04-27 (`git log -1 --format=%ci`). The
content-hash skip is behaving **correctly**. Tier-1 freshness is fine; the staleness is
concentrated in the tiers the automatic path never touches.

**A second inconsistency.** The documented user-facing entry point `/recall --pageindex` routes to
`tree_search(...)` — the **LLM reasoning path at `model="sonnet"`** (`opc/scripts/core/recall_learnings.py:1343,1362-1367`)
— not to the fast hybrid path the CLI deliberately defaults to. The one surface a human is told to
use is wired to the slow mode the system moved away from.

## 2. Frontier scan

Every arXiv ID and load-bearing URL below I fetched and verified myself this session (✓). Items I
did **not** personally fetch are marked `[unverified-by-me]` and carry no numeric weight.

**The strongest new evidence is a direct, published challenge to standing vector indexes.**
✓ [arXiv:2602.23368](https://arxiv.org/abs/2602.23368), *"Keyword search is all you need: Achieving
RAG-Level Performance without vector databases using agentic tool use"* (Subramanian et al.,
Amazon; submitted 2025-12-19). Verified abstract claim, verbatim: tool-based keyword search in an
agentic framework can *"attain over 90% of the performance metrics compared to traditional RAG
systems without using a standing vector database."* **Note the correction:** a secondary aggregator
reported "94.5% faithfulness" for this paper; the abstract says **"over 90% of the performance
metrics."** Cite the latter.

**Harness practice has consolidated, but is genuinely split — not unanimous.**
- ✓ [vadim.blog, 2026-03-03](https://vadim.blog/claude-code-no-indexing/): *"Claude Code does not
  pre-index your codebase or use vector embeddings. Instead, it uses filesystem tools — Glob …
  Grep … and Read."* It quotes Claude Code's creator Boris Cherny (on Hacker News): *"Early
  versions of Claude Code used RAG + a local vector db, but we found pretty quickly that agentic
  search generally works better."* **Attribution caveat:** this is a secondary blog quoting an HN
  comment, not an Anthropic engineering publication. Oracle looked for an Anthropic primary post
  documenting this transition and did not find one.
- ✓ **Counterweight — [Cursor, 2026-01-27](https://cursor.com/blog/secure-codebase-indexing)**:
  Cursor still ships a production embeddings pipeline. Verbatim: *"Semantic search is one of the
  biggest drivers of agent performance"* and *"These chunks are converted into the embeddings that
  enable semantic search,"* with Merkle-tree change detection and vector storage. The
  "everyone dropped vectors in 2026" narrative circulating in secondary blogs is **overstated**;
  the real picture is a split by product shape (a hosted multi-user IDE amortizes an index across a
  team; a local CLI agent does not).
- `[unverified-by-me]` Cognition/Windsurf's SWE-grep (RL-trained fast retrieval models) and
  Sourcegraph Amp layering agentic search over a pre-existing SCIP code graph — both found by
  oracle via search, not directly fetched. Directionally: specialised *retrieval models* and
  *existing structural indexes*, not new document vector stores.
- `[unverified-by-me]` OpenAI Codex CLI issue #5181 indicates semantic indexing there is a feature
  request, not shipped.

**Structure-aware retrieval research is alive, and the newest work argues against our shape.**
- ✓ [arXiv:2603.18409](https://arxiv.org/abs/2603.18409) **TopoChunker** (2026-03-19) — agentic,
  cost-routed, topology-preserving chunking; *"outperforms the strongest LLM-based baseline by 8.0%
  in absolute generation accuracy and achieves an 83.26% Recall@3, while simultaneously reducing
  token overhead by 23.5%."* Notably this is chunking-side structure preservation, **not** a
  standing reasoning tree.
- ✓ [arXiv:2606.25656](https://arxiv.org/abs/2606.25656) *"Is GraphRAG Needed?"* (2026-06-24) — a
  second independent 2026 paper converging with the *"Do We Still Need GraphRAG?"* result the prior
  scan cited. Its most useful line for us, verbatim: *"further analysis identifies a
  retrieval-generation gap where expanded retrieval does not proportionally improve generation
  quality, suggesting retrieval-oriented metrics overstate advanced retrieval benefits."* That is a
  direct caution against justifying doc-RAG on retrieval metrics alone.
- ✓ [arXiv:2606.29718](https://arxiv.org/abs/2606.29718) *"Diagnosing and Mitigating Context Rot in
  Long-horizon Search"* (2026-06-29) — extends context rot into the **agentic multi-turn search**
  setting: *"extensive context causes models to directly give up or prematurely provide uncertain
  answers, and this issue is exacerbated as the context grows."* Evaluates seven context-management
  methods. This cuts *both* ways — it is an argument against dumping everything into context, and
  an argument that a retrieval layer must return *little and precise*, not *more*.

**Carried forward, previously verified in the 2026-07-19 scan (not re-fetched today):** Anthropic's
Contextual Retrieval post (35%/49%/67% retrieval-failure reductions; the "<200K tokens → skip
retrieval, use prompt caching" guidance) and Chroma's Context Rot report. Oracle found **no vendor
publication revising that ~200K threshold.**

**Reranking:** oracle surfaced candidate newer rerankers (Jina v2, Cohere Rerank 4, ZeroEntropy
zerank) but **every numeric gain figure was secondary-blog sourced and none survived verification**.
No open-weight model was confidently identified as superseding `bge-reranker-v2-m3`. Treat the
reranker landscape as **unchanged pending a primary-source pass**.

**Genuine gap in the literature:** oracle found **no** primary quantitative study of index
staleness/maintenance cost for frequently-changing repos. Our own measurement in §1 (96% stale) is,
for our purposes, better evidence than anything published.

## 3. Gap analysis

### 3.1 On architecture, we are not behind — the frontier moved toward us

The prior scan's conclusion holds and is now better supported. Hybrid FTS+vector RRF over
structural nodes remains a defensible shape; the frontier's movement in the last six months has
been *away* from standing document vector indexes for local coding agents (Amazon ✓, Cherny ✓,
Codex CLI), not toward the reasoning-tree machinery PageIndex markets. Nothing in this scan asks us
to build doc-RAG capability.

### 3.2 The real gap is not capability — it is an unused asset with a live cost

This reframes the component. The prior scan asked "should we evolve doc-RAG?" and answered no. The
sharper question is "**what is doc-RAG costing us while dormant?**" — and the answer is not zero:

| | Read path | Write path |
|---|---|---|
| Status | Dormant (per-prompt hook off since 2026-06-01, 0/16 hits) | **Live and automatic** (`settings.json:632-636`) |
| Trigger | Deliberate CLI / `/recall` invocation | Every `docs/**`, `SKILL.md`, `agents/*.md`, ROADMAP, README edit |
| Cost | ~0 when unused | ~1 detached `uv run python` spawn per ~2 matching edits |
| Yield | No measured hits | Refreshes 5 Tier-1 docs; **96% of the 180-tree index stays stale** |

We are paying a recurring write cost, on a machine with documented spawn-latency problems, to
maintain 2.8% of an index whose read side has no measured consumer. That is the finding.

### 3.3 The frontier supplies the argument against fixing it rather than cutting it

The tempting "fix" is to widen the reindex scope so the trigger surface and reindex scope match
(reindex tiers 2–4 too). ✓ arXiv:2606.25656's *retrieval-generation gap* is the direct counter:
expanding retrieval does not proportionally improve generation, and retrieval-oriented metrics
overstate the benefit. Widening the scope multiplies the write cost by ~40x (180 trees vs 5) to
improve a metric that the frontier says overstates its own value, for a reader that does not exist.

### 3.4 A meta-gap: the loop produced a recommendation and nothing happened

The 2026-07-19 scan's **single ADOPT** was to correct the SKILL's overclaim. Twelve days later
`.claude/skills/pageindex-search/SKILL.md:12` still reads *"hierarchical tree indexes + LLM
reasoning (98.7% accuracy) instead of vector similarity (~50%)"*, and the comparison table at
`SKILL.md:114` still credits PageIndex 98.7% vs vector 50%. `git log` shows no commit touching that
file since the skill-evaluation pipeline commit. The claim is doubly wrong: 98.7% is a vendor
FinanceBench-only figure, **and** it describes `--mode llm`, which is not the default. This is a
finding about the self-improvement loop, not about doc-RAG: proposals that end in "someone should
edit a doc" appear not to convert.

## 4. Recommendations

**Overall verdict: SKIP** — do not evolve, extend, or re-enable doc-RAG. The dominant action is
subtractive.

**R1 — ADOPT: unregister the `pageindex-watch` hook.** Remove the PostToolUse entry at
`.claude/settings.json:632-636`. This stops a recurring detached-process spawn on a broad edit
surface that maintains 2.8% of an unread index. Keep `batch_index` and the CLI intact so any
deliberate reindex still works. **Gated on the consumer check in R5** — do it after confirming
nothing reads fresh trees. Highest value-per-line-changed item in this proposal.

**R2 — ADOPT: correct `SKILL.md` (re-raised from 2026-07-19, did not land).** State that the
default is hybrid FTS+vector RRF; mark 98.7% as a vendor, FinanceBench-only figure describing the
opt-in `--mode llm` path; note that under the effective-context budget, reading/grepping the doc
beats indexing it. **Add one line the prior scan did not know to ask for:** that `/recall
--pageindex` invokes the LLM tree path, not the hybrid default. Docs-only, no behaviour change.

**R3 — SKIP (downgraded from WATCH): do not wire the SI-01 reranker into PageIndex's
`search_hybrid`.** The prior scan listed this as a conditional WATCH. With the read path measured
as unused and the write path recommended for removal, reranking PageIndex results is work on a
surface nobody queries. **SI-01 itself stays valuable — on the memory path**, where there is a
measured 27.4% hit rate to move (`CURRENT-STATE.md:35`, `BACKLOG.md:149`). This is a deliberate
change from the 2026-07-19 recommendation. Additional reason to hold: every reranker gain figure
oracle surfaced this pass failed verification, so the "49%→67%" framing should not be leaned on
without a primary-source pass.

**R4 — SKIP: TopoChunker, GraphRAG, HippoRAG, reasoning-tree retrieval.** ✓ TopoChunker is real and
well-benchmarked, but it optimises chunking for corpora we do not have; ✓ arXiv:2606.25656 and
arXiv:2604.09666 both find graph approaches justified mainly by multi-hop workloads over large
heterogeneous corpora. Our corpus is a few hundred markdown files under the ~200K effective-context
threshold. Adopting any of these would be building capability for a query mix we do not run.

**R5 — ADOPT: run the consumer check, then park the pillar under SG-03.** Before removing anything,
settle the prior scan's #1 open question — which this scan could not fully close. `/recall
--hybrid` fans PageIndex out alongside vector memory (`recall_learnings.py:1996`), so the reader
count is **unmeasured, not proven zero**. Concretely: grep for `--pageindex`/`--hybrid` call sites
in hooks and scheduled jobs, and check recall telemetry for `source: "pageindex"` rows. If that
comes back empty, PageIndex becomes a clean SG-03 park candidate: ~4.8K LOC + 180 rows +
5 source files, removable with a documented restore path.

**R6 — WATCH: PageIndex-MCP for genuinely oversized external documents.** Unchanged from the prior
scan. If a recurring 10-K/contract/long-PDF workflow ever appears, the vendor MCP is the
harness-native shape (opt-in tool, docs leave the box — needs a data-residency check first).

## 6. Benefits

- **Fewer background processes on a machine that is measurably bad at spawning them.** R1 removes
  roughly one detached `uv run python` spawn per two doc edits from the PostToolUse path. Given the
  documented spawn-latency pathology and MSYS fork-storm history on this box, edit-triggered
  subprocess churn is a real tax, and doc-heavy sessions (like writing these proposals) are exactly
  when it fires most.
- **An honest system surface.** `CURRENT-STATE.md` currently tells a future session the pillar is
  "On-demand only" when a hook is firing on every doc edit; `SKILL.md` advertises 98.7% accuracy
  for a code path that does not run by default. Both mislead the next reader — including Dave.
  Fixing them costs nothing and prevents a wrong decision later.
- **A concrete pruning candidate with the evidence attached.** SG-03 gets ~4.8K LOC, 5 source
  files, 180 DB rows, and a registered hook — with measurements (96% stale, 0/16 read hits) rather
  than a hunch — plus a gate that prevents deleting something still in use.
- **Effort redirected to where it is measurable.** R3 keeps the reranker on the memory path, which
  has a live 27.4% hit rate and an existing SI-01/FH-02 measurement gate, instead of spending it on
  a retrieval surface with no reader.
- **Confidence that the "no doc-RAG" posture is right.** Two independent 2026 papers plus Anthropic's
  own harness practice now support it. The counter-example (Cursor ✓) is a hosted multi-user IDE
  that amortises an index across a team — a different shape from a local CLI agent, which is worth
  knowing so the question does not get reopened on a Medium post.

## 7. Open questions

- **Does anything actually read PageIndex trees?** Still not fully settled (R5). `/recall --hybrid`
  fans out to PageIndex (`recall_learnings.py:1996`), so the reader count is **unmeasured, not
  zero**. This gates R1 and the SG-03 park. It was also the prior scan's #1 open question — it has
  now been open for two review cycles, which is itself a signal.
- **Why did the prior scan's only ADOPT not land in 12 days?** If the self-improvement loop reliably
  produces docs-only recommendations that nobody executes, the loop's output format may be the
  problem, not its analysis. Worth a look during an `observability` or `learning-loop` pass.
- **Does `pageindex_config.yaml`'s `search.default_model: haiku` violate `.claude/rules/no-haiku.md`?**
  Carried unresolved from 2026-07-19. Moot if the pillar is parked; worth 5 minutes if not.
- **Reranker landscape is unverified.** Every 2026 reranker comparison figure oracle surfaced was
  secondary-blog sourced and failed the verification bar. Before SI-01 leans on any "newer than
  bge-reranker-v2-m3" claim, someone should fetch primary benchmark pages. `[Speculation]` that the
  landscape has moved at all.
- **Unverified-by-me frontier items** (do not build on without a check): Cognition SWE-grep,
  Sourcegraph Amp's SCIP layering, Chroma Context-1, and OpenAI Codex CLI issue #5181. Oracle found
  these via search without direct fetch. None carry weight in the recommendations above.
- **Spawn cost is traced, not measured.** The "~1 spawn per 2 matching edits" figure comes from
  reading `pageindex-watch.ts:164-196`, not from counting processes. If R1 needs a stronger
  justification than "no reader," instrument it for a day first.
