# Doc-RAG (PageIndex) — Next-Evolution Proposal (2026-07-19)

## 1. Where CCv3 is today

CCv3 vendored VectifyAI's PageIndex (~4.8K LOC in `opc/scripts/pageindex/`, upstream CHANGELOG dated 2025-04 — `opc/scripts/pageindex/CHANGELOG.md:4`) plus Postgres `pageindex_*` tables. The design intent: parse a long markdown/PDF doc into a hierarchical "table-of-contents" tree (headers → nodes), then retrieve by having an LLM reason over the tree outline rather than doing vector-similarity chunk retrieval.

**What actually runs is not what the skill markets.** Three verified facts:

1. **The default search path is hybrid RRF (FTS + pgvector), not LLM tree-reasoning.** The CLI's `--mode` defaults to `hybrid` and routes to `search_hybrid` / `search_fts` (`opc/scripts/pageindex/cli/pageindex_cli.py:132-146,338-341`), which is "PostgreSQL full-text search … + pgvector cosine via Reciprocal Rank Fusion" (`opc/scripts/pageindex/fast_search.py:1-6`). The LLM "98.7% reasoning" tree search (`tree_search.py`, `--mode llm`) is an **opt-in fallback**, not the hot path (`cli/pageindex_cli.py:146-147`). So the retrieval unit is the *tree node* (a real markdown section, not an arbitrary chunk), but the *ranking* is lexical+vector, exactly the shape the frontier converged on.
2. **The per-prompt hook was disabled and the pillar is on-demand only.** `pageindex-navigator` was turned off 2026-06-01 after telemetry showed **0/16 query-hits at 1.8–15.8s/prompt** (`docs/system-update/CURRENT-STATE.md:38`; `.claude/rules/code-intel-boundaries.md` operational notes). It does not fire per prompt; the CLI must be invoked deliberately.
3. **The SKILL overclaims.** `SKILL.md` asserts "98.7% accuracy … instead of vector similarity (~50%)" and a vector-vs-PageIndex table crediting PageIndex 98.7% (`.claude/skills/pageindex-search/SKILL.md:12,109-117`). That number is a **vendor, single-domain** figure (see §2), and it describes the `--mode llm` path that is *not* the default. The default hybrid path has no such benchmark.

Other baseline facts: indexing tiers docs (ROADMAP/README → architecture → skills >300 lines → agents) via `doc_inventory.py`; the LLM shim (`claude_llm.py`) uses Sonnet on CLI / Haiku on API; `tree_search.py` escalates to the RLM wrapper above 300K chars (`tree_search.py:19`) — and RLM is dormant/Docker-gated (`docs/architecture/INDEX.md`).

**Known limitations (verified):** dormant/underused ("honing", on-demand only, 0/16 per-prompt hits — `CURRENT-STATE.md:38`); no dedicated ST-/SG- arc in `docs/system-update/BACKLOG.md` (the only adjacent item is **SI-01**, the built-but-dormant `bge-reranker-v2-m3` reranker on the *memory* path — `BACKLOG.md:149`); a cross-encoder reranker that is *not* wired into PageIndex's own hybrid search either.

## 2. Frontier scan

Research delegated to `oracle` (14 sources); every load-bearing or post-cutoff citation below I re-verified myself by WebFetch (marked ✓). Post-cutoff arXiv IDs (2026+) were verified directly per the citation self-audit.

**PageIndex itself — the thesis holds directionally; the cost does not.** The 98.7% FinanceBench number is real but is a **first-party** result from Mafin 2.5 on SEC-filing QA ([VectifyAI/Mafin2.5-FinanceBench](https://github.com/VectifyAI/Mafin2.5-FinanceBench); [VectifyAI/PageIndex](https://github.com/VectifyAI/PageIndex)); oracle found no independent third-party replication. An independent practitioner critique (✓ [sjramblings.io, Feb 2026](https://sjramblings.io/pageindex-deep-dive-vectorless-rag/)) is blunt: PageIndex's multi-step reasoning chain "takes seconds" vs milliseconds for vector search, indexing costs ~$0.50–$5.00 per 100-page doc, the tree metaphor "starts breaking down" on unstructured content (email/Slack/tickets), and it is "only validated on FinanceBench" — the author recommends a **hybrid vector + reasoning** approach for production. PageIndex has also shipped an **MCP server** (✓ [VectifyAI/pageindex-mcp](https://github.com/VectifyAI/pageindex-mcp), API-key/Bearer auth, free tier ~1,000 pages) so an agent like Claude can call it on-demand for a specific large document.

**Reasoning/structure RAG lineage.** The named techniques CCv3's PageIndex sits among: **RAPTOR** (✓ [arXiv:2401.18059](https://arxiv.org/abs/2401.18059)) — recursively embed/cluster/summarize chunks into a tree, retrieve across abstraction levels, +20 absolute points on QuALITY with GPT-4; **GraphRAG** ([arXiv:2404.16130](https://arxiv.org/abs/2404.16130)) — entity graph + community summaries + map-reduce, strong on *global* corpus-wide questions at a large LLM-call cost; **HippoRAG** ([arXiv:2405.14831](https://arxiv.org/abs/2405.14831)) — entity graph + Personalized PageRank for cheap multi-hop. Common 2025-26 framing: these are **complementary to agentic iterative retrieval, not replacements**.

**Anthropic Contextual Retrieval — the cheap, orthogonal upgrade.** (✓ [Anthropic, Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)) Prepend a short LLM-generated context blurb to each chunk *before* indexing, index it both densely (contextual embeddings) and lexically (contextual BM25): **35%** reduction in top-20 retrieval failures from contextual embeddings alone, **49%** with contextual BM25 added, **67%** with a reranker on top. It stays inside embed-and-retrieve — architecturally orthogonal to tree navigation, and in principle combinable *within* a PageIndex node.

**Retrieval vs long-context — the most load-bearing finding for us.** Anthropic's own guidance: for knowledge bases **under ~200,000 tokens (~500 pages)**, skip retrieval and put the whole thing in the prompt with prompt caching (✓ same Contextual Retrieval post). And a 1M-token window does *not* mean 1M usable tokens: **"Lost in the Middle"** ([arXiv:2307.03172](https://arxiv.org/abs/2307.03172)) established that models under-use mid-context information, and Chroma's **Context Rot** report (✓ [trychroma.com/research/context-rot](https://www.trychroma.com/research/context-rot), 18 frontier models incl. Claude 4 / Gemini 2.5 / GPT-4.1 / Qwen3) found performance "grows increasingly unreliable as input length grows" — non-uniform degradation even on simple tasks. Net: retrieval still matters, but the operative question is *effective* context, and for sub-200K-token corpora long-context beats standing up doc-RAG.

**Agentic search is closing the gap with pre-built structure.** (✓ [arXiv:2604.09666](https://arxiv.org/abs/2604.09666), "Do We Still Need GraphRAG?", Apr 2026, verified exists) introduces RAGSearch and finds **"agentic search substantially improves dense RAG and narrows the performance gap to GraphRAG,"** while GraphRAG keeps an edge on complex multi-hop when its offline build cost is amortized — the two are "complementary." PageIndex's tree-walk is itself a form of agentic retrieval (pay the structuring cost once, navigate cheaply per query) vs agentic-grep (re-explore per query).

**What coding-agent harnesses actually ship for document retrieval.** None ship built-in tree-based *document* RAG. Claude Code / Aider explore agentically with grep/glob/read + a lightweight structural map; Cursor is the outlier maintaining a local vector index (secondary: [MindStudio, "Why … Use grep, Not Vectors"](https://www.mindstudio.ai/blog/is-rag-dead-what-ai-agents-use-instead)). Where tree doc-RAG persists, it's an **opt-in MCP tool** an agent calls for a genuinely large unstructured document — which is exactly the shape PageIndex-MCP took.

## 4. Recommendations

**SKIP — do NOT revive per-prompt doc-RAG or build reasoning-tree machinery.** Our own telemetry (0/16 hits, up to 15.8s/prompt — `CURRENT-STATE.md:38`) plus the frontier (Anthropic's <200K long-context guidance ✓; sjramblings' seconds-per-query latency ✓; agentic-search-narrows-the-gap ✓) all point the same way: for a sub-200K-token markdown corpus, long-context + grep/Read + the existing code-intel stack dominate. Building or re-enabling tree-reasoning retrieval would spend effort re-earning a failure we already measured. This is the dominant, evidence-backed verdict.

**ADOPT (cheap, honesty) — correct the SKILL's overclaim.** Update `SKILL.md` so it (a) states the **default is hybrid FTS+vector RRF over tree nodes**, not LLM reasoning; (b) marks 98.7% as a **vendor, FinanceBench-only** figure for the opt-in `--mode llm` path, not a property of what runs; (c) says plainly that for docs under the effective-context budget, prefer reading the doc / grep over indexing. Rationale: the current text will steer a future session to trust a number that doesn't describe the hot path — a claim-verification hazard the culture explicitly guards against. Docs-only, no behavior change.

**WATCH (conditional on the pillar being kept at all) — reuse the SI-01 reranker in `search_hybrid`.** The frontier names reranking as the single biggest gain after hybrid (49%→67% ✓). `_apply_rerank` (`bge-reranker-v2-m3`) already exists for memory (SI-01). *If* doc-RAG stays in service, wiring it into `fast_search.search_hybrid` is a small, infra-reusing lift. Gate it behind SI-01 actually shipping and behind evidence anyone uses PageIndex search — do not build it speculatively.

**WATCH — Contextual-Retrieval-style node augmentation.** Prepend a short LLM-generated blurb to each tree node before FTS/vector indexing (orthogonal to, and combinable with, the tree). Cheap and frontier-validated, but only worth it if doc-RAG earns real usage. Track, don't build.

**WATCH — PageIndex-MCP as an on-demand tool for genuinely large external documents.** For the rare case of a 10-K / contract / long PDF that exceeds the effective-context budget, the vendor MCP (✓ API-key auth) is the harness-native pattern (opt-in tool, not per-prompt). Track; adopt only if a concrete recurring large-PDF workflow appears — our corpus today is small markdown.

**SKIP — GraphRAG / HippoRAG / entity-graph doc RAG.** Their edge is global/multi-hop questions over large heterogeneous corpora at 100-1000x LLM-call cost; we have neither the corpus nor the query mix to amortize that.

**SKIP — pure long-context "just stuff every doc."** Context Rot ✓ + Lost-in-the-Middle ✓ mean effective context < rated context; keep grep/Read + optional on-demand structural search rather than blindly filling the window.

## 6. Benefits

- **Cheaper (no wasted build):** the biggest win is *not building the wrong thing.* This scan is evidence that our hybrid-RRF-over-tree-nodes shape is already the 2026 consensus and that reviving reasoning-tree RAG would re-earn a measured failure (0/16 hits) — so effort goes to SI-01/memory and code-intel, not doc-RAG.
- **More reliable / honest surface (Dave-visible):** the SKILL fix stops a future session (or Dave) from trusting a vendor single-domain 98.7% that doesn't describe the default path — the same claim-verification discipline the rest of the system enforces.
- **Reuse over rebuild:** if doc-RAG is ever exercised, the one improvement worth making (reranking) rides entirely on SI-01 infra already being built — no new dependency, small lift, frontier-validated 49%→67% gain shape.
- **A clear park decision:** naming doc-RAG a scoped, on-demand-only niche (docs beyond the ~200K effective-context budget) removes ambiguity about a "honing" pillar and hands SG-03 a concrete prune/park candidate with a consumer-check gate.
