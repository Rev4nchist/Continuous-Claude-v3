# Skills System — Next-Evolution Proposal (2026-08-01)

## 0. Why this proposal is different from the last two

Two prior proposals cover this component: `docs/self-improvement/proposals/2026-07-07-skills.md` and
`docs/self-improvement/proposals/2026-07-20-skills.md`. Both were substantively right. **Neither
produced a single landed change**, verified this run:

- `.claude/skills/_eval/eval-results.json:1` still stamps `2026-03-07T22:47:19.365Z`;
  `collision-results.json:1` still stamps `2026-03-07T22:43:41.722Z` — the "re-run the stale eval"
  ADOPT from both proposals has not run.
- There is no `scripts/skills/` directory — the drift guard (07-20 rec 2) does not exist.
- There is no `skill-routing.jsonl` or any `skill*.jsonl` under `.claude/logs/` — the routing
  telemetry (07-07 R2) does not exist.
- `grep -rn "skill-usage" .claude/hooks/src --include=*.ts` returns **nothing** — the
  `shared/skill-usage.ts` that 07-20's open question #1 asked about is not in the tree at all.
- Description bloat got *worse*, not better: 07-07 measured 20 descriptions over 400 chars; today it
  is **29** (measured over `.claude/skills/*/SKILL.md` frontmatter this run), topped by `impeccable`
  at 895 chars.

A third proposal repeating "re-run the eval, build telemetry, write a drift guard" would be worth
nothing. So this one does two things instead: it **performs the measurement** both prior proposals
deferred (it turned out not to need new instrumentation), and it reports **one newly-urgent fact**
that did not exist when either was written.

## 1. Where CCv3 is today

**Catalog.** 148 directories under `.claude/skills/` contain a `SKILL.md` (counted this run). Their
frontmatter `name` + `description` totals **32,231 characters ≈ 8.1k tokens** for the repo catalog
alone; the live session also carries plugin skills, and Anthropic's published figure of ~100 tokens
per Skill (source 1) puts 148 skills at ~14.8k tokens, consistent with the live `/context` reading
recorded for this machine. 29 descriptions exceed 400 chars (max 895), all under the documented
1,024-char cap (source 1).

**Two parallel selection mechanisms**, unchanged in shape since the 07-07 write-up:

*A. Native Agent Skills discovery (harness-owned).* Every skill's name+description is in the system
prompt at startup; the SKILL.md body loads only when the model judges it relevant (source 1).

*B. A keyword/regex activation hook (repo-owned).* `.claude/hooks/src/skill-activation-prompt.ts`
(UserPromptSubmit) reads `.claude/skills/skill-rules.json` (72,685 bytes; **58 skills + 18 agents**
registered) and injects a "SKILL ACTIVATION CHECK" block grouped by priority
(`skill-activation-prompt.ts:610-637`), plus agent suggestions (`:640-644`), plus a
prereq/peer graph, plus a zero-match `npx skills find` fallback (`:675-706`).

**What changed since 2026-07-20 — and it is the important part.** The `enforcement: 'block'` branch
(`skill-activation-prompt.ts:654-669`) went from inert to live. The source comment at `:661-666`
records why it was dead — the harness reads `hookSpecificOutput` and discarded the `result`/`reason`
fields the branch used — and `git log` shows the fix landed in **`fd906dd` (2026-07-28), "fix(hooks):
16 hooks that exited 0 and said nothing"**, four days ago. Three skills carry `enforcement: block`,
all at `priority: critical`: `systematic-debugging`, `databases`, `code-review` (verified over
`skill-rules.json`; the other 55 are `suggest`).

**The matcher is an unbounded substring test.** `skill-activation-prompt.ts:407-409`:
`triggers.keywords.find(kw => prompt.includes(kw.toLowerCase()))` — no word boundary. Of 566
registered keywords, 29 are ≤5 characters (`databases:index`, `databases:sql`, `databases:table`,
`databases:join`, `personas:be a`, …).

**Live demonstration, this session.** This research session's own prompt was hard-blocked with
`⛔ BLOCKING: You MUST invoke databases skill(s) before generating ANY response` — for a task with no
database work. Reproduced deterministically: the literal substring `index` occurs inside the path
`docs/architecture/INDEX.md`, which the goal prompt instructs the session to read. The LLM
ambiguity-validation layer does not catch it: `AMBIGUOUS_KEYWORDS`
(`.claude/hooks/src/skill-validation-prompt.ts:41-63`) holds 22 terms — `commit`, `push`, `debug`,
`build`, `plan`, `fix`, `test`, `review`… — and **none of `index`, `table`, `query`, `sql`, `join`,
or `schema`**. The three blocking skills' most collision-prone keywords bypass the only precision
defense in the pipeline.

### 1a. The measurement both prior proposals deferred

07-07 R2 and 07-20 open question #2 both concluded routing precision could not be known without
building a suggested-vs-invoked log. That was wrong: the evidence is already on disk. I scanned
**1,832 session transcripts** under `~/.claude/projects/` (recursive, including subagent
transcripts), spanning **2026-06-29 → 2026-08-01 (~33 days)**, and counted three things.

**Suggestion side** (189 transcripts carried a `SKILL ACTIVATION CHECK`):

| Metric | Value |
|---|---|
| Hook firings observed | 189 |
| Firings containing `⛔ BLOCKING` | 118 (62.4%) |
| Mean skills+agents suggested per firing | 9.7 |
| Distinct entities ever suggested | 88 |

**Load side** — the two paths by which a skill body can actually enter context:

| Path | Count | Distinct |
|---|---|---|
| `Skill` tool invocations | 129 | 27 skills |
| `Read` of a `SKILL.md` | 226 | 57 skill dirs |
| **Union, restricted to our 148-skill catalog** | — | **53 skills** |
| **Catalog skills with zero touches in the window** | — | **95 of 148 (64%)** |

**Joining the two** over the 59 catalog skills the hook actually suggests:

| Metric | Value |
|---|---|
| Total suggestions of catalog skills | **1,489** |
| Total loads of those same skills | **118** |
| Suggested skills **never loaded once** | **40 of 59** |

Worst offenders (suggested → loaded): `databases` 103 → 2 (and it hard-blocks), `plan-agent` 93 → 0,
`firecrawl-scrape` 85 → 0, `ui-audit` 83 → 0, `describe_pr` 81 → 0, `ui-ux-pro-max` 77 → 0,
`perplexity-search` 64 → 0, `mcp-guidance` 64 → 0, `github-search` 50 → 0, `mot` 37 → 0. Also
notable: **40 of the 58 skills registered in `skill-rules.json`** — the hand-curated set the hook
exists to promote — were never loaded in the window.

**Honest limits on this measurement.** (a) Suggestions are only visible in transcripts that carry the
UserPromptSubmit context (main sessions); loads are counted across *all* transcripts including
subagents — so the load side is counted generously and ~8% is an **upper bound** on precision, not a
point estimate. (b) A skill not loaded is not proof it contributed nothing: its always-resident
description can still nudge behavior. But the body is where the procedure lives, so zero loads means
approximately zero procedural effect. (c) I can only see the two load paths above; a third path would
be missed. (d) 189 firings is a modest sample and the window predates the `fd906dd` blocking fix for
almost all of it — meaning **the 62.4% blocking rate was mostly harmless when measured and is not
harmless now.**

## 2. Frontier scan

All six sources fetched and quote-verified directly this run. The three 2026 arXiv IDs were fetched
individually to confirm both existence and that the abstracts contain the figures attributed to them.

1. **Anthropic — Agent Skills overview.** https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview
   Verified: Level 1 metadata is "Always (at startup)", "~100 tokens per Skill"; "until a Skill is
   triggered, only its name and description occupy context"; `description` max 1,024 chars. **No
   deferral or search mechanism for Skills is documented** — all descriptions stay resident.
2. **Anthropic — Skill authoring best practices.** https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices
   Verified quote: "The description is critical for skill selection: Claude uses it to choose the
   right Skill from potentially 100+ available Skills." Anthropic's answer to a large catalog is
   **description quality, not a router**. Also verified: "There is not currently a built-in way to run
   these evaluations. Users can create their own evaluation system. Evaluations are your source of
   truth for measuring Skill effectiveness." And, directly relevant to pruning: "**Ignored content:**
   If Claude never accesses a bundled file, it might be unnecessary or poorly signaled."
3. **Anthropic — Tool search tool.** https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool
   Verified quotes: "Claude's ability to pick the right tool degrades once you exceed 30–50 available
   tools"; a 5-server setup "can consume ~55k tokens… Tool search typically reduces this by over 85
   percent"; up to 10,000 deferred tools/request; regex and BM25 variants shipped, with a documented
   "Custom tool search implementation" path for "embeddings or semantic search". **Scope check: this
   page is entirely about the `tools` array and never mentions Skills.** Observable corroboration:
   this session's own system prompt shows ~180 MCP tools deferred behind `ToolSearch` while all ~148
   skills are listed inline with full descriptions — the mechanism shipped for tools, not for skills.
4. **Gillespie & Perry, "Scaling Enterprise Agent Routing: Degradation, Diagnosis, and Recovery"**
   (arXiv:2606.17519, submitted 2026-06-16). https://arxiv.org/abs/2606.17519 — verified to exist and
   to state: single-step routing on a "110-agent, 584-tool catalog"; "routing F1 on under-specified
   requests drops 16--23 percentage points across models"; embedding-based shortlisting "recovers
   +10--11pp F1 at full scale across all three models"; degradation decomposes into retrieval and
   confusion gaps; validated on 1,435 human-labeled utterances.
5. **Zhou et al., "A Single Rewrite Suffices: Empirical Lessons from Production Skill Description
   Optimization"** (arXiv:2606.30775, submitted 2026-06-29). https://arxiv.org/abs/2606.30775 —
   verified: an automated pipeline using "false-positive and false-negative cases"; "a single LLM
   rewrite… captures most of the available improvement"; 79.2% F1 vs 79.4% for manually tuned; effort
   "from 120 minutes to 3.8 minutes (32 times speedup)".
6. **Gan & Sun, "RAG-MCP: Mitigating Prompt Bloat in LLM Tool Selection via Retrieval-Augmented
   Generation"** (arXiv:2505.03275, submitted 2025-05-06). https://arxiv.org/abs/2505.03275 —
   verified: retrieval over indexed tool metadata "more than triples tool selection accuracy (43.13%
   vs 13.62% baseline)" and "significantly cuts prompt tokens (e.g., by over 50%)".

## 3. Gap analysis

**Where CCv3 is ahead.**
- We own an eval + collision harness (`.claude/skills/_eval/`). Anthropic explicitly says no built-in
  evaluation exists and users must build their own (source 2). We built one — and then stopped
  running it for five months.
- We now have something almost nobody has: **a measured, retrospective routing-precision number on
  our own live traffic** (§1a). Source 5's entire method depends on having FP/FN cases; §1a *is* a
  4-month FP corpus, already collected.
- The prereq/peer graph and priority tiers are genuinely orthogonal to anything the first-party spec
  provides.

**Where CCv3 is even.** Description-driven selection. The field converged on "the LLM reads a good
description" (sources 1, 2). Our native layer does exactly that.

**Where CCv3 is behind — and the ranking has changed.**

1. **A hard gate with ~2% observed precision went live four days ago.** `databases` blocked 103 times,
   loaded twice. That branch was inert for ~186 days (`:661-666`, fixed by `fd906dd`), so nobody has
   ever experienced its real cost. This is not a routing-quality nicety; it is a live behavioral gate
   whose matching is an unbounded substring test with no word boundary and no ambiguity check on its
   riskiest terms. **This did not exist as a risk when either prior proposal was written.**
2. **The catalog is ~64% dead weight by measurement.** 95 of 148 skills untouched in 33 days, and 40
   of 58 hook-registered skills never loaded. Source 2's own guidance — content Claude never accesses
   "might be unnecessary" — plus source 3's 30–50 accuracy knee, both point the same way: the cheapest
   available precision gain is a smaller catalog. `SG-03`/`DEL-12` (`docs/system-update/BACKLOG.md:96,105`)
   were blocked on exactly the usage data §1a now supplies.
3. **The nudge layer is net-negative on its own numbers.** 1,489 suggestions bought 118 loads at a
   mean of 9.7 entities per firing. Source 4 names this precisely: a "confusion gap" that persists
   even with perfect retrieval — surfacing more candidates does not help, and here it costs context on
   every prompt.
4. **Still no retrieval arm, and still no first-party way to get one for Skills.** Source 3's
   `defer_loading` is `tools`-array only, confirmed by fetch *and* by direct observation of this
   session. Sources 4 and 6 show retrieval works (+10–11pp F1; 13.62%→43.13%) — but at 110 agents/584
   tools and thousands of tools respectively, not at 148 skills whose descriptions the model already
   reads semantically.

## 5. Integration approach

**R1 — de-fang the blockers (effort S, risk low, do first).**
Files: `.claude/hooks/src/skill-activation-prompt.ts:407-409` (word-boundary match for keywords below
a length threshold, substring retained for long/distinctive ones);
`.claude/hooks/src/skill-validation-prompt.ts:41-63` (extend `AMBIGUOUS_KEYWORDS`);
`.claude/skills/skill-rules.json` (**both copies**, per `git-sync-workflow.md` — the repo copy is
canonical). Standard hook lifecycle applies: rebuild `dist/`, and per `.claude/rules/proactive-delegation.md`
re-run `bash scripts/audit-braintrust-emits.sh` after any TS hook edit.
Verification: replay the `index`/`INDEX.md` case and confirm `databases` no longer matches, then
confirm a genuine SQL prompt still does.
BACKLOG ties: none open — this is new, created by `fd906dd`. Worth a line in the `fd906dd` follow-up
trail since that commit revived it.
What could go wrong: word boundaries could *under*-match legitimate triggers (`N+1`, `/fix`, `PLAN-`
are punctuation-bearing and would break under a naive `\b`). Mitigate by applying boundaries only to
purely alphabetic keywords and gating on R3's eval set before/after.

**R2 — census-driven prune (effort M, risk medium).**
Artifacts: the census script + its output committed under `docs/self-improvement/`; the candidate list
feeds `SG-03` (`BACKLOG.md:96`) and the deferred `DEL-12` (`BACKLOG.md:105`).
Method: archive, never delete — `.claude/skills/_archive/` already exists as the convention. Batch by
family (the Fourth-presentation cluster is already flagged as ~46MB of duplication at
`CURRENT-STATE.md:52`). Every removal also removes its `skill-rules.json` entry in the same commit, or
the `QW-08` ghost-entry class returns.
What could go wrong: **zero-touch ≠ useless.** A disaster-recovery or once-a-quarter skill legitimately
shows zero loads in 33 days (`wizard`/bootstrap-shaped skills especially). The census ranks candidates;
it does not decide. Require an explicit keep/archive judgement per skill, and never batch-archive on
the count alone.

**R3 — eval refresh (effort M — eval-set authoring dominates, risk low).**
Files: `.claude/skills/_eval/eval-harness.js`, `collision-test.js`, `eval-sets.json`; stamp results
and wire a staleness check into `scripts/health_check.py` (the `/health-check` skill already runs
weekly). Run **after** R2 so the eval covers the kept catalog rather than 95 skills on the way out.
What could go wrong: the eval measures only the keyword layer, so a green number can coexist with poor
*native* selection — state that limitation next to the number rather than letting the number imply
more than it measures. This is exactly the vacuous-gate failure class already recorded for this repo.

**Sequencing:** R1 (days) → R2 (prune) → R3 (measure the pruned catalog) → R4 (optimize what survives).
R5/R6/R7 stay unbuilt.

## 6. Benefits

- **Removes a live behavioral hazard (R1).** A hard "you MUST invoke X before responding" gate with a
  measured 103→2 hit rate started reaching the model on 2026-07-28. It already derailed this session's
  opening turn. Dave gets back prompts that aren't hijacked by a substring collision inside a filename.
- **A measurably lighter and sharper session (R2).** 95 unused skills carry description weight in every
  session (~100 tokens each, source 1 — order ~9.5k tokens for the dead tail alone) and dilute the set
  the model picks from, against a documented 30–50 accuracy knee (source 3). Pruning is the one lever
  we fully own, since Skills have no deferral path.
- **Less noise per prompt (R1+R2).** 9.7 suggested entities per firing, ~92% of which are never acted
  on, is attention tax on every technical prompt.
- **Numbers that mean something (R3).** "Skills system healthy" currently rests on a March snapshot
  covering 97 of 148 skills. After R3 it rests on a run over the catalog that actually exists.
- **A cheaper measurement habit (R6-as-revised).** The census is ~100 lines, runs offline over data
  already on disk, adds zero per-prompt latency, and answered in one pass the question two proposals
  budgeted a new telemetry pipeline for.

## 7. Open questions

1. **Is `databases`-as-blocker recoverable, or should all three blockers become `suggest`?** R1(c)
   demotes one; `systematic-debugging` (28 suggested → 9 loaded) and `code-review` (62 → 3) are better
   but still weak. 07-20's open question #4 asked whether `enforcement: block` should survive at all —
   §1a is the first evidence that can answer it, and the answer may be "no".
2. **How much of the 1,489→118 gap is the hook being wrong versus the model correctly ignoring a
   redundant nudge?** If native selection already had the right skill, a "wasted" suggestion is cheap
   noise rather than a miss. Distinguishing these needs the loaded-skill set compared against the
   suggested set *per prompt*, which the census can do but this pass did not.
3. **Which of the 95 zero-touch skills are deliberately rare?** Needs a human keep/archive pass; the
   census cannot infer intent. (§5, R2 risk.)
4. **Did the `fd906dd` revival change behavior in the 4 days since?** The window measured here is
   almost entirely pre-revival. Re-running the census over 2026-07-28→now, once enough sessions
   accumulate, gives the first real post-revival blocking-cost number.
5. **Will Anthropic extend `defer_loading`/tool search to Agent Skills?** Verified absent today
   (source 1 documents no such mechanism; source 3 is `tools`-array only). If it ships, R5 flips from
   WATCH to near-free and the always-on description cost largely disappears. Worth tracking the Skills
   docs and changelog.
6. **Do the ~90 skills absent from `skill-rules.json` behave better or worse than the 58 in it?** The
   census can compare load rates for registered versus unregistered skills — a direct test of whether
   the hook layer earns its keep at all.
