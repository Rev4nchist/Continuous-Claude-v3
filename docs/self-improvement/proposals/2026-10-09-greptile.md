# Greptile replaces CodeRabbit in the CCv3 PR loop (2026-10-09)

Verdict: **ADOPT Greptile as the PR review gate.** Build three small PRs: a repo config, a
reviewer-neutral status adapter, and one rewritten on-demand rule. **SKIP** Greptile's Claude Code
plugin and MCP server for now. **Steal** two ideas from its `greploop` skill: a SHA-bound wait and an
iteration cap. Status: **approved 2026-10-09**; PR-1 in progress.

Dave's decisions (2026-10-09): "go with your recommendations". D1 confidence at least 4/5. D2 remove
CodeRabbit after PR-2 lands and 2 real PRs pass the Greptile gate. D3 rule name `pr-review-loop`.
D4 keep review on every push. D5 skip the Greptile plugin and MCP server.

Why now: CodeRabbit rate-limits most CCv3 PRs (Essentials plan). PRs #67-#70, #79, #99, #106 and #111
all landed with `-IgnoreReview`. On 2026-10-09 the PR watcher sent three out-of-date reports, all
driven by CodeRabbit status. Greptile reviewed the same PRs with no limit hit.

How it was built: an `oracle` agent read the Greptile docs (https://www.greptile.com/docs, 26 cited
pages). A `scout` agent mapped every CodeRabbit dependency in the repo and in `~/.claude`. Live GitHub
data from PR #111 filled the gaps the docs leave open.

## 1. Answer

- **The review gate is one script.** `scripts/github/coderabbit-status.mjs` hard-codes the CodeRabbit
  bot login, status name, review-proof text and rate-limit strings. `land-pr.ps1` and the `ccv3-mods`
  pr-loop (`/watch`, `/land`, `pr_watch`, `pr_status`) both call it. Replace it with a
  reviewer-neutral `review-status.mjs` that has a Greptile adapter. Keep the JSON contract, so the
  plugin and `land-pr.ps1` change only a path and some text.
- **Greptile gives a better proof than CodeRabbit did.** It writes a summary block into the PR body
  with machine-readable markers. "Reviewed this head" becomes a string compare, not text guessing.
- **One rule replaces `pr-coderabbit-loop.md`.** It tells the agent how to wait, read P0/P1/P2
  findings, fix or dismiss, and resolve threads. Rename it `pr-review-loop.md` so the next reviewer
  switch is cheap.
- **A `.greptile/config.json` makes the setup visible in the repo.** Today every setting lives in
  the dashboard. The config also teaches Greptile three CCv3 rules that cause real defects here.
- **No new skill.** The loop fires at "PR opened" and "land", which the rule-router already
  catches. A skill would add listing cost for no new trigger.

## 2. Greptile signals (live PR #111 vs docs)

| Question | Signal | Source |
|---|---|---|
| Was this head reviewed? | PR body block `<!-- greptile_comment -->` ... `<!-- /greptile_comment -->`, with a "Last reviewed commit" link to `/commit/<40-hex>` equal to the head SHA. Also a check run from app `greptile-apps` on the head SHA with `completed` / `success`. | live #111 |
| Confidence | `<!-- greptile_confidence_score:N -->` in the PR body, 0-5. 5 = merge, 4 = minor polish, 3 or less = address feedback first. | live #111; docs `/code-review/first-pr-review` |
| Review count | "Reviews (2)" in the same block. | live #111 |
| Findings | Inline comments by `greptile-apps[bot]` with P0/P1/P2 badges. A GitHub review object exists only when comments are added. 0 comments means only the check run and the body block change. | live #111 |
| Severity meaning | P0 must fix before merge. P1 should fix. P2 consider fixing. | docs `/code-review/first-pr-review` |
| Cancelled review | Check `completed` / **`neutral`**, summary "Review was cancelled". It happens when a newer push supersedes the review. **Not a review.** | live, commit `3767929` |
| Failed review | 😕 reaction; check conclusion `failure`. | docs |
| Skipped (spend cap) | MCP status `SKIPPED`. The GitHub signal is undocumented. Treat "no Greptile check on the head after 15 minutes" as unavailable. | docs `/code-review-bot/billing-seats` |
| Re-review on push | Already on in this repo's dashboard (`3767929` and `5dfb333` each got a check). The doc default is `["open"]` only. | live; docs `/code-review/greptile-config-reference` |
| Replies | Greptile reads replies that tag `@greptileai` and learns from them. It does not resolve GitHub threads itself. | docs `/code-review/developer-essentials`, `/mcp-v2/tools` |
| Cost | $30 per seat per month, 50 credits included. Base review 1 credit, Plus 3, Apex 10. Overage $1 per credit. No rate limit documented. | docs `/code-review-bot/billing-seats`, `/code-review/review-tiers` |

**Trap for the switch:** `coderabbit-status.mjs:76` accepts any check run that ends `neutral`. Today
that is harmless, because READY also needs CodeRabbit's own proof. A cancelled Greptile review also
ends `neutral`, so an adapter that copied line 76 would call a superseded review green. The adapter
must treat `neutral` from `greptile-apps` on the head as "not reviewed".

## 3. Proposed changes (three PRs, in order)

### PR-1: `.greptile/config.json` (small, immediate value)

Config is read from the PR's source branch, so PR-1 tests itself.

```json
{
  "autoReview": ["open", "push"],
  "statusCheck": true,
  "strictness": 2,
  "ignorePatterns": ".claude/hooks/dist/**\n**/*.min.js\n**/package-lock.json\n.claude/cache/**\ndocs/reviews/**",
  "instructions": "CCv3 is a Windows-first Claude Code harness. Many files exist as two copies (repo and ~/.claude, src and dist, settings.json and its template). Prefer findings about correctness, security and drift between the two copies over style.",
  "rules": [
    { "id": "hook-dist", "scope": [".claude/hooks/src/**"], "severity": "high",
      "rule": "After a change to a hook in .claude/hooks/src/<name>.ts, rebuild it and include any changed .claude/hooks/dist/<name>.mjs in the same PR. A type-only or comment-only edit that leaves the built output byte-identical needs no dist change." },
    { "id": "settings-template", "scope": [".claude/settings.json", ".claude/settings.json.template"], "severity": "high",
      "rule": "A hook registration added to .claude/settings.json must also be added to .claude/settings.json.template, and the reverse." },
    { "id": "no-rules-dir", "scope": [".claude/**"], "severity": "medium",
      "rule": "Never add files under .claude/rules/. Rules live in .claude/rules-src/; .claude/rules/ makes Claude Code load every rule twice." }
  ]
}
```

`autoReview` and `statusCheck` match what the dashboard does today. Writing them down stops a silent
dashboard change from breaking the gate.

### PR-2: reviewer-neutral status adapter

- New `scripts/github/review-status.mjs`. `coderabbit-status.mjs` stays one release as a thin alias,
  then goes.
- **READY** needs all of:
  - The head is reviewed. The PR-body "Last reviewed commit" SHA equals the head, AND a
    `greptile-apps` check on the head is `completed` / `success`.
  - Confidence is at or above the bar (decision D1).
  - 0 unresolved review threads from any reviewer (GraphQL `isResolved`, unchanged).
  - 0 open P0 comments.
  - Every other check and status is green. A `neutral` Greptile check on an *older* SHA is ignored.
  - `mergeable_state` is `clean`.
- **UNAVAILABLE** replaces `rateLimited`. It is set when the head check is cancelled with no newer
  check, has failed, or no Greptile check appears within 15 minutes of the head push. Land only with
  `-IgnoreReview` on Dave's yes, as today.
- **JSON contract:** keep `ready`, `head`, `reviewedHead`, `unresolved`, `mergeable_state`, `prState`,
  `merged`, `reasons`. Add `reviewer`, `confidence`, `unavailable`. Keep `rateLimited` as an alias of
  `unavailable` until the plugin is updated.
- **Rewire:** `land-pr.ps1:59` and the error text at `:68`. Plugin `hooks/pr-loop/index.ts:39`
  (`STATUS_SCRIPT`) and the description strings. `model.ts` message strings and the STALLED comment.
- **Tests:** rewrite `coderabbit-status.test.mjs` as `review-status.test.mjs`. Fixtures come from

## 4. The working rule (draft of `pr-review-loop.md`)

1. **When a PR opens,** call `pr_watch` with the PR number in the same turn.
2. **After each push, wait for the review of that exact head.** Use `pr_status`, not the 👍 emoji or a
   bot comment. Greptile already re-reviews on push. Post `@greptileai` only if no Greptile check
   appears on the head after 15 minutes. Each review costs a credit.
3. **Batch fixes into one push.** Every push is a new review and a new credit. Cap the fix loop at
   5 rounds, then report to Dave.
4. **Read every finding.**
   - P0: fix before merge. Never dismiss a P0 without Dave's yes.
   - P1: fix, or dismiss with a one-line reason.
   - P2: fix if cheap, or dismiss with a reason.
5. **To dismiss a finding,** reply with `@greptileai <reason>` (Greptile learns from tagged replies),
   add a 👎 reaction to the original comment, then resolve the thread through GraphQL
   `resolveReviewThread`. To mark a fix, reply "Fixed in <sha>", then resolve. Greptile never resolves
   GitHub threads itself.
6. **Never resolve a thread you did not act on.** Verify `isResolved` through GraphQL, not the bot's
   text.
7. **Do not raise the review tier** (`@greptileai review this at apex`, 10 credits) without Dave's
   yes. That is spend.
8. **Before calling a PR ready,** run `node scripts/github/review-status.mjs <N>`. Say "ready" only
   on READY.
9. **Landing:** on Dave's yes, `pwsh -File scripts/github/land-pr.ps1 -Pr <N>`. If UNAVAILABLE, post the
   reason on the PR and use `-IgnoreReview`, as today.
10. **When you edit a PR body,** keep the `<!-- greptile_comment -->` ... `<!-- /greptile_comment -->`
    block byte for byte. It is the review proof.

## 5. Skipped, and why

- **Greptile Claude Code plugin** (`/greptile:review`, `/check-pr`, `/greploop`). `greploop` pushes and
  loops on its own until 5/5. That duplicates `pr_watch` and `/land`, and it bypasses the
  Dave-presses-Land model. It also adds skill-listing cost. Stolen instead: the SHA-bound wait and
  the 5-round cap (§4 steps 2-3).
- **Greptile MCP server** (`https://api.greptile.com/mcp`, OAuth). Its `get_merge_request` gives
  `hasNewCommitsSinceReview`, but the PR-body marker and the check run already prove the same
  thing through `gh`. It would be one more OAuth surface and one more tool list. Revisit only if the
  GitHub signals prove unreliable in the first 10 PRs.
- **Auto-approve** (`autoApprove`). It is off by default and stays off. Only Dave's yes lands a PR.

## 7. Risks

- **Undocumented signals.** The check name, `neutral` = cancelled, and the PR-body markers come from
  live data, not the docs. Mitigation: the adapter tests use real fixtures, and an unknown shape
  fails closed (exit 2, "could not determine"), never READY.
- **Body edits erase the proof.** A PR-body PATCH that drops the Greptile block removes the review
  marker. Mitigation: §4 step 10. Without the block, the adapter still reports whether the check run
  reviewed the head, with `confidence: null`, but it adds a reason line, so it **never returns
  READY** without the block. PR-2 has a test for this case.
- **Silent skip at the spend cap.** Mitigation: the 15-minute UNAVAILABLE timeout.
- **Learning drift.** 👎 reactions train Greptile per org. A wrong dismissal teaches it to stay quiet.
  Mitigation: never dismiss a P0, and give every dismissal a reason.
