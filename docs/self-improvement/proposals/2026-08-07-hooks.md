## 2. Frontier scan

The last pass scanned the security literature. This pass deliberately scans a different axis — **how other harnesses structure the interception layer itself** — because that is where the field moved and where CCv3's recurring bug class lives.

**(a) Every major framework converged on the same three primitives within ~12 months, and all three run in-process.**

- **LangChain / LangGraph v1** documents two hook *styles*: node-style (`before_agent`, `before_model`, `after_model`, `after_agent`) and wrap-style (`wrap_model_call`, `wrap_tool_call`). The wrap contract is explicit: "You decide if the handler is called zero times (short-circuit), once (normal flow), or multiple times (retry logic)" (https://docs.langchain.com/oss/python/langchain/middleware/custom, fetched today).
- **Pydantic AI** goes furthest: `before_*` / `after_*` / `wrap_*` / `*_error` variants across Run, Node, Model-request, Tool-validate, Tool-execute, Output-validate and Output-process levels, **with a documented composition rule** — verbatim: "within a single Hooks instance, `before_*`, `after_*`, and `on_*_error` fire in registration order (the order they were defined or passed to the constructor). `wrap_*` nests as middleware, with the first-registered wrapper as the outermost layer" (https://pydantic.dev/docs/ai/core-concepts/hooks/, fetched today).
- **Google ADK** exposes `before_tool_callback` / `after_tool_callback` and `before_model_callback` / `after_model_callback` registered on the agent constructor (https://google.github.io/adk-docs/callbacks/types-of-callbacks/). **Microsoft Agent Framework** ships a three-layer chain-of-responsibility middleware pipeline (Agent Run / Function Calling / IChatClient) with an explicit `next()` (https://learn.microsoft.com/en-us/agent-framework/agents/middleware/). [Both URLs relayed by the research pass and HTTP-verified there; I did not personally fetch these two.]

**(b) The one primitive a subprocess hook model structurally cannot have: `wrap`.** A shell-out hook can allow, deny, or rewrite input. It cannot hold local state across the before- and after-halves of the same tool call, because the "before" process has already exited. Every framework above gets that for free from the call stack. CCv3 substitutes external state files — and that substitution is exactly where its documented failures live: `agent-error-capture` stored nothing for 161 days, the Braintrust off-switch was inert, and 19 hooks were mute for 186 days. This is a real, nameable architectural trade — process isolation and language-agnosticism bought at the price of wrap-semantics and typed in-band returns. It is not automatically the wrong trade (§4, N6).

**(c) The frontier separates *observing* from *enforcing* at the API level — CCv3 does not, and there is now a verified upstream hazard proving why that matters.**

- **OpenAI Agents SDK** makes guardrails a distinct primitive from observation, with a hard failure mode: "If an agent input or output fails a guardrail, the guardrail can signal this with a tripwire," and "The runner immediately raises an `InputGuardrailTripwireTriggered` or `OutputGuardrailTripwireTriggered` exception and halts agent execution." It defines three kinds — input, output, and **tool** guardrails, the last of which "wrap function tools and let you validate or block tool calls before and after execution" (https://openai.github.io/openai-agents-python/guardrails/, fetched today).
- **Claude Code issue #28812, "[DOCS] PreToolUse hook `permissionDecision` "allow" silently bypasses native permission system" — closed as not planned** (https://github.com/anthropics/claude-code/issues/28812, fetched today). Verbatim: *"There is no warning that returning `permissionDecision: "allow"` as a default/fallthrough in a PreToolUse hook **completely replaces the native permission system**. This means the "Allow / Always allow / Deny" prompt is never shown for any tool call that passes the hook's checks."* The reported workaround is to emit no JSON at all rather than an explicit allow.
  - **This is the exact shape of `permission-auto-allow`.** A hook whose intent is "block the bad, defer the rest" instead becomes "block the bad, pre-approve everything else." CCv3 rediscovered this independently three times and patched it three times with named exclusions (§1). Upstream has declined to fix or even document it, so — like #32376 in the last pass — it is permanently the operator's problem.
  - [Note] A second reported issue (`#13339`, `permissionDecision: "ask"` ignored in the VS Code extension) was relayed by the research pass but I did not independently fetch it; I am not resting anything on it.

**(d) Observability standards have not caught up to policy layers — an unclaimed lead, not a gap to close.** The OpenTelemetry GenAI agent conventions define `create_agent`, `invoke_agent`, `invoke_workflow`, `plan`, and `execute_tool` spans (https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md, fetched today; the older path in the main semantic-conventions repo is now a redirect stub). There is **no span, event, or attribute for a guardrail, policy check, permission decision, or safety filter**. So "did a guard fire, and what did it decide" is not yet a standard telemetry concept. A harness that emits it is ahead of the standard rather than merely compliant.

**(e) Policy-as-code for agent tool calls is now vendor-documented, not just academic.** Microsoft's Agent Governance Toolkit documents an OPA/Rego and AWS-Cedar policy-decision-point pattern authorizing individual agent tool calls before execution (https://microsoft.github.io/agent-governance-toolkit/tutorials/08-opa-rego-cedar-policies/) [relayed and HTTP-verified by the research pass; not personally fetched]. This strengthens the last pass's R7 (AgentSpec DSL, https://arxiv.org/abs/2503.18666, ICSE 2026) from "one peer-reviewed paper" to "a paper plus a shipping vendor pattern." I am deliberately **not** re-quoting AgentSpec's effect-size figure this pass — the research pass could not confirm it from the abstract alone, so treat the paper as evidence for the *approach*, not for a number.

**(f) The honest negative result: nobody has shown deterministic guardrails reduce agent failure rates.** The two most-cited artifacts measure the *problem*, not the *fix*. **AgentHarm** (https://arxiv.org/abs/2410.09024) benchmarks 110 malicious agentic tasks across 11 harm categories and finds leading models "surprisingly compliant" without jailbreaking — a model-behavior result, not a guardrail-efficacy result. **ToolEmu** (https://arxiv.org/abs/2309.15817, ICLR 2024) provides an LM-emulated sandbox for identifying agent risks. A dedicated search found **no published study comparing agent unsafe-action rates with versus without a deterministic hook layer**. That absence should be stated plainly in any pitch for more guard work: the case for guards here rests on incident evidence from this repo, not on external effect sizes.

**(g) Carried forward, unchanged and not re-argued:** the Check Point CVE chain where hook/config files were the vector (https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/); Willison's lethal trifecta (https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/); the ~30-event Claude Code hook surface and its five handler types (https://code.claude.com/docs/en/hooks, and the official plugin-dev hook skill at https://github.com/anthropics/claude-code/blob/main/plugins/plugin-dev/skills/hook-development/SKILL.md).

**The synthesis that matters, and it is different from the last pass.** Twelve days ago the framing was "live but ungoverned." Today it is sharper: **the layer got much better at knowing when it is broken, and no better at stopping anything.** That was arguably the right order — a guard you cannot prove fires is worse than no guard, and the contract ratchet proved 19 of them were not firing. But the ledger is now lopsided. Detection shipped; enforcement did not; and the one metric that measures the gap between committed intent and live behaviour moved the wrong way (16 → 17). The frontier's answer to "why does an undifferentiated hook layer keep producing silent no-ops" is the observe/enforce type split that OpenAI ships and CCv3 does not — which means the already-recommended R5 now has an external design precedent, not just internal reasoning.

## 4. Recommendations

Carried-forward items are listed once with status and are **not** re-argued; the case for them is in the 2026-07-26 file.

**N1 — Commit `permission-auto-allow`, and invert it from denylist to allowlist. ADOPT. Highest new-value item this pass.**
It is the only permission-*widening* hook in the system, it is registered only in the un-version-controlled active settings, and #28812 documents exactly this pattern silently replacing the native permission prompt — closed as not planned, so no upstream fix is coming. Its three exclusions were each added after an incident, which is the signature of a control that is one unknown-unknown behind. Two changes, both small: (a) register it in the repo `settings.json` so its behaviour is reviewable in a diff; (b) flip the default — enumerate the tools that *may* be auto-allowed rather than the three that may not. Where possible prefer emitting **no decision** over an explicit allow, per the workaround in #28812, so the native prompt survives as the backstop.

**N2 — Extend `registration-reconcile.mjs` to fail on undeclared active-only registrations. ADOPT (small).**
The script exists, already parses both files, and its own header names this as the shelf-life risk. Today it verifies the live config *could* be rebuilt; it does not notice 17 hooks accumulating outside version control. Add a committed `active-only-allowlist.json` — an operator declares each intentional machine-local registration once, and anything unlisted fails. That converts silent accumulation into a one-line decision, and it is a far cheaper down payment on the last pass's R2 than a new integrity hook. Seed the allowlist with the current 17 so it starts green, then let it ratchet.

**N3 — Type the harness as guard vs observer, using the OpenAI Agents SDK split as the design anchor. ADOPT (carried forward = R5 + ST-02, upgraded rationale).**
Unchanged in necessity; the argument is now external rather than internal. OpenAI ships observation and enforcement as *different primitives* with different failure modes (tripwire → raise → halt). CCv3 has one `command` type for all 114 hooks, which is precisely how `guardrail-enforcer` could emit a field the harness does not read and look healthy for 186 days. A `createGuard` / `createObserver` split — observers structurally unable to emit a decision field, guards required to emit a legal one — makes that bug unrepresentable rather than merely detectable. Bundle the canonical `getSessionId` into the same harness (6 impls → 1). **Ship one hook per commit**; bulk-editing shared hook files is this repo's documented regression pattern.

**N4 — Emit a policy-decision record for every guard fire. ADOPT (small, and it unblocks the big one).**
Verified: OpenTelemetry's GenAI agent conventions define no guardrail/permission span (§2d). CCv3 already writes structured jsonl (`.claude/logs/roadmap-sync.jsonl` is the model) and already emits to Braintrust. One shared `recordDecision({hook, event, tool, decision, reason})` call inside N3's `createGuard` gives three things at once: the first real answer to "which guards actually fire in daily work," the **precondition for shipping R3's Rule-of-Two guard warn-only and mining the distribution before enforcing**, and a telemetry shape ahead of the current standard. Do this *with* N3, not after.

**N5 — `mcpServers` integrity gate + config/artifact integrity detector. ADOPT (carried forward = R1 + R2, unchanged, still the top security items).**
Both remain unshipped 12 days on, and `sync-to-active.sh` still launders a repo-tracked file into global host-privileged MCP config at two call sites (`:331`, `:494`). Nothing in this pass changes the analysis or the priority. If only one enforcement item ships this month, it should be this one — N1–N4 are cheaper, but this is the one with a matching CVE.

**N6 — Re-platform the hook layer onto in-process middleware. SKIP (and now for a stated reason, not an assumption).**
The wrap-semantics gap in §2b is real and it maps onto real CCv3 bugs. It is still not worth 114 rewrites: the subprocess model buys process isolation, language-agnosticism, and crash containment, and Claude Code's hook contract is a subprocess contract regardless of what CCv3 prefers. The right response is to stop *emulating* wrap where it is fragile — N3/N4 give before-side decisions a durable record without pretending the after-side shares memory — and to record the trade-off in the hook docs so the next person does not rediscover it as a bug.

**N7 — Declarative policy DSL for the `rules/*.md` safety tables. WATCH (carried forward = R7, evidence strengthened).**
Now backed by both a peer-reviewed DSL (AgentSpec, ICSE 2026) and a shipping vendor pattern (Microsoft's OPA/Cedar toolkit). Still gated on N3 and still too large to start. Revisit if the imperative-guard count keeps growing.

**N8 — Build a ToolEmu/AgentHarm-style evaluation of this hook suite. SKIP (this iteration), but record the reason.**
§2f is the honest finding: no published work shows deterministic guardrails reduce agent failure rates, and CCv3 has no evaluation of its own either. Building one is real work for a single-operator harness and would compete with N1–N5. The value of naming it is to keep the guard case resting on what it actually rests on — incident evidence from this repo (19 mute hooks, 161 dead days, a false-positive file lock) — rather than on an effect size nobody has published.

**Retired: R6.** Claude Code 2.1.224 clears both sandbox CVEs. No action.

## 6. Benefits

- **The security posture becomes reviewable.** Today 17 hooks run that no committed file describes, and two of them are security controls pointing in opposite directions — a supply-chain guard and a permission-widener. After N1(a) + N2, a `git diff` shows what enforces on this machine, and a new undeclared registration fails a ratchet instead of accumulating silently.
- **One documented, upstream-unfixable footgun gets closed locally.** `permission-auto-allow` is a live instance of #28812 — a blanket allow that replaces the native permission prompt — in a hook that has already been patched three times reactively. N1 stops the fourth incident from being the one that matters.
- **Silent no-ops become unrepresentable rather than merely detectable.** The ratchet suite is real progress, but it catches the bug *after* it ships. N3's typed guard/observer split is how OpenAI's SDK prevents the same class at the API boundary. Given this repo's record — 186 days mute, 161 days storing nothing, an off-switch that never switched — moving from detection to prevention on this specific class is where the leverage is.
- **The oldest stuck recommendation finally gets its missing input.** N4 produces the guard-fire distribution that R3 has been blocked on across two proposals, at small cost, and as a side effect puts CCv3 ahead of the OpenTelemetry GenAI conventions, which define no guardrail span at all.
- **The remaining CVE-shaped path closes.** N5 removes the one place a repo-tracked file becomes global host-privileged MCP config. Dave pulls from a third-party upstream and a background post-commit hook syncs the result; this is the concrete risk in that workflow, and it is now the only carried-forward item with a matching real-world CVE.
- **Two anxieties can be retired.** Claude Code 2.1.224 clears both sandbox CVEs the last pass flagged (R6 done), and the wrap-semantics gap is now a *documented deliberate trade* rather than an unexamined weakness — so nobody spends a session rediscovering it as a bug or proposing a 114-hook rewrite.

## 7. Open questions

1. **Does inverting `permission-auto-allow` to an allowlist reintroduce the friction it was built to remove?** It exists to work around `.claude/` sensitive-file prompts (v2.1.78+). If that workaround still needs breadth, the honest fix may be narrowing its *scope* (paths) rather than its *tool list*. Measure prompt volume before flipping — this is exactly what N4's telemetry is for.
2. **Are the 17 active-only registrations deliberate machine-local config or accumulated drift?** Carried over unanswered from the last pass and now one worse. N2 forces the decision but does not make it; someone has to classify all 17 once. The presence of `package-install-guard` in that list suggests at least some are accidental.
3. **Why do the enforcement items keep not shipping?** Four of them are now 0-for-2 across proposals while detection work shipped promptly in the same window. If the reason is that enforcement risks breaking a working setup, then the sequencing advice ("warn-only first, enforce after a clean week") needs to become a hard convention rather than a suggestion — and N4 is the prerequisite for it.
4. **Does the deployed 2.1.224 build actually honour `defer`, `updatedInput`, `if`, and `SubagentStart`/`SubagentStop`?** Unanswered from the last pass; still unanswered, because this was a read-only run. One canary hook resolves all four and gates any platform-surface work. Cheap, and it stays cheap.
5. **Should CCv3 emit a guardrail span, or wait for OpenTelemetry?** Emitting now means inventing a local shape that may diverge from a future standard. Given no standard exists and N4's value is immediate, my inclination is to emit a plain jsonl record now and map it to spans later — but the divergence cost is real and unmeasured.
6. **Is 34 unregistered hook sources a prune candidate or a staging area?** Unchanged from the harness-strategy Step 10 arc. Worth a decision before the number grows again; note the prior lesson that fossil files sometimes carry the only coverage of something live, so audit before deleting.
7. **Can any of this be trusted while the model can edit it?** The last pass's question 8 stands, and the ratchets partly answer it: a ratchet that runs in CI or a scheduled task, outside the session, is a check the session cannot quietly weaken. Whether the current ratchets run anywhere other than by hand is unverified and worth confirming.
