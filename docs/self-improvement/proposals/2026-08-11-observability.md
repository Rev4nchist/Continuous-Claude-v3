## 1. Where CCv3 is today

### What shipped since 07-30

**The shutdown spool (`5abcb64`, 2026-08-08) — this is the big one.** `session_end` and `stop` used to perform a blocking HTTPS POST while the CLI tore the session down; a stalled connection measured **30.97s under a 10s budget**, and the harness cancelling the hook destroyed the batch. The commit message records the impact: "82 of 720 turns (11%) in 30 days never finalized, with single lost batches of 145 and 236 spans." Three root causes were fixed: `batch_insert_spans` returned a bare `[]` for success *and* failure alike (so every historical "Turn finalized" log line was uninformative); failures now spool to `~/.claude/state/braintrust_spool.jsonl` (fsync'd, lock-guarded, dead-lettered at 7 days) and drain at SessionStart or via a detached child; and HTTP 413 now splits by halving instead of retrying forever.

This directly answers 07-30's own open question 5 ("Should the emit path spool to a local JSONL and flush out-of-band?"). For the **Python span layer**, the answer shipped and is yes.

**The Stop-event move is scoped and unblocked** (`df04272`, `3732f65`, `802eb25`). `docs/hooks/braintrust-stop-event-scope.md` measures the defect: `braintrust_hooks.py stop` is registered under `SessionEnd` but written for per-turn work, so **7,610 of 8,726 turn spans (87%) across 1,637 sessions were opened and never closed** (`braintrust-stop-event-scope.md:19-30`). Both blocking prerequisites were resolved empirically and both came back favourable — `Stop` and `UserPromptSubmit` are serialized by the CLI (five held runs, zero overlaps, `:92-103`), and Braintrust accepts a child span whose parent has not arrived yet (`:111-118`). The remaining change was a deletion plus a registration.

**UPDATE, same day: this SHIPPED in `ccdd14b` (2026-08-11 11:14), after this proposal was drafted.** `stop` is now registered on a new `Stop` key in both `settings.json` copies (timeout 15000) and stays on `SessionEnd` as a safety net for an abrupt exit mid-turn. It no longer writes `current_turn_span_id`, and it is idempotent on re-entry — which it had to become, because clearing that key was silently doubling as the re-entry guard. Verified live: the STOP-hook count incremented on a turn boundary and `turn_last_line` appeared in session state. Recommendation 2 in §4 is therefore already done; read it as rationale, not as work outstanding.

### 🔴 A live defect, found while verifying the baseline

**The spool currently holds one record of 541,362,531 bytes (541 MB), spooled 2026-08-07, that has failed on every flush since.** Verified directly:

- `ls -la ~/.claude/state/braintrust_spool.jsonl` → 541,362,531 bytes, mtime 2026-08-11 07:31.
- `wc -l` → **1 line**. It is a single `{project_id, events[], spooled_at}` record; `spooled_at: 1786279884.67`, spans `created: "2026-08-07..."`.
- `braintrust_hook.log`, every flush from 2026-08-10 onward: `Spool flush: sent=0..1 retry=1 deferred=0 deadlettered=0 first_error=WriteTimeout: The write operation timed out`. Three such flushes today alone (07:28:12, 07:29:05, 07:31:24).

The mechanism, traced through `.claude/hooks/braintrust_hooks.py`:

1. `flush_spool` does `SPOOL_FILE.read_text(...).splitlines()` (`:447`) — the **entire 541 MB** into memory as one string, then `json.loads` on a single 541 MB line.
2. `_post_events` attempts the upload and raises `WriteTimeout` — a **transport** error. The server never returns a status code.
3. `_is_payload_too_large(detail)` tests for `"HTTP 413"` or `"content length exceeded"` (`:293-295`). A `WriteTimeout` matches neither, so **`_split_and_post` is never reached.** The halving fix is gated behind a server response the server never gets the chance to send.
4. `remaining.append(line)` → `_rewrite_spool(remaining)` writes 541 MB back to disk (`:519-521`).

So every session start and session end pays a 541 MB read, a 541 MB JSON parse, a timed-out upload attempt, and a 541 MB write — and the record is unchanged afterward. At `SPOOL_MAX_AGE_SECONDS = 7 * 24 * 3600` (`:48`) it dead-letters around **2026-08-14**, at which point `_deadletter` appends all 541 MB to the dead-letter file (≈1 GB on disk) and the spans are lost anyway.

Two honest qualifications. First, this is **not a regression** from `5abcb64` — before the spool, this batch would have been dropped silently. The fix converted silent loss into a visible, self-announcing tarpit, which is strictly better and is exactly why the "honest status" half of that commit was worth shipping. Second, the *upstream* cause is already documented: because `stop` runs once per session, "an entire session's LLM spans are built in one pass at shutdown … what produced the real 94-span / 19.4 MB batch that hit Braintrust's 10 MiB cap" (`braintrust-stop-event-scope.md:32-33`). This record is the same mechanism at roughly 28× that scale. `MAX_SPLIT_DEPTH = 6` yields 64 sub-batches; 541 MB / 64 ≈ 8.5 MB, so even if the split *had* triggered it would clear the 10 MiB cap only barely.

## 2. Frontier scan

Eight sources, all fetched and quote-verified this run. Two figures a research subagent supplied did **not** survive verification and are excluded: a claim that TRAIL's abstract cites OpenTelemetry-native traces and 841 span-level errors (the abstract says neither), and a claim that Braintrust's OTel guide states "<1ms per call" overhead (the page gives only qualitative claims). Four further 2026 arXiv IDs it returned were title-only and are omitted rather than cited on weak evidence.

**Trajectory-level failure attribution is now a real research area with numbers.**

1. **FALAT** — *Tracing Failures in LLM Agent Trajectories via Dependency-Guided Search*, Rafi, Ahasanuzzaman, Kim, Wang, Chen, 30 May 2026, [arXiv:2606.00765](https://arxiv.org/abs/2606.00765). Verbatim: "failure attribution cannot be treated as independent step-level classification" — because "later actions may appear incorrect, but only because they depend on an earlier corrupted state." FALAT "traces dependencies among decisions, tool outputs, and agent messages to distinguish error-introducing steps from steps that merely inherit or propagate prior mistakes," reaching "46.0% step-level accuracy on algorithm-generated trajectories and 29.1% on the more challenging hand-crafted trajectories" on the Who&When benchmark.
2. **AgenTracer** — *Who Is Inducing Failure in the LLM Agentic Systems?*, 3 Sep 2025, [arXiv:2509.03312](https://arxiv.org/abs/2509.03312). Sets the baseline this problem starts from: "Current state-of-the-art reasoning LLMs … remain strikingly inadequate for this challenge, with accuracy generally below 10%." It is "the first automated framework for annotating failed multi-agent trajectories via counterfactual replay and programmed fault injection," and `AgenTracer-8B` "outperforms giant proprietary LLMs like Gemini-2.5-Pro and Claude-4-Sonnet by up to 18.18%," delivering "4.8-14.2% performance gains" downstream. Older than the 3–9 month window; included because it is the reference point FALAT measures against.
3. **TRAIL** — *Trace Reasoning and Agentic Issue Localization*, 13 May 2025, [arXiv:2505.08638](https://arxiv.org/abs/2505.08638). "148 large human-annotated traces … grounded in established agentic benchmarks," and the sobering result: "modern long context LLMs perform poorly at trace debugging, with the best Gemini-2.5-pro model scoring a mere 11% on TRAIL." Foundational, and the reason to treat any "just have an LLM read the trace" plan with suspicion.
4. **MAST** — *Why Do Multi-Agent LLM Systems Fail?*, 17 Mar 2025, [arXiv:2503.13657](https://arxiv.org/abs/2503.13657). "MAST-Data, a comprehensive dataset of 1600+ annotated traces collected across 7 popular MAS frameworks," and a taxonomy "developed through rigorous analysis of 150 traces … validated by high inter-annotator agreement (kappa = 0.88)," identifying "14 unique modes, clustered into 3 categories: (i) system design issues, (ii) inter-agent misalignment, and (iii) task verification." A ready-made off-the-shelf failure vocabulary.

**Automatic failure clustering is now a shipped vendor feature, on the platform we already pay for.**

5. **Braintrust Topics** — [braintrust.dev/articles/what-are-topics-in-braintrust-2026](https://www.braintrust.dev/articles/what-are-topics-in-braintrust-2026). Verbatim: it "gives teams a scalable way to review production traces by automatically classifying logs by user intent, sentiment, and issues, then grouping similar traces into clusters that teams can inspect and act on." Mechanics: "Once at least 100 facet summaries have been collected, Braintrust uses a `brain-embedding-*` model to convert each summary into a vector, then groups similar summaries into topics." It regenerates "once per day," with `bt topics poke` to force a run and `bt topics rewind` to replay history. This is unsupervised clustering, distinct from the server-side online scoring 07-30 correctly SKIPped.

**Failure promotion has a documented workflow — but only in vendor material.**

6. **Braintrust, production failures → regression tests** — [braintrust.dev/articles/turn-llm-production-failures-into-regression-tests](https://www.braintrust.dev/articles/turn-llm-production-failures-into-regression-tests). Five steps: "Capture the failed trace," "Diagnose the failure mode," "Promote the trace into a regression dataset," "Write a scorer for the recurring pattern," "Gate releases on the scorer." On the dataset row: "should preserve the input, the expected behavior when a gold answer exists, and metadata such as the failure label, source span ID, timestamp, prompt version, and model version." Note honestly: I found **no academic benchmark or paper** formalizing eval-set drift; this is industry practice, not a validated method.

**Instrumentation cost: the field's answer is batch-and-defer, and sample at the tail.**

7. **Braintrust OTel tracing guide** — [braintrust.dev/articles/opentelemetry-llm-tracing-guide](https://www.braintrust.dev/articles/opentelemetry-llm-tracing-guide). Verbatim: "Exporters batch spans and send them asynchronously, so network export does not block the model call or agent step"; "OpenTelemetry usually has low request-path impact when span export is batched and asynchronous"; and "Tail-based sampling at the Collector waits until a trace finishes before deciding whether to keep it, which allows teams to retain error traces while sampling successful runs." No quantified overhead figure is given on the page.

**Judge validation: the largest study yet says the metric everyone reports is the wrong one.**

8. **Reliability without Validity** — Norman, Rivera, Hughes, 17 Jun 2026, [arXiv:2606.19544](https://arxiv.org/abs/2606.19544). "21 judges from nine providers across MT-Bench, JudgeBench, and RewardBench … over 118 runs and approximately 541,000 individual judgments." Four findings, verbatim: "kappa deflation between exact match and Cohen's kappa is universal (33--41 pp on MT-Bench), judge rankings shift by up to 14 positions across benchmarks, high test--retest reliability (>0.95) coexists with severe position bias (>0.10) in two production-deployed judges (instantiating a consistency--bias paradox), and verbosity bias is small (<0.011) across our cohort under a single pairwise rubric." It explicitly covers "the April 2026 frontier."

## 3. Gap analysis

**Where CCv3 is ahead.** The spool's *design intent* — never silently discard, dead-letter rather than drop, log an explicit status — is more conservative than anything in the surveyed vendor material, and it was built from a measured production failure rather than a best practice. The empirical probes behind the Stop-event scope doc (a hook that varies its own hold to separate "the CLI serialized us" from "the human was slow") are better evidence discipline than the vendor guides model. Cross-family judging (`plan_rubric` on Codex) remains a genuine asset and is now better supported: source 8's "judge rankings shift by up to 14 positions across benchmarks" is an argument against trusting any single judge family.

**Where CCv3 is behind.**

- **Batch size is bounded at retry, not at write.** Source 7's frame is that export is *batched and asynchronous* by construction. CCv3 accumulates a whole session into one payload and only discovers the problem when the server rejects it — and, per §1, only *if* the server can reply at all. 541 MB is what "bound it at the wrong end" looks like.
- **Two pipelines, one durability story.** The Python span layer spools; the TypeScript score layer still `await`s a POST inline (`braintrust-score.ts:355`). Whatever the current per-tool-call cost is, it is paid on the critical path, and 07-30's measured ~640–690 ms figure predates the spool and was never re-measured after it. The number is now of unknown currency.
- **Sub-agent work is still unscored, and the frontier moved.** `closedqa` skips nested Task spans. Meanwhile FALAT (1) and AgenTracer (2) are about precisely the question a kraken/review fan-out raises — *which step, in which sub-agent, introduced the error* — and FALAT's central claim is that treating this as independent per-step classification is wrong. CCv3 does not attempt it at all.
- **We have never named our failure modes.** MAST (4) offers 14 modes in 3 categories at κ=0.88; Topics (5) offers automatic clustering with a 100-summary threshold on the platform we already use. CCv3 has scores but no taxonomy, so a low score is a number rather than a diagnosis.
- **The judge validation gap is now quantified.** 07-30 recommended reporting κ. Source 8 raises the stakes: exact-match agreement overstates judge quality by **33–41 pp**, and two *production-deployed* judges combined >0.95 test–retest reliability with >0.10 position bias. Our three judges have never been measured on either axis, and consistency would not have revealed the problem if we had.

**Where the frontier still does not fit us.** Unchanged and still correct: server-side online scoring cannot invoke local subscription CLIs. Also new this pass — the trajectory-attribution work (1, 2) assumes a *labeled* failure trajectory. TRAIL's 11% best-model result (3) is a direct warning against pointing a general LLM at a raw trace and believing the answer.

## 4. Recommendations

1. **ADOPT — Drain the 541 MB record, then bound the batch at write time.** Two parts. (a) Operationally: the record cannot succeed and will dead-letter to ~1 GB of disk on ~2026-08-14; deal with it deliberately rather than letting the timer do it. (b) Structurally: enforce a size cap **when spooling and when posting**, before any network attempt — if `len(json.dumps(events))` exceeds the cap, split immediately rather than waiting for a status code that a timed-out upload never returns. This is the direct fix for the §1 defect and the smallest item on this list. Related and nearly free: make `flush_spool` read the spool **line by line** instead of `read_text()` on the whole file (`braintrust_hooks.py:447`), so one poisoned record cannot make every flush a 541 MB memory event.
2. ~~**ADOPT — Implement the Stop-event move.**~~ **DONE in `ccdd14b`, 2026-08-11**, hours after this proposal was written. Retained for its rationale, which still holds and now applies to recommendation 1: per-turn finalization is the **upstream** cure, because it stops manufacturing session-sized batches in the first place. Recommendation 1 is still worth doing and is now the *only* outstanding half — it is the guard that holds if this regresses. Corroboration from the live rollout: the very first per-turn run finalized with status `split`, because one session's accumulated backlog exceeded the 10 MiB cap in a single pass. That is exactly the §1 defect, observed once on the way out.
3. **ADOPT — Enable Braintrust Topics on the `claude-code` project.** Lowest effort-to-insight ratio here: it is a platform feature on data we already send, needing ~100 facet summaries to start (source 5). It converts "these sessions scored low" into named recurring clusters without a human reading traces and without the CCv3 code path growing. Seed the vocabulary from MAST's 14 modes (source 4) rather than inventing one. **Verify the billing implication before enabling** — see §7.
4. **ADOPT — Calibrate the judges, and report κ *plus* a position-bias check.** This supersedes 07-30's item 3 rather than repeating it. Source 8 shows consistency alone is actively misleading: >0.95 test–retest reliability coexisted with >0.10 position bias in production judges. So the minimum is two measurements per judge, not one — Cohen's κ against a small hand-labeled set, and an order-swap probe. Keep 07-30's PPI/Rogan–Gladen correction as the aggregate step; this pass adds the bias axis, which is cheap (re-run the same items with the order flipped) and would otherwise be invisible.
5. **ADOPT (10 minutes) — fix the two stale pointers.** `CURRENT-STATE.md:40` and `components-manifest.json:44`. Fourth proposal flagging the manifest; a component whose defining failure was trusting a green signal should not ship a manifest pointing at a file that does not exist.
6. **WATCH — Trajectory-level failure attribution (FALAT / AgenTracer).** The right long-term answer to `nested_subagent_no_correlation`, and the research is moving fast. Not yet: FALAT's best step-level accuracy is 46.0% on generated and 29.1% on hand-crafted trajectories (source 1), and AgenTracer needs a trained 8B model plus a labeled dataset (source 2). Neither is a drop-in. Revisit when either publishes a usable artifact, **or** once recommendation 3 has produced enough clustered failures to make a labeled CCv3 trajectory set cheap. Prerequisite either way: **ST-02**, since attribution needs joinable sub-agent identity.
7. **WATCH — Failure promotion into a regression set.** Source 6 gives a concrete five-step workflow, and it is the natural sequel to Topics. Held back because it depends on recommendation 3 producing clusters and recommendation 4 making scores trustworthy — and because I found no academic validation for it, only vendor practice. Unchanged in rank from 07-18 and 07-30; the difference is that it now has a documented shape to copy.
8. **SKIP — Re-litigating the native-OTel spike this pass.** 07-30 made the case and it still stands; approving it a fourth time adds nothing. Note one update that *lowers* its urgency: its headline benefit was moving the emit cost off the critical path, and for the Python layer the spool has now done that without OTel. What remains is sub-agent correlation and `session.id` (→ ST-02). Leave 07-30's recommendation 2 standing as written; do not re-scope it here.
9. **SKIP — Judge panels, and server-side online scoring.** Both re-affirmed from 07-30 on unchanged reasoning. Source 8 adds a small point *for* our existing cross-family routing (rankings shift by up to 14 positions across benchmarks, so one family is fragile) but nothing that argues for more judges per dimension.

## 6. Benefits

- **~1 GB of disk and a recurring multi-hundred-MB memory spike stop happening.** Today every session start and end reads 541 MB, parses it as JSON, fails to upload it, and writes it back. Recommendation 1 ends that outright, and the streaming read means no single bad record can ever do it again.
- **Four days of spans stop being at the mercy of a 7-day timer.** Right now the resolution path is "wait until 2026-08-14 and lose them."
- **87% of turn spans become real spans.** Braintrust currently computes an unbounded duration for 7,610 open-ended turn spans — every duration-based reading of that data is wrong until recommendation 2 lands.
- **Low scores turn into named problems.** Topics plus MAST's vocabulary converts "this session scored 0.4" into "this is the inter-agent-misalignment cluster, 23 sessions this month" — which is the difference between a metric and a work item, and it is where the review/fan-out heavy way Dave actually works gets visible.
- **Judge numbers become defensible.** Source 8's 33–41 pp κ deflation means the honest reading is that we currently do not know how good our judges are. Two cheap measurements per judge replace three unvalidated rubrics.
- **No new spend on four of the five ADOPTs.** 1, 2, 4 and 5 are local code and docs on existing infrastructure. 3 is the only one with a possible billing implication, and it is flagged rather than assumed.

## 7. Open questions

1. **Does enabling Topics change the Braintrust bill, and does it send trace content to an embedding model in a way we should think about first?** The article documents a `brain-embedding-*` model over production traces but I did not verify pricing or plan gating. This is the one gate on recommendation 3 and it is Dave's call, not mine.
2. **Salvage or discard the 541 MB record?** It is ~4 days of LLM spans from 2026-08-07. Splitting it offline into <10 MiB batches and replaying is feasible; whether the spans are worth the operation is a judgment call. Either way it should be a deliberate decision, not a timer expiry.
3. **What is the TypeScript emit path costing now?** 07-30's ~640–690 ms per tool call was measured before the spool. The TS path never got a spool and still `await`s inline, so the figure may be unchanged — but it is unverified as of today, and every "should we keep tracing on" argument rests on it. Cheap to re-measure; worth doing before anyone re-opens that trade.
4. **Why was `stop`'s POST attempting 541 MB rather than dead-lettering on the 10 MiB cap at the source?** The batch was over the documented cap by ~54× at creation. Recommendation 1 makes the question moot, but the answer may reveal a second uncapped accumulation site.
5. Unchanged from 07-30, still outstanding: **has the Braintrust API key been rotated?** A failing test printed `Authorization: Bearer sk-…` into its output. Everything above assumes the credential is trusted.
6. Is there value in a small CCv3-labeled trajectory set (à la Who&When) once Topics has clustered enough failures — enough to make recommendation 6 actionable rather than a WATCH? [Speculation] I suspect yes, but nothing in the sources sizes how many labeled trajectories that would take.
