## 2. Frontier scan (oracle pass this session; every arXiv ID fetched and title/date-confirmed)

- **Benchmarks matured, then came under fire.** LongMemEval (500 questions over ~115K-token
  histories; commercial assistants drop ~30% accuracy on sustained recall —
  https://arxiv.org/abs/2410.10813) and MemBench (ACL Findings 2025; retrieval-style memory degrades
  badly past ~100K tokens; "reflective" recall much harder than factual —
  https://arxiv.org/abs/2506.21605) are the citable harnesses. But a Feb–May 2026 critical survey
  argues current agentic-memory benchmarks are under-scaled, metrics misaligned with semantic
  utility, and results backbone-dependent (https://arxiv.org/abs/2602.19320) — i.e., architectural
  sophistication doesn't reliably show up in numbers. A Dec-2025 survey goes further and calls the
  long/short-term (and episodic/semantic/procedural) taxonomy itself insufficient
  (https://arxiv.org/abs/2512.13564). Practical read: local, per-corpus evals (which we have) beat
  imported leaderboard claims.
- **Graph/temporal memory wins are real but concentrated.** Zep's bi-temporal knowledge graph
  reports 94.8% DMR and up to +18.5% on LongMemEval with 90% latency reduction vs full-context
  (https://arxiv.org/abs/2501.13956); the ICLR'26 "When to Use Graphs in RAG" companion benchmark
  explicitly scopes graph advantages to multi-hop/relational queries
  (https://github.com/GraphRAG-Bench/GraphRAG-Benchmark) rather than claiming general superiority.
- **Write-time LLM consolidation is the converged pattern.** Mem0's extract/consolidate/update
  pipeline (https://arxiv.org/abs/2504.19413) is the same shape as our just-shipped
  distill-before-store; Letta's sleep-time compute extends it to idle-time background rewriting —
  "raw context into learned context" (https://www.letta.com/blog/sleep-time-compute, fetched this
  session).
- **Embedding model currency:** BGE-large-en-v1.5 (Sep 2023 lineage) is now mid-tier among open
  models; the Qwen3-Embedding family (June 2025) claims leading results on MTEB multilingual in its
  abstract (https://arxiv.org/abs/2506.05176 — no specific scores stated in the abstract; specific
  leaderboard placements circulating in secondary posts were not primary-verified, so none are
  quoted here). Late chunking (https://jina.ai/news/late-chunking-in-long-context-embedding-models/)
  targets long-document chunking and is largely inapplicable to our short discrete learnings.
- **Vendor direction (Anthropic):** the memory tool remains file CRUD with no
  search/embedding/ranking primitive
  (https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); context management
  reports 84% token savings / 39% performance improvement on a 100-turn benchmark — the vendor
  optimizes context efficiency, not recall rate (https://www.anthropic.com/news/context-management).
  Claude Code's native auto memory (MEMORY.md index + topic files, 200-line/25KB session load —
  https://code.claude.com/docs/en/memory) is structurally the pattern CCv3 already runs: convergent
  validation, not a gap.
- **Production retrieval pattern:** hybrid (BM25+dense) → RRF → cross-encoder rerank on the top-N is
  the now-standard two-stage shape (consistent with sbert guidance cited in the 07-24 refresh —
  https://sbert.net/examples/applications/retrieve_rerank/README.html). CCv3 has stage 1 live and
  stage 2 built-but-dark.

## 4. Recommendations

**R1 — Re-run `eval_recall.py` in `--daemon-mode --warmup` and refresh the eval set. ADOPT (do
first, ~1 session).** The May eval answered the precision question (+107% NDCG@5) but its latency
arm is obsolete: it measured the cold uv path (baseline p50 9.9s) that ST-05 has since replaced.
The one number that decides the reranker's fate — warm-daemon rerank p95 — has never been measured,
and the harness to measure it already exists with a decision gate in its docstring. Extend the
42-pair set (built 05-17) with ~10–15 pairs covering post-May corpus content, including distilled
entries, then run both arms warm. No new code; this is running infrastructure we already own.

**R2 — Surface `--rerank` on the manual `/recall` path now. ADOPT (small).** For explicit `/recall`
the user is already waiting on a CLI round-trip; multi-second rerank latency is acceptable there
today, and the offline evidence (found-rate 57%→83% at k=5) says the answer quality difference is
large. This is a skill-file change (`.claude/skills/recall/SKILL.md` documents the flag; the CLI
already supports it) — zero hook-path risk, and it starts generating live rerank usage data before
any SI-01 decision. Consistent with the triage backlog's "rank 5: reranker wiring
(async/manual-first)".

**R3 — Provenance tags at store time (carry-over of 07-12 R5). ADOPT (small).** Still unshipped and
still cheap: tag writes with their producing layer (L0/L1/L2/manual/distilled — the `distilled` tag
from `f1eb429` is a start) via the existing tags column, and show it in injected context. Directly
serves the trust-tier direction the 06-30/07-12 passes sourced; complements ST-07.

**R4 — Hold the line until the ~07-31 re-baseline; then attribute the residual ~2s. ADOPT
(discipline, not build).** n=6 is not evidence; the baseline JSON's success criteria
(fallback <15%, no hit-rate regression) need the week of traffic. When it runs, add one analysis
the criteria don't list: split daemon-internal latency from client-observed whole-hook time
(the 07-24 snapshot itself warns `total_elapsed_ms` is whole-hook) to attribute the ~2s residual —
spawn/connect tax vs daemon compute vs merge overhead. That attribution decides whether the hot
path can ever approach the 136ms target or whether the SessionStart index-injection architecture
(07-24 watch list) gets promoted.

**R5 — Embedding model swap. WATCH (measure-first).** BGE-large-en-v1.5 is aging, but MTEB deltas
on long multilingual documents may not transfer to short English learnings, and a swap churns the
daemon's RAM footprint and cold-start (~30–45s today, `embedding_daemon.py:9`). Trigger: after R1's
refreshed eval set exists, run a candidate model as a third arm; adopt only on a material
found-rate/NDCG lift. Re-embedding the corpus itself is cheap at this size.

**R6 — Sleep-time consolidation. WATCH (unchanged from 07-12 R7, trigger unchanged).** The Letta
pattern remains the fit (bounded idle pass on the resident daemon, propose-don't-delete
supersessions); flip to ADOPT only if the re-baseline shows stale entries in live top-3 results.
SUPERSEDE routing for distilled memories (ADD/UPDATE/SUPERSEDE — deferred v2 of `f1eb429`) is the
natural first slice when it flips.

**SKIPs re-affirmed (third time, now with sharper sources):** general graph/temporal KG layer —
Zep's wins concentrate on multi-hop/relational queries our "have we hit this error before" workload
mostly isn't (2501.13956, GraphRAG-Bench scoping); episodic/semantic/procedural store split — the
field's own critical surveys can't show taxonomy sophistication translating to measured gains
(2602.19320, 2512.13564); replacing pgvector with vendor-native memory — the memory tool has no
retrieval primitive, and native auto-memory already coexists as our index layer.

## 7. Open questions

1. **Warm-daemon rerank latency** — the only missing number for SI-01. R1 answers it; until then
   any hook-path rerank talk is premature.
2. **Where do the ~2 seconds go?** Whole-hook p50 ~2.1s post-fix vs 136ms design target. Spawn tax,
   daemon queueing, SQL, or measurement scope? R4's split-attribution answers it; the answer decides
   between "tune the daemon" and "move recall off the per-prompt path entirely" (the index-injection
   watch item).
3. **Does the 05-17 eval set still represent the corpus?** It predates the distill pipeline and two
   months of writes; found-rates from a stale set could flatter or damn either arm. [Speculation]
   Distilled atomic entries should retrieve better than verbatim blobs — R1's added pairs can test
   exactly that.
4. **Will post-fix hit quality hold?** Early rows all returned results, but `kept_after_floor`
   distribution vs baseline (the third success criterion) needs the full week's data.
5. **Rerank daemon operational state** — `rerank.py --daemon` availability/warmth on this box hasn't
   been probed recently; a dead rerank daemon would make R2 silently fall back to RRF (fail-open by
   design, but worth a probe when wiring).
