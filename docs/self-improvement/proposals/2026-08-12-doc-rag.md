### Defects found while verifying (all new — not in `BACKLOG.md`)

**D1 — The reindex trigger cannot fire on a single edit.**
`pageindex-watch.ts` creates a pending batch with `timestamp: now` (lines 180-185), then
computes `elapsed = now - pending.timestamp` (line 191) and only reindexes when
`elapsed >= DEBOUNCE_MS` (2000 ms, line 42). On a fresh batch `elapsed` is always `0`, so the
first indexed-file edit never triggers. A flush needs a **second** indexed-file edit arriving
≥2 s later. Edit `ROADMAP.md` once and stop, and it is never reindexed. This is the mechanical
cause of the 74/84 staleness.

**D2 — `--pageindex` fans out one synchronous LLM subprocess per indexed document, uncapped.**
`recall_learnings.py:1352` calls `service.list_trees(project_path=project)` — which applies no
`LIMIT` (`pageindex_service.py:206-231`) — then loops every tree calling `tree_search(...)`
(`recall_learnings.py:1362-1368`). `tree_search` issues a blocking `claude_complete`
(`tree_search.py:140`), which shells out to the Claude CLI. For this project that is **84
sequential CLI spawns for one query**. `tree_search_async` exists at `tree_search.py:171` and is
unused on this path. The `SKILL.md:44-47` and `subsystems/pageindex.md:170-173` both instruct the
user to run exactly this command.

**D3 — Ranking compares uncalibrated self-reported confidences across documents.**
`tree_search.py:165` takes `confidence` straight from the model's own JSON; `recall_learnings.py:1384`
then sorts all documents' results by that field. There is no cross-document normalisation.

**D4 — Retrieval returns stale content with no staleness signal.**
`doc_hash` is computed and stored (`pageindex_service.py:69,140-153`) and is used by
`batch_index.py:85,102` to *skip* unchanged docs on write. It is never consulted at query time.
With 74/84 stale, a retrieval hit is more likely to be outdated than current, and the result
carries no marker saying so.

**D5 — Three copies of an accuracy claim that the cited source does not support.**
"98.7% accuracy vs ~50% for vector similarity" appears at `.claude/skills/pageindex-search/SKILL.md:12`
and `:114-117`, `opc/scripts/pageindex/tree_search.py:4-5`, and
`.claude/docs/architecture/subsystems/pageindex.md:5`. Provenance is analysed in §2.

**D6 — The architecture doc describes dead machinery as live.**
`.claude/docs/architecture/subsystems/pageindex.md:85` lists `pageindex-navigator` as
"**Always-on architectural guidance**" and `:91-99` documents it plus `navigator-safety` as
active hooks. Neither is registered. The same file's SQL schema at `:47-56`
(`tree_json`, `project_name`, `content_hash`, `SERIAL` PK) does not match the real table
(`tree_structure`, `project_id`, `doc_hash`, `uuid` PK) — `SKILL.md:89-99` has it right.

**D7 — Stale model pins.** `claude_llm.py:17-21` maps to `claude-sonnet-4-5-20250929`,
`claude-haiku-4-5-20251001`, `claude-opus-4-20250514`. Two generations behind the session model.

## 2. Frontier scan

Every URL below was fetched directly this session. Where a number is quoted, the fetched page
states it.

**1. The "98.7%" figure is real, vendor-reported, and about something else.**
The PageIndex README states: "PageIndex achieved state-of-the-art 98.7% accuracy on FinanceBench
(financial document QA benchmark)"
([github.com/VectifyAI/PageIndex](https://github.com/VectifyAI/PageIndex)). The linked results
repo shows Mafin 2.5 at 98.7% with 100% coverage, against **Quantly 94%** (100% coverage),
**Fintool 98%** (66.7% coverage), **ChatGPT-4o + Search 31%** and **Perplexity 45%** (partial
coverage) ([github.com/VectifyAI/Mafin2.5-FinanceBench](https://github.com/VectifyAI/Mafin2.5-FinanceBench)).
Three things follow. It is a self-run, self-published vendor benchmark with no independent
reproduction found. It is financial **PDF** QA, not markdown. And **no baseline in that table is a
vector-RAG system scoring ~50%** — the two low scores are web-search products on a different
subset. The "~50% vector" half of our claim has no source in the material we imported it from.

**2. Anthropic Contextual Retrieval — the highest-evidence retrieval gain published, and it is
about chunking.** The post states contextual embeddings alone "reduced the top-20-chunk retrieval
failure rate by 35% (5.7% → 3.7%)"; with contextual BM25, "by 49% (5.7% → 2.9%)"; adding
reranking, "by 67% (5.7% → 1.9%)". Metric is "1 minus recall@20"
([anthropic.com/news/contextual-retrieval](https://www.anthropic.com/news/contextual-retrieval)).
The technique prepends LLM-generated situating context to each chunk before indexing — it exists
to repair context lost by chunking.

**3. Anthropic's own guidance names stale indexing as the reason Claude Code avoids a pre-built
index.** Published 2025-09-29: "Claude Code is an agent that employs this hybrid model: CLAUDE.md
files are naively dropped into context up front, while primitives like glob and grep allow it to
navigate its environment and retrieve files just-in-time, effectively bypassing the issues of
stale indexing and complex syntax trees." The post states the tradeoff plainly — "runtime
exploration is slower than retrieving pre-computed data" — and endorses hybrids: "the most
effective agents might employ a hybrid strategy, retrieving some data up front for speed, and
pursuing further autonomous exploration at its discretion"
([anthropic.com/engineering/effective-context-engineering-for-ai-agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

**4. RAPTOR — the peer-reviewed hierarchical-retrieval result.** Sarthi et al., ICLR 2024:
recursive embedding, clustering and summarising into a tree; abstract states "by coupling RAPTOR
retrieval with the use of GPT-4, we can improve the best performance on the QuALITY benchmark by
20% in absolute accuracy" ([arXiv:2401.18059](https://arxiv.org/abs/2401.18059)). Its value is
*inferring* structure over unstructured text.

**5. Agentic retrieval has moved from pattern to published architecture.** A-RAG (Feb 2026)
"exposes hierarchical retrieval interfaces directly to the model", giving it three tools —
"keyword search, semantic search, and chunk read" — and reports it "consistently outperforms
existing approaches with comparable or lower retrieved tokens"
([arXiv:2602.03442](https://arxiv.org/abs/2602.03442)). This is retrieval-as-tool, not
retrieval-as-pipeline.

**6. Embedding retrieval degrades specifically in the agentic-coding setting.** CORE-Bench (Jun
2026), "over 180K queries and 106K broader-context relevance labels", reports "a sharp drop from
traditional code search to code retrieval in agentic coding settings"
([arXiv:2606.11864](https://arxiv.org/abs/2606.11864)). No percentage is given in the abstract, so
none is quoted here.

**7. Long context does not remove the need for selection.** Chroma's report (Hong, Troynikov,
Huber, 2025-07-14, 18 models) states "model performance degrades as input length increases, often
in surprising and non-uniform ways"
([trychroma.com/research/context-rot](https://www.trychroma.com/research/context-rot)) — the page
gives no single degradation percentage, so none is quoted. NoLiMa is sharper: "At 32K, for
instance, 11 models drop below 50% of their strong short-length baselines", and GPT-4o falls
"from an almost-perfect baseline of 99.3% to 69.7%"
([arXiv:2502.05167](https://arxiv.org/abs/2502.05167)). And length hurts even when retrieval is
perfect: performance "degrades substantially (13.9%--85%) as input length increases but remains
well within the models' claimed lengths" ([arXiv:2510.05381](https://arxiv.org/abs/2510.05381)).

**8. PageIndex now ships a hosted MCP server.** It is an HTTP MCP at `https://api.pageindex.ai/mcp`
with API-key auth, and "your existing API key, documents, and plan work seamlessly across both
REST and MCP access" — meaning documents are uploaded to PageIndex servers
([docs.pageindex.ai/mcp](https://docs.pageindex.ai/mcp)). A `claude.ai PageIndex` connector is
already present in this harness's tool list.

## 3. Gap analysis

**Where we are behind — but not in a way more retrieval technology fixes.**

The field's own answer to our situation is that we should not be running this index. Anthropic
names "stale indexing" as the specific failure agentic search avoids, and our measurement is that
88% of our index is stale. We did not discover a subtle limitation; we reproduced the predicted
one, and the mechanical cause is a 5-line debounce bug (D1), not a retrieval-quality problem.

**Where we duplicate ourselves.** The path that actually runs fast — `fast_search.py:47-70` — is
FTS plus pgvector cosine fused by RRF over `pageindex_nodes.embedding vector(1024)`. That is the
same retrieval architecture as the memory subsystem (`CURRENT-STATE.md:35`: BGE-large-en-v1.5
1024-dim, pgvector, hybrid RRF), pointed at a second, staler corpus. We imported a framework whose
stated selling point is being "vectorless" and then run it as a vector index. The reasoning-based
tree search that is the actual differentiator is on the path nobody can afford to call (D2).

**Where we are actually ahead.** Three things are genuinely good and worth keeping. Markdown tree
generation is deterministic and LLM-free, so refresh costs CPU only — no tokens, no API. FTS
search returns in well under a second (verified live this session). And `batch_index` already
does hash-based skip, so a full corpus refresh only touches what changed.

**Where the claims outrun the evidence.** D5 and D6 are the most serious finding in this review.
A skill file and an architecture doc that a future session will read as fact assert a 98.7%-vs-50%
accuracy advantage that the cited benchmark does not establish for our use case, and describe an
unregistered hook as "always-on". By `BACKLOG.md`'s own severity legend that is S1 — a
decision-driving false claim.

**Where the frontier has nothing for us.** Contextual Retrieval repairs damage caused by chunking;
our nodes are author-written markdown sections that were never chunk-split. RAPTOR infers
hierarchy where none exists; markdown headers already give us one. Neither addresses staleness,
coverage, or zero usage.

## 4. Recommendations

**R1 — Correct the unsourced accuracy claims and the dead-machinery docs. ADOPT.**
Remove or re-source "98.7% accuracy vs ~50% vector" at `SKILL.md:12`, `SKILL.md:114-117`,
`tree_search.py:4-5`, `subsystems/pageindex.md:5`. The honest replacement: a vendor-reported
FinanceBench result on financial PDFs, no independent reproduction, not measured on markdown. In
the same pass fix `subsystems/pageindex.md:85,91-99` (navigator hooks are not registered) and
`:47-56` (the SQL schema is wrong). Highest value per line changed in this whole proposal.

**R2 — Cap the `--pageindex` fan-out. ADOPT.**
Two acceptable forms. Cheapest: route `--pageindex` and the PageIndex leg of `--hybrid` to
`fast_search` FTS, and put `tree_search` behind an explicit single-document flag
(`--tree-search --doc <path>`). Better but larger: keep tree search, add an FTS prefilter to pick
the top 3-5 candidate documents, then use `tree_search_async` (`tree_search.py:171`) over just
those. Either way the uncapped 84-spawn loop at `recall_learnings.py:1357-1368` must not survive,
because `SKILL.md:44-47` actively tells the operator to invoke it.

**R3 — Fix the refresh trigger and add a staleness signal. ADOPT.**
Fix the D1 debounce so a single indexed-file edit reindexes. Then close the loop at read time:
compare stored `doc_hash` against the file on disk during search and either refresh or mark the
result `STALE (indexed <date>)`. A retrieval layer that silently returns 3-month-old content is
worse than none, because the agent trusts it. Refresh is CPU-only, so this is affordable.

**R4 — Shrink the component to a cheap, fresh, agent-callable document locator. ADOPT.**
Stop framing this as a RAG system. Its defensible job is answering "which document and which
heading covers X" in under a second, over a corpus that is actually current. That is
`fast_search --mode fts` plus R3. Expose it the way A-RAG does — as a tool the agent chooses,
alongside grep and read ([arXiv:2602.03442](https://arxiv.org/abs/2602.03442)) — never as a
per-prompt injection. The per-prompt experiment already ran: 16 attempts, 0 hits, up to 15.8 s.

**R5 — Route real long PDFs to the hosted PageIndex MCP, not local code. ADOPT (narrow, gated).**
The one job agentic grep genuinely cannot do is read a 200-page PDF. PageIndex now sells exactly
that as a hosted MCP ([docs.pageindex.ai/mcp](https://docs.pageindex.ai/mcp)), and the connector
is already in this harness. Prefer it over maintaining 4,838 LOC locally for a case that has not
arisen. **Gate:** documents are uploaded to PageIndex servers. That needs the same data-egress
posture as `.claude/rules/grok-worker-safety.md` — first-use confirmation naming the destination,
no repo secrets, no regulated content. Do not enable it silently.

**R6 — Anthropic Contextual Retrieval. WATCH, and route it to memory, not doc-RAG.**
The 49%/67% result is the strongest published retrieval gain we have a verified number for
([anthropic.com/news/contextual-retrieval](https://www.anthropic.com/news/contextual-retrieval)),
but it repairs chunking damage we do not have in markdown. Its reranking half is already ratified
as **SI-01** on the memory path. Revisit only if a future corpus needs chunk-splitting.

**R7 — RAPTOR-style recursive summarisation. SKIP.**
RAPTOR's gain comes from inferring hierarchy over unstructured text
([arXiv:2401.18059](https://arxiv.org/abs/2401.18059)). Our documents ship an author-written
hierarchy in their headers, which we already parse for free. Adding recursive LLM summarisation
would put per-node token cost onto a corpus whose demonstrated problem is that nobody refreshes
or queries it.

**R8 — ColBERT / ColPali late interaction. SKIP.**
No verified head-to-head evidence on markdown was found. ColPali's advantage is scanned and
visual PDFs, which is not our corpus. Real infrastructure cost, no measured benefit for us.

**R9 — Full retirement of `opc/scripts/pageindex/`. WATCH — decide after R1-R4.**
Retirement is defensible today on usage alone (zero retrievals in 1,497 logged recalls). It is
not recommended *yet*, because R1-R3 are small and would leave a working, honest, cheap locator,
and because deletion of a 4.8K-LOC subsystem with two Postgres tables belongs in **SG-03** with a
per-item static-reference check. Re-evaluate after one month of R4: if the FTS locator is still
called zero times, retire it under SG-03 and keep only R5.

Suggested order: **R1 → R2 → R3 → R4**, then R5 on demand, then re-measure before R9. R1 and R2
are independent of every open gate (ST-02, ST-05, FH-02) and can ship immediately. R3 touches a
registered hook, so it should follow the standard hook-edit verification.

**What could go wrong.** Fixing D1 (R3) is the one change with real blast radius: it converts a
trigger that almost never fires into one that fires on most documentation edits. If `--tier 1`
scoping is wrong, that becomes a background reindex storm on a machine with a measured spawn-latency
pathology. Verify the tier filter and measure reindex wall-time on the 74 stale docs **before**
shipping the trigger fix. Second risk: R2 changes what `--pageindex` means, and `SKILL.md` plus
`subsystems/pageindex.md` both document the old behaviour — update all three in one change, or the
doc-rot this proposal is fixing simply moves.

## 6. Benefits

- **A retrieval surface that cannot silently lie.** Today a `--pageindex` hit is more likely stale
  than current (74 of 84) and says nothing about it. R3 makes every result either fresh or
  labelled. This is the concrete win: the agent stops confidently quoting three-month-old docs.
- **A documented command stops being a latency trap.** `SKILL.md:44` currently tells Dave to run
  a command that spawns 84 sequential Claude CLI processes. R2 removes that. Sub-second FTS
  replaces an unbounded wait.
- **Three false claims removed from load-bearing files.** A future session reading `SKILL.md` or
  the architecture doc today learns that PageIndex is 98.7% accurate versus 50% for vectors, and
  that an always-on navigator hook is running. Neither is true. R1 costs about an hour and
  prevents a decision made on fiction.
- **Honest scope, less to maintain.** R4 plus R9 put a 4,838-LOC subsystem on a path to either a
  small useful tool or a clean deletion, instead of indefinite "honing" status.
- **A real capability gained, cheaply.** R5 gives long-PDF reading — the one thing agentic grep
  cannot do — with no local code to maintain, using a connector already present.
- **No token cost to any of it.** Markdown tree generation is LLM-free and embeddings are local,
  so the freshness fix costs CPU, not spend.

## 7. Open questions

1. **Is there any live consumer of the vendored PageIndex beyond `recall_learnings.py`?** This
   review checked `.claude/` and `opc/scripts/core/`. Before R9, run a per-item `git grep` across
   the whole tree per the SG-03 deletion protocol.
2. **What bounds a reindex sweep once D1 is fixed?** `batch_index --tier 1` is invoked by the hook
   (`pageindex-watch.ts:97-102`), but the tier definitions were not audited here. Needed before R3
   ships.
3. **Should the 66 backslash `doc_path` rows be normalised?** They are Windows-specific and would
   fragment the unique key `(project_id, doc_path)` if the same repo were ever indexed from a
   POSIX shell. No duplicate pair exists today, so this is latent, not active.
4. **Does the 5.9% coverage figure reflect intent or neglect?** 84 of 1,430 markdown files may be
   a deliberate Tier-1 selection. If deliberate, the selection rule should be written down; if
   not, coverage is a second open defect alongside freshness.
5. **Would a corpus-freshness SLO belong under SG-01?** SG-01 currently scopes the memory recall
   floor. Doc-corpus staleness is the same class of problem with the same fix shape — one
   measurement, one threshold, one alert. [Speculation] Folding it in is probably cheaper than a
   separate arc.
6. **Do any of Dave's real documents need PDF reading at all?** R5 is proposed on capability
   grounds, not observed demand. If no PDF workload exists, R5 should also be SKIP and R9 becomes
   unconditional.
