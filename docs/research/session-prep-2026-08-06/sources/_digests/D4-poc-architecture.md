# D4 — agent-poc ("Otto" lineage) architecture digest

Source: cloned repo `fourth/agent-poc` (shallow clone, single visible commit `1c974df`, 2026-08-04, author Ventsislav Nikolov, co-authored "Claude Opus 5 (1M context)"). All citations are repo-relative paths. **Everything in this repo is POC-stage unless marked otherwise.**

## FACTS

- The repo is Fourth's "PerformanceOS" agent-platform POC: a .NET 8 solution (`FourthAgents.sln`) implementing a three-layer agent architecture (Domain / Investigation / Cohort agents) that emits Next Best Actions (NBAs) for restaurant operations at claimed 75,000+ location scale, targeting Azure (agent-poc/CLAUDE.md §Architecture).
- The NBA pipeline is the only coordination point: ingest → enrich → govern → conflict detection → playbook filter → dedup → deliver → track → learn; there is deliberately no central coordinator (agent-poc/CLAUDE.md §"Three Agent Layers" and §"Key Design Rules").
- 70-80% of domain-agent logic is deterministic pure C#; only 20-30% is LLM reasoning; deterministic ops never use the LLM (agent-poc/CLAUDE.md §"Key Design Rules").
- Tools are domain-owned MCP endpoints; agents call them via `IToolClient` against a Mock MCP Gateway — a standalone Minimal API on port 5000 serving all tool definitions with scenario-driven mock data ("Agents developed against it work against production without code changes" is the stated intent) (agent-poc/CLAUDE.md §"Mock MCP Gateway").
- Parallel to the .NET stack, a TypeScript stack ships the Skill Marketplace, Skill Registry, and authoring harness (agent-poc/CLAUDE.md §"Skill Marketplace + Substrate Separation").
- The local runtime is 14 Docker services: public site (3000), customer demo app (3001), curation harness (3002), Skills Studio (3003→3005), platform staff app (3004), Fastify Skill Registry (4000), .NET mock gateway (5000), .NET agent runtime-host (5050), 7 Node mock domain MCP servers (5001-5007), and a Cosmos DB emulator (agent-poc/compose.yml header comment + services).
- `registry/` is a Fastify API backed by Cosmos DB + blob volumes with a hard dual-substrate split: two Cosmos containers, two blob roots, two HMAC signing keys (boot guard refuses equal keys), two actor-tier allowlists; the public DAL has no path to the internal store (agent-poc/CLAUDE.md §"Substrate boundary"; compose.yml registry service env).
- A composition-DAG validator rejects PLATFORM_PUBLIC → PLATFORM_INTERNAL invocations with `CROSS_SUBSTRATE_LEAK`; three forever-retention defect-signal topics fire when substrate isolation has a bug (agent-poc/CLAUDE.md §"Substrate boundary").
- `site/` is the public-facing app with two route groups: `(marketing)` (home, /developers, /marketplace with skill detail pages, /platform/tools, /standards, /why, /use-cases) and `(portal)` — a sandbox developer portal at /portal with catalog, dashboard, iq (FourthIQ), keys, playground, and webhooks pages (agent-poc/site/src/app directory tree).
- The portal logs in with an API key POSTed to `/api/sessions` against the gateway; the login screen brands itself "Fourth MCP Portal — Sandbox developer portal" and states "Sandbox keys only. Production tenant features live in the customer app." (agent-poc/site/src/app/(portal)/portal/layout.tsx:68-108).
- Portal auth is a cookie check that only verifies the `fp4_session` cookie exists and is ≥20 chars — POC-grade, not real session validation (agent-poc/site/src/middleware.ts:21-33).
- Authenticated portal users land on /portal/iq by default (agent-poc/site/src/middleware.ts:6-13).
- `site/` also exposes `/api/managed-agents/{agents,environments,memory-stores,sessions}` routes — a managed-agents API surface inside the portal app (agent-poc/site/src/app/api tree).
- `api-docs/` is a separate hand-authored Docusaurus site with getting-started, authentication, mcp-protocol, rate-limits, tools, and webhooks pages; its quick-start issues 90-day sandbox testing keys via `curl http://localhost:5000/keys/testing` — i.e. docs point at the local mock gateway (agent-poc/api-docs/README.md; api-docs/docs/getting-started.md).
- The /developers marketing page pitches "a fully MCP-compliant server with 200+ tools", JSON-RPC 2.0 + SSE transport, "no vendor lock-in, no proprietary protocols", with SDK downloads and rate-limit tables (agent-poc/site/src/app/(marketing)/developers/page.tsx).
- `platform/` is a minimal Next app for Fourth staff — partner-keys management behind an AD **stub** login with an env allowlist (agent-poc/platform/src/app/partner-keys/page.tsx; platform/src/lib/auth/ad-stub.ts; compose.yml platform service).
- `demo/` is the customer-facing demo app with `(admin)` (admin, marketplace) and `(operator)` (agents, briefings, inbox, knowledge-base, ops, org, playbook, reports, workspace) route groups; the localhost marketplace prototype at `demo/src/app/marketplace/` is preserved as the canonical UI contract (agent-poc/demo/src/app tree; docs/specs/skill-marketplace/MARKETPLACE-AND-SUBSTRATE-DESIGN-v1.md §0.2-0.3).
- `curation/` is the internal authoring harness; `SCOPE_LOCK=PLATFORM_INTERNAL` switches one codebase between customer-facing and internal-substrate deployments (agent-poc/compose.yml curation service comments).
- `packages/skills-seed/` is the canonical home of shipping skill content: 15 public marketplace skills, 10 public drafts, 20 internal-harness, 16 (+15 regional variants) internal-foundation skills, seeded idempotently by SHA-256 content hash (agent-poc/packages/skills-seed/README.md).
- A production-shaped architecture reference exists at `docs/specs/skill-marketplace/production/` (registry, marketplace, curation, Azure Cosmos/blob data plane), last-reviewed 2026-05-08, with an ownership table naming Platform/Frontend/Internal Tools/SRE/Security teams (agent-poc/docs/specs/skill-marketplace/production/README.md).
- The sole visible commit documents `REGISTRY_PLATFORM_INTERNAL_MCP_SERVERS_ENABLED`: a third, per-resource flag stacked on the parent (`INTERNAL_REGISTRY_API_ENABLED`) and read flags, defaulting to false because tenant MCP-server rows carry `authKey` material; without it the internal mcp-servers route 404s (never registered), so `IExternalMcpRegistryClient` in the .NET runtime resolves zero tenant servers — "silently empty tenant-registered federation" (git show 1c974df; docs/specs/skill-marketplace/production/07-security-and-secrets.md:146-158).

- A Knowledge Base domain (`kb`) exists: customer-managed document corpus with provenance on every retrieval, tenant isolation at blob/index/query levels, 9 tools, plus admin console and employee chat UIs in the demo app (agent-poc/CLAUDE.md §"Knowledge Base Domain").
- `foundation/` is a separate Next app ("fourth-foundation") implementing the Foundation Discovery Surface — an agentic customer-onboarding experience ("first-to-fortieth day", replacing ERP-style configuration forms), specified in an intent doc owned by "Christian Berthelsen, CPTO & Co-Founder", dated April 2026 (agent-poc/foundation/package.json; docs/specs/foundation build/Foundation-Discovery-Claude-Code-Build-Instruction.md header).

- The marketplace design doc (v1.3, 2026-05-03) names its owner as Christian Berthelsen (CPTO) and draws intent from `~/Downloads/PerformanceOS/*` spec files on the author's machine (docs/specs/skill-marketplace/MARKETPLACE-AND-SUBSTRATE-DESIGN-v1.md header).

## DECISIONS ALREADY MADE

These are settled in the POC's own docs (settled for the POC — not evidence Fourth has ratified them for production):

- **Scope enum split is canonical**: the legacy `PLATFORM` scope is gone, replaced by `PLATFORM_PUBLIC` / `PLATFORM_INTERNAL`; this design overrides two prior intent specs (docs/specs/skill-marketplace/MARKETPLACE-AND-SUBSTRATE-DESIGN-v1.md §0.3; agent-poc/CLAUDE.md §"Key invariants").
- **Substrate separation is "never softened"** — enforced at schema, storage, governance, signing-key, and flag layers, with defect signals on breach (agent-poc/CLAUDE.md §"Substrate boundary").
- **Authority precedence**: live codebase > localhost prototype > intent spec > prior PRDs; divergences recorded in DIVERGENCES.md, never silently absorbed (docs/specs/skill-marketplace/MARKETPLACE-AND-SUBSTRATE-DESIGN-v1.md §0.3).
- **`demo/src/app/marketplace/` is the canonical UI shape**; the production site surface extends it, neither is redesigned (docs/specs/skill-marketplace/MARKETPLACE-AND-SUBSTRATE-DESIGN-v1.md §0.3).
- **`packages/skills-seed/` is the canonical home for skill content**; boot-time migrations and the seed CLI consume it; legacy seed-import is a no-op (docs/specs/skill-marketplace/production/README.md §"Where do I look").
- **Sandbox/production split of the developer surface**: the portal is sandbox-only ("Sandbox keys only. Production tenant features live in the customer app") (site/src/app/(portal)/portal/layout.tsx:108).
- **MCP + open standards as the external interface**: JSON-RPC 2.0, SSE, any MCP client, explicitly "no vendor lock-in" (site/src/app/(marketing)/developers/page.tsx).
- **Internal-substrate surfaces default OFF and are per-resource gated**; production enablement goes through Trust Center sign-off (docs/specs/skill-marketplace/production/07-security-and-secrets.md:144-152; compose.yml registry CUR-C-3/C-4 comment).
- **Skill promotion flow**: author in curation harness → internal API → promotion review → public registry → webhook fanout to consumer apps (docs/specs/skill-marketplace/production/README.md §"Where do I look").
- **No central agent coordinator; deterministic-first agents; Knowledge ≠ Episodes** (agent-poc/CLAUDE.md §"Key Design Rules").

## PORTAL IMPLICATIONS

- **Christian has already built a developer-portal experience layer inside this POC.** `site/` contains a marketing /developers page, a marketplace browser, and a full sandbox portal (catalog, keys, playground, webhooks, FourthIQ), plus a separate Docusaurus api-docs site and a staff partner-keys app (site/src/app tree; api-docs/; platform/). [inference] Dave's Pillar 3 mandate overlaps this surface directly; the Thursday scope conversation should establish whether Dave inherits/owns this experience layer over Christian's registry+gateway substrate, or builds a separate portal — building blind to this repo risks duplication.
- **The decay risk A0 names is already observable here**: hand-authored api-docs (211 tools, localhost URLs) vs the gateway's live catalog (282 definitions) have diverged inside one repo maintained by heavy AI assistance. [inference] The portal must generate its reference surfaces from the machine-readable sources (the gateway's `/tools` endpoint, the registry's public API) rather than hand-authoring them — the POC hands Dave both the failure example and the data sources to fix it.
- **A governed content pipeline already exists to ride**: skills-seed → hash-idempotent boot migration → registry → webhook fanout to consumer apps, with versioning, signing, yank, and audit (packages/skills-seed/README.md; production/README.md). [inference] The portal's "maintained product, not documentation wallpaper" requirement maps naturally onto being another registry consumer with cache-invalidate fanout, instead of a static site.
- **The substrate boundary defines the portal's hard ceiling**: the portal/marketplace is by design a read-only projection of PLATFORM_PUBLIC only; internal capabilities are structurally unreachable (MARKETPLACE-AND-SUBSTRATE-DESIGN-v1.md §0.1; CLAUDE.md §"Substrate boundary"). [inference] Portal scoping can safely promise "everything public, nothing internal" as an architecture-enforced guarantee, which is a strong trust story for external developers.
- **Everything external-facing is POC-grade**: cookie-length auth, AD stubs, sandbox keys against a mock gateway, dev-only tokens (middleware.ts; ad-stub.ts; compose.yml). [inference] A real portal needs the missing production pieces (identity, key lifecycle, a non-mock gateway) — these are the unwritten chapters (03-08 *(planned)*) and are where Dave's portal roadmap and Christian's platform roadmap must be sequenced together.
- **The one recent commit signals the POC is actively debugged, not abandoned** — 2026-08-04, diagnosing live external MCP federation with a 1M-context Claude (git show 1c974df). [inference] Treat agent-poc as a moving upstream: portal decisions should reference its contracts (registry API, tool catalog schema, actor tiers) rather than snapshot them.
