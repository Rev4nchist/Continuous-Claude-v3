## FACTS

- The MCP server routes requests via lookup: an incoming tool call is looked up to find "the API endpoint responsible for the implementation of this tool" (A3 @0:04).
- The server authenticates to backend APIs with basic auth only; "the customer never sees, actually, how we authenticate on the backend" (A3 @0:04).
- Backend APIs are mostly newly created; adapting existing Fourth APIs "turned out to be very complex and specific on the APIs" (A3 @0:38).
- A separate market API was created because "Christian was very insisting on having the market data as part of his POC also available on the central server"; it returns the same data Christian provided (A3 @0:38–1:10).
- Two token types: customer-wide token (all data for a customer; integration/head-office/service scenarios, matching how legacy integration APIs worked) and user-scoped token (carries customer + user identity; downstream APIs enforce that user's data-access rules — location, employee, inventory) (A3 @1:47–3:34).
- Each tool has an associated scope — worked example: tool "HR get employee" carries scope `HR:Read` (A3 @3:53–4:14).
- Scope filtering is two-level: customer level (which scopes the customer gets, based on products owned) then token level (a subset of the customer's scopes picked per token) (A3 @4:20–5:37).
- Concrete entitlement example: a customer with HotSchedules but not Macromatix gets scheduling + forecasting scopes and never sees inventory tools (A3 @4:20).
- Narrow-agent example: an inventory-only agent token limited to `Inventory.Read` / `Inventory.Audit` / `Inventory.Write` — write called "the most dangerous one" (A3 @5:18).
- Known POC security gap in Toma's words: "almost anyone, if they know the APIs to acquire tokens, anyone can get a token" (A3 @1:47).
- Toma (not "no owner") stated the provisioning follow-up as his own need: "I need to meet Michael and Christian to understand how individual users will be given access to the MCP server" (A3 @1:10).

- Real tokens are obtainable "via the management API"; a token-request UI is planned: "The UI is in progress … we'll start it probably in the next few weeks and we'll do a UI with Vancy [Vance] … for customer admin … or a user within the customer, to be able to request a new token by themselves" (A3 @6:57–7:28).

## PORTAL IMPLICATIONS

- **The Access Management pillar has an active competing builder.** Engineering starts a token-request UI within weeks (A3 @6:57–7:28) and already owns the key-provisioning prototype (A3 @36:18). [inference] Dave should NOT build key-provisioning UI; the portal's play there is the experience wrapper (guidance, demo-token flow, consultant delegation UX) — and the Christian scoping call must land before Engineering's UI hardens the boundary.
- **Docs should be agent-first, not human-doc wallpaper.** Toma expects documentation to "in most cases … be skills, like instructions for LLM. We don't expect consultants to go and call the tools" (A3 @29:47). [inference] The portal's documentation hub should ship consumable artifacts — skills, MCP configs, ready-made scenario prompts (the colleague's prepared Claude queries, A3 @46:20) — with human prose as the secondary layer. This also directly counters the A0 portal-decay risk: static REST docs are exactly the wrong deliverable.
- **Deprioritize a per-tool playground.** Dave himself judged it low-value on the call (A3 @23:20) and Toma agreed IT professionals use MCP Inspector (A3 @23:21). [inference] Catalog + MCP-level test harness beats per-tool try-it buttons.
- **The MCP tool testing agent is a ready-made quick win with a warm sponsor.** Toma wanted it and "never progressed" (A3 @24:52); QAI is writable with keys promised (A3 @43:28). [inference] A tool-reliability/description-quality agent run against QAI is a Pillar-2/Pillar-3 bridge Dave can demo — it also produces the reliability data the catalog needs (which tools actually work, A3 @24:21).
- **Trust story has two disclosed holes the portal cannot paper over:** open token acquisition (A3 @1:47) and unenforced vendor key scoping (A3 @40:25). [inference] Portal copy must not promise per-vendor isolation; enterprise security reviews will probe both (matches A4 §Barrier hypotheses).
- **The onboarding path today is artisanal:** credentials outside secrets stores, passwords that rot on redeploy, a manual Anthropic key + licensing acceptance, and a copy-paste MCP gateway key (A3 @16:09, @28:23, @34:25–35:33). [inference] The portal's core measurable value = productizing time-to-first-call; Dave can baseline it himself with the QAI keys and Claude Code (A3 @43:38).
- **The naming blocker may be smaller than A4 suggests.** Transcript supports one main platform (Fourth360) plus Christian's separately-hosted POC (A3 @30:15, @20:38); [inference] in the Christian conversation, treat "PerformanceOS" as a label to confirm/kill in one question rather than a fourth surface.
- **Management API partition sketches the portal's API surface:** PAT-creation endpoints external, customer/scope admin internal (A3 @41:12–41:28). [inference] Portal access-management features should build on the management API's external slice, not new endpoints.
- **Scale architecture is a live design conversation Dave already owns:** the code-execution-over-tools thread and Search Discovery Router (A3 @26:24–27:16, @45:11) give Dave a credible seat in the Mark/Balaji architecture session — Pillar 1 research feeding Pillar 3 directly, per the A0 relevance test (A0 §Pillar 1 relevance test).
