**Auth model (the model is understood; internals are NOT — A5 §Body says do not conflate)**
- Two personal-access-token types: customer-wide (all data for a customer; integrations/head-office/service-to-service) and user-scoped (carries customer + user identity; downstream APIs enforce that user's data-access rules) (A4 §Track 2; A5 §Current Focus).
- Scopes filter at two levels: customer level (scopes/modules per Fourth products owned — customers only see tools for products they have) and token level (subset of customer scopes per token, enabling narrowly scoped agents, e.g. Inventory-only) (A4 §Track 2).
- Worked example: tool `HR:GetEmployee` ↔ `Scope: HR:Read` (A4 §Track 2).
- Tool-level permission resolution is split: scope association + two-level filtering at the MCP layer; downstream APIs evaluate the user's data-access permissions (A4 §Track 2).
- Known pre-production security gap: anyone who knows the token-acquisition APIs can obtain a token; named next step is a Michael + Christian session on user provisioning — a known gap with a next step, not an incident (A4 §Track 2; A5 §Latest Update).
- Current setup requires customers to manually enter their own Anthropic API key, partly for GDPR/EMEA compliance; provisioning should ideally be automated (A4 §Track 5).
