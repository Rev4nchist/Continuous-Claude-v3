01 / Executive summary

A shared operating surface, not another agent framework.

The design extends the current repository into a durable, authenticated run service with a useful operator interface. Its primary promise is controlled execution: a user can launch valuable automation without terminal access and still explain what ran, why, under whose authority, at what cost, and with what result.

Product outcome

Decision

A governed workspace to discover repeated work, codify it as versioned capabilities, execute it safely, inspect live progress and evidence, and improve it through evaluation plus approval.

Missing layer

Evidence

The repository already has the kernel. What it lacks is shared identity and policy, durable run/task state, leases, idempotent side effects, approvals, artifact lineage, a registry, and an operator client.

v1 boundary

Decision

Deliver three reference workflows through one API and dashboard. No arbitrary code execution, visual workflow builder, auto-merge, multi-region active-active, or autonomous definition promotion.

Definition of success: at least 80% of reference runs finish without terminal intervention; duplicate launches create one run and one side-effect set; worker restart resumes at the last checkpoint; all external writes are attributable; projection failures remain visible and retryable; no skill promotes itself.

Who it serves

  • Operator: launch, supervise, approve, recover.
  • Builder: define in Git, test fixtures, evaluate, ship.
  • Contributor: use curated actions through typed forms.
  • Auditor/Admin: reconstruct authority, versions, and effects.

Architectural invariants

  • UI, voice, CLI, and Notion are clients of the same authenticated API.
  • A browser request never shells directly into claude -p.
  • Each entity has exactly one authoritative writer.
  • Every run pins exact definition, policy, and model configuration versions.
  • Self-improvement proposes candidates; independent gates promote them.

04 / Source of truth

One entity, one authoritative writer.

The most important boundary in the design is not a framework choice. It is authority. Notion holds human intent; Git holds executable truth; PostgreSQL holds transactional runtime truth. Everything else is a projection or a specialized byte/telemetry store.

Notion

Human authority

Portfolio, project and task intent, durable human decisions, curated knowledge, human-readable results and artifact links. It can submit approval commands and display approval projections.

Does not own: operational approval state, leases, event streams, prompts, secrets, high-volume logs, or queue semantics.

Git

Executable authority

Versioned agents, skills, workflows, schemas, evaluations, policy configuration, releases, deployment definitions, and immutable content hashes.

Does not own: mutable run state, human task status, or live approvals.

PostgreSQL + pgvector

Runtime authority

Runs, attempts, tasks, immutable events, leases, runner session/checkpoint state, operational approvals, idempotency, grants, receipts, outbox, evaluation records, artifact metadata, and semantic memory.

Does not own: canonical project intent or executable source definitions.

05 / Target architecture

Clients command. The control plane decides. Sandboxed workers act.

A narrow API separates operator intent from execution authority. The orchestrator resolves pinned definitions and policy, workers claim renewable leases, and the tool broker exposes only approved capabilities. PostgreSQL anchors state while asynchronous projections feed human and telemetry surfaces.

Experience + control

React/TypeScript catalog, launch forms, timeline, approval inbox and artifacts. Node/TypeScript API owns authentication, registry lookup, run creation, policy and SSE.

Execution + data

Workers claim tasks, create a sandbox/worktree, invoke the resolved Claude adapter and tools, checkpoint, and emit normalized events. PostgreSQL 16 + pgvector uses one migration chain.

Knowledge + observability

Notion holds human work and curated outputs. A durable telemetry outbox exports traces, costs, policy outcomes and evaluations to Braintrust and an OTel-compatible sink.

Reliability invariant: a database transaction writes the state transition, immutable event, and outbox message together. Durable resume requires both a committed workflow checkpoint and a runner-session reference. Every external side effect has a stable operation_id; retries first inspect the adapter receipt. Projection failure cannot roll back a completed run.
06 / Runtime contracts

Durability is a product behavior, not an implementation detail.

Typed records and explicit state machines make restart, retry, approval, cancellation, audit, and version promotion predictable. Terminal attempt states are immutable. Retrying appends a linked attempt under the same run aggregate and never erases history.

Manifest and runner boundary

Every executable definition declares owner, entrypoint, typed input/output schemas, agents, tools, side effects, approval rules, timeout, retry, and evaluation. The runner implements start, resume, cancel, and an async event stream. It receives resolved capabilities only and cannot discover unrestricted host credentials.

Workspace isolation contract

Every runtime, identity, approval, grant, event, memory, artifact, evaluation, receipt, and outbox record carries workspace_id. Repository queries require an explicit workspace predicate, reinforced by PostgreSQL row-level security and cross-workspace negative tests.

Side-effect recovery classes

Each adapter action declares one class: idempotent (stable key + receipt), reconcilable (read-after-write confirms outcome), compensatable (explicit audited undo), or non-repeatable (no automatic retry; quarantine for human resolution).

Policy rule: evaluate principal, role, pinned workflow, tool action, resource, environment, data class, risk, and prior approvals outside the model. Return allow, deny, or require_approval with a reason. The most restrictive applicable decision wins.

Three workflows prove the whole operating model.

The first release should not prove breadth. It should prove the same durable, policy-aware lifecycle across research, code change, and scheduled publishing, including failure and recovery at every side-effect boundary.

Intended side effect, target resource, data scope, risk, diff or content preview, grant used, policy reason, expiry, and whether the operation is reversible.

Self-improvement lifecycle

09 / Security & trust

The model never decides its own authority.

Capability resolution, secrets, policy, approval validity, tenancy, and side-effect idempotency sit outside prompts. Shared environments capture sanitized model content only by explicit policy. Self-improvement cannot bypass review or rollback.

Prompt injection

Label untrusted content, separate data from instruction, enforce tool policy outside the model, require approval for sensitive writes.

Excess authority

Deny by default; scope capability grants to action, resource, workspace, environment and expiry; resolve short-lived credentials in adapters.

Sandbox escape

Non-root execution, read-only base, explicit mounts, per-run worktree, egress allowlist, and CPU/memory/time limits.

Duplicate effect

Stable operation id, request hash, adapter receipt, transactional event/outbox, and quarantine when external outcome is ambiguous.

Cross-workspace leak

Mandatory workspace predicate, row-policy tests, namespaced vector retrieval, cache keys and private artifact paths.

Secret disclosure

References rather than values, sensitive-field schema annotations, redaction before export, canary scanning, and retention controls.

Malicious definition

Git review, approved/signed release, pinned hashes, independent evaluation, immutable run history and rollback pointer.

Feedback poisoning

Provenance, confidence, quarantine, minimum evidence, fixture evaluation, and human promotion.

Supply chain / webhook

Lockfiles, SBOM, pinned images/actions, scans; verify Notion signature, replay window and event-id dedup.

11 / Acceptance

No checkbox closes from inspection alone.

Evidence rule Each acceptance claim needs a fresh command, API response, test report, trace, screenshot, or recovery demonstration linked from the release record. P0 is release-blocking; P1 proves useful operation.

P0 release blockers

  • Authentication, roles, revocation and workspace isolation fail closed.
  • Idempotent run creation and exclusive worker leases.
  • Checkpoint recovery without repeating completed tool operations.
  • Deterministic cancel, timeout, retry and terminal states.
  • Every external write has grant, policy, operation id, hash and receipt.
  • Expired/denied approvals cannot act; injection cannot alter grants.
  • Canary secrets absent from every surface.
  • Audit hash chain and administrative attribution pass.
  • Restore meets RPO/RTO; migration failure is recoverable.
  • Ambiguous external operations are quarantined.

P1 functional proof

  • All three reference workflows finish end to end.
  • Verified Notion webhook and reconciliation paths.
  • Human-owned fields never overwritten.
  • Notion throttle retry and drift visible to operators.
  • Contributor launches approved actions without terminal.
  • Accessible live timeline and approval preview.
  • Empty, stale, offline, denied and error states tested.
  • One correlated trace spans run through projection.
  • Queue, lease, cost and projection metrics present.
  • P0/P1 synthetic alerts reach the operator route.

Performance & soak

SLOs at 2× expected concurrency; 24-hour soak without orphaned leases, memory growth, duplicate effects, or drift; backpressure under worker/Notion outage; paginated event history.

Definition safety

Every run pins hashes/config; a candidate needs test/evaluation evidence and approval; rollback changes only the default; active runs continue pinned.

Sign-off packet

Release SHA/images, migration + restore evidence, test and accessibility reports, threat closure, load/soak/chaos, workflow traces + Notion pages, rollback rehearsal, limitations and owners.

12 / Decision register

What is settled, what is provisional, what must be resolved.

These labels prevent research findings, selected architecture, operating assumptions, and unresolved ADRs from blending together.

Settled decisions

Decision
  • Brownfield extension, not rewrite.
  • Claude Agent SDK preferred production boundary; claude -p local adapter only.
  • Git / Notion / PostgreSQL authority split.
  • Typed durable state and idempotent side effects.
  • One authenticated API for every client.
  • Human-gated definition promotion.
  • Railway API/workers/database; Vercel or Railway web, portable topology.

Phase 0 assumptions

Assumption
  • Dave plus a small trusted team are initial users.
  • Existing Ralph, Maestro and reporting jobs can supply fixtures.
  • Railway, PostgreSQL/pgvector, Notion and Braintrust remain approved.
  • Shared automation gets explicit service billing/auth.
  • Current source-tree and schema drift can be resolved incrementally.

Open Phase 0 gates

Open question
  • Exact production identity provider and role mapping.
  • Queue and durable runner session/checkpoint store.
  • Sandbox substrate and enforceable filesystem/network/resource boundaries.
  • Artifact object store and retention tiers.
  • Railway web vs Vercel static/edge split.
  • Runner service billing, credential isolation and concurrency contract.
  • Whether fixtures justify Mastra, Conductor, Agno or LangGraph.
  • Final data-classification, approval, and adapter recovery-class matrices.
  • Validate the Notion 24-hour RPO / 8-hour RTO through a staging rehearsal.
Decision method: choose the simplest option that passes identical durability, isolation, authority, trace, development and deployment fixtures. Record any deviation from this package as an ADR before implementation.
