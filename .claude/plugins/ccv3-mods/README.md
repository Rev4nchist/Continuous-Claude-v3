# ccv3-mods

CCv3 function-hook mods for Claude Code 2.1.292+. One plugin, one module per mod. Designs: the "CCv3 Mods" canvas (2026-10-09).
Plan: `.claudedocs/2026-10-07-mods-plan.md` in the primary checkout.

## Mods

| Module | What it does |
|---|---|
| `brief_set` (tool of `hooks/agentic-os/`, `brief.ts`) | The model sets the session brief: title, goal, stop-at, plan, open asks, decisions, proof. Registered in interactive and headless runs, main session only (a subagent call is refused). Writes the `brief` and `chip` keys of the state file; no database row. Plan and ask replace the whole list (`ask: []` clears). A proof joins on task id, subject and kind; no match saves nothing and lists the valid ids. Every string passes `hooks/shared/redact.ts` (a port of `memory_redact.py`) before storage. A prompt from Dave marks open asks `answered?`; an ask goes stale 24 hours after the last activity. A turn-end parser fills goal, stop-at and asks from the model's own restate line and `## Next steps` block when `brief_set` was not called (marked `parsed`, never overrides). The restate parser reads `Restate:`, `Restating the ask:`, `Restated ask:` and `Restate the ask -` lines (label, then the goal up to its stop clause, then the stop-at from `stop at/before/after/there`, also from an `I stop at X` sentence of its own); `Goal:`/`Objective:` and `Stop at:`/`Stop point:` lines still work. In `## Next steps`, an item that says Dave has nothing to do is not an ask. The set is closed and the whole item must match. It is `None` (not `None of`), `None for now`, `Nothing to do` or `Nothing for you to do`, or `No action needed`, with at most one `waiting on X` clause after it; or it is only `Waiting on X` or `I'm waiting on X`, where X is not `you`, `your` or `Dave`. X is short and has no `?`, comma, `then` or `and`. A block of only such items is an empty list and clears the old asks. A bare line under the block is an ask only when it holds a `?`. Every other item is an ask, such as `Waiting on CI, then approve PR 12` or `None for now. Paste the log`: an action line (`Paste ...`, `Run ...`) is a `question`, and only a line with decide, choose, pick or select is a `decision`. The goal and stop-at also come from each main-loop model request, not only the final text: the one `turn.step` hook in `hooks/hud/index.ts` calls `parseStep` (`brief.ts`) and writes the `brief` atom (a subagent request is never read; asks come from the final text only). A labelled restate may replace an older parsed value; an unlabelled `I will ... stop at ...` sentence fills only an empty slot, and a `brief_set` value is never replaced. Tests: `brief.test.ts` (P13-P24, E11-E15b). Chip: working (a tool, the main turn, or a running agent: the same list as the AGENTS rows and NOW), waiting-on-dave (an open ask beats a running run for the chip), blocked (refused tool or blocked step; red gate and peer lane deferred), done (every step proven), idle. A subagent `turn.start` (event has `agentId`) is passed on and never touches the main turn, its clock or the refusal. The pane, NOW and the chip read one agent list: `agent.list` (the `agents` atom) is authoritative for an id it holds, and a running `agentRuns` run is added only when the list lacks it. A subagent `turn.start` reopens a settled run under the same id, and its `turn.complete` removes the id from the atom. The band and the `/os` pane tabs read it (see the core band row and the `/os` row). |
| Steward (`hooks/agentic-os/steward.ts`, wired in `index.tsx`) | Watches the work and shows whether the session brief fell behind. It injects nothing into the session: no `prompt.compose` section, no context on `prompt.submit`, no nudge text to the model, no prompt submitted. The reason is the prompt cache: any text added to the system prompt or the prompt changes the cached prefix, and the cache hit rate comes before a fresher brief. It counts main-loop tool calls and signals since the last `brief_set` (commit with HEAD moved, PR opened, Workflow or Agent run, `resume_handoff`, lane claim, e2e artifact written; a subagent's calls and `brief_set` itself do not count; the turn-end parser does not restart the counts). The counts live in the `steward` state key (`briefAt` and `activity`), reset at session start, `/clear` and resume. Drift: `unset` (work, no goal), `stale` (15 tool calls, or any commit, PR or run), `finished` (every plan step done, work goes on), else `ok`. It only draws: when drift is not `ok`, the pane Overview shows one dim WATCH item (`  ! <sentence>` with the age at the right, once, in the WATCH block; the words come from `driftSentence` in `plain.ts`): `The session goal is not set yet, and work has started.`, `12 tool calls and 1 commit since the plan last changed.` or `Every plan step is done, but work goes on.`. `CCV3_MOD_STEWARD_OFF=1` (read live) stops the counting and hides the row. Observer only: it never denies or rewrites a call; the drawn row passes `redact`. Tests: `tests/steward.test.ts`, `tests/os-tabs-model.test.ts`. |
| `hooks/agentic-os/` | Captures this session's tasks (`TaskCreate`, `TaskUpdate`, `TodoWrite`), plan (`ExitPlanMode`), current step and context %. Draws one band above the prompt. Writes `~/.claude/state/agentic-os/<session-id>.json` after each task, plan or turn change, and one final snapshot with `endedAt` at session end (every reason; written first, before the /clear and resume resets, under the ending id; only when the end bound leaves 300 ms or more; no later write in that process lands for that id, a module set `endedIds` keeps this after the engine resets the atoms; a resume back to an id that ended earlier in the same process, or in a new process, writes the id again without `endedAt`; a headless run with no task, plan or brief writes none). Reads the lane board with `node ~/continuous-claude/scripts/coordination/lane.mjs board --json --as <session-id>` (it was `mine --json`) at session start, after a Bash or PowerShell call that names `lane.mjs`, at `/os` and at a press of the Work tab. One good read writes three atoms: `lanes` (this session's lanes, the `mine` subset: the band and the compact keeper read it), `board` (every lane the board lists: the Work tab and the Overview WATCH block) and `boardAt` (the time of the read). A failed read writes none of them, so the pane keeps the last good board and says how old it is. Observer only: it never denies or rewrites a call. |
| Core band (`hooks/agentic-os/band-model.ts`, `gitinfo.ts`) | Two lines above the prompt, always drawn in an interactive session (PRD 5.3), through the `row-core-1` and `row-core-2` keys. Line 1: chip (WORKING in blue, WAITING ON DAVE in amber, BLOCKED, DONE, IDLE; the same `deriveChip` value the snapshot holds), a project dot and repo, branch (read from the `.git` files at the session start and each turn start, and again at an in-session resume or clear, which fire `classic.SessionStart` and no `session.start`), `lane <first lane>`, ctx, cost (the HUD's; `-` when unknown). Line 2: `GOAL` (`not set` in amber when no brief or goal; a dim `working_on` fallback after it only if the state has one, none is wired yet; `[parsed]` marks a goal from the turn-end parser), a block-character plan bar with `done/total` (the task list when it holds a task, else the brief plan steps, never both: PRD 5.1; 10 cells at most; proven, unproven, doing (blue), blocked and to-do in their own tones), `ASK n` (open asks only; amber only on the WAITING ON DAVE chip, red on BLOCKED, dim otherwise; answered ones show dim as `n answered?`; `stale` after 24 hours quiet), `UNPROVEN n` (done steps with no proof). Width: no line is wider than the band; the goal is cut first with an ellipsis, line 1 drops the lane, then the branch, the chip is never cut; under 40 columns the full form is not drawn (`bandLines` still returns one chip-and-goal line, but the render does not use it). **Row budget** (`index.tsx`): the two core lines draw when `maxRows` holds them and the HUD row (3 rows, or 2 with the HUD off). With less room, and at every budget under 40 columns, ONE compact line (`compactLine`, key `row-core-1`) takes their place: chip, repo, `ctx N%`, `5h N%`, `7d N%`, cost, `N helpers running`. It has no lane and no GOAL: GOAL is dropped by design under 40 columns. Repo, cost and helpers show from 40 columns up; a helper count of 0 draws nothing. **Band rule (Dave, 2026-10-29)**: the band always shows ctx, 5h and 7d when known, plus cost. Limits not read yet draw `5h -` and `7d -`; a list without a window draws nothing for it. Cut order when the line is too wide: helpers, cost, repo (clipped to the room left, 4 characters at least, else dropped), 7d, 5h. The chip is never cut. ctx goes last of all: at 20 to 24 columns a wide chip such as WAITING ON DAVE (17 cells) leaves no room for it, and ctx is dropped there. This is a known limit, kept on purpose (Dave, 2026-10-29): the chip is never cut, and no real band is that narrow. The line never passes the width (20 at least). Below the core lines come the HUD row (`row-hud`), then the widget line (`row-band`, the earlier band: plan title, task progress, step, PRs, agents), each if rows are left. The core lines never move when there is room. **Debug log**: `CCV3_MOD_BAND_DEBUG=1` (exactly `1`; off by default) makes each band render append one JSON line to `~/.claude/state/agentic-os/band-debug.log` and keeps the newest 200 lines. The line holds numbers and booleans only (`maxRows`, `bodyColumns`, `hudNow`, `quiet`, `lines`): no goal, path or name. A failed write never touches the render, and nothing goes to the session. The HUD row now comes back after a resume: see the HUD row. Repo, branch and worktree come from `.git/HEAD` (and the `.git` file, `commondir` for a linked worktree) of the session folder: file reads only, at the session start and each turn start, capped at 4 KB, never throwing; the snapshot carries them as `repo`, `branch`, `worktree` (null when unknown). Observer only; every string passes `redact`. Not built: a terminal-side Fleet view of other sessions (the web Fleet Browser reads the state files; the Fleet view is the next slice), project colours, `tones.ts` generated from `tokens.json` (five tones were added to the existing map: `chipDoing`, `doing`, `chipWarn`, `chipOk`, `chipDim`). Tests: `band-model.test.ts` (L1-L11, CL1-CL14), `gitinfo.test.ts` (Q1-Q14), `agentic-os.test.ts` (C1-C6; E11-E15, E11c and E13b for the final snapshot, ids that `brief.test.ts` also uses for other cases; the 300 ms floor has no test, the kit cannot cut the end bound), `band-reliability.test.ts` (B1-B4 row budget, HS1-HS8 HUD seed, G1-G7 debug log, M1-M8 the band rule). |
| `/os` (same module, `os-tabs-model.ts`, `session-tab.ts`, `work-tab.ts`) | Opens the Agentic OS pane (PRD 5.3, redesigned 2026-10-29) with seven tabs: **Overview**, **Session**, **Steps**, **Work**, **Checks**, **Choices**, **Swarm** (the earlier Plan, Proof and Decisions; only the labels changed, the ids and Button keys `tab-plan`, `tab-proof`, `tab-decisions` stay; the words live in `tab-words.ts`). Each is a Button: a press, or its digit `1` to `7` while the pane has the focus (ctrl+x tab); Swarm is key 7, after Choices. **Comms** and **Resources** are one dim footer row, `later: Comms · Resources`, plain text that cannot be pressed or selected; the footer draws only when the body keeps 3 rows or more, and goes first in a short pane. The pane opens on Overview. The selected tab is the `osTab` atom (types contract), reset to Overview at `/clear` and resume. The terminal draws a live tab as `1: Overview`, and the strip wraps with those 3 extra cells counted. The test kit presses a Button by key only and has no keystroke, so a digit press is not tested here; T6 checks that each Button carries the right `hotkey` prop, and the engine turns the digit into the press. **Overview** is the session briefing (`digest.ts`), in plain words from `plain.ts`: the chip word with repo and branch, `GOAL`, `NOW` (the task in progress, else `Thinking`, else `N helpers running`; never the tool name), then **NEEDS YOU** (open asks with `recommend:`, a READY PR as a wait for the merge yes, a pending approval, a blocked step, a failed check, a rate limit), **DONE** (the block id stays `highlights`: commits, merged PRs, passed proofs, decisions by Dave, finished helper runs) and **WATCH** (the steward's drift sentence from `driftSentence`, done steps with no proof, a PR with unresolved threads, a helper running over 10 minutes, a lane another live session holds and whether its scope may touch my files, anything deferred, the compact-keeper check), newest and most urgent first, then one dim health row (`ctx`, cost, cache). Each block shows 3 to 5 items (fewer in a short pane), a `+N more` row for the rest, and one dim line when empty (`nothing needs you`, `no highlights yet`, `nothing to watch`). An item is 1 to 3 rows: `  <mark> <text>` (`>` needs, `+` done, `!` watch) with the age (`now`, `Nm`, `Nh`, `Nd`) at the right of row 1; a text cut at 3 rows, or an item whose home tab holds more (an ask with a recommendation, a peer lane that may overlap), ends `…more -> <tab>`. A derived fact starts with `[derived]`. Strings pass `redact`, are made one line and are bounded (`text.ts`). Not fed yet, so those rows stay empty: commits, merged and READY PR alerts (the pr-loop drops them from the live list), PR threads, proof numbers (a stored proof has an artifact, not a pass count), failed checks (the pr-loop's `fails` counts failed status reads, not CI checks) and rate-limit minutes; `TabState.feed` takes them when a source exists. Peer lanes and the keeper line are fed now (the board and the `compactions` atom). **Session**: `STATE` (chip word, `GOAL`, `STOP AT` with `[parsed]` for a parsed value), `NOW`, `HELPERS` (running runs of the agent ledger, `agentRuns`, plus one `A workflow: N helpers done, M running` row per `workflowRunId` that has a running helper), `TIMELINE` (newest first: keeper line, proofs, finished helpers, Dave's decisions, `Saved N files to git`) and `ROOM` (context, cost, 5-hour and weekly allowance, cache). **Work**: `YOUR LANES` (the lanes of the board this session holds, each note dim), `OTHER SESSIONS` (every lane another session owns, live sessions first; `as of <age>` is its own dim row because the board can be old; `held by a stopped session`, `lease lapsed, session alive` and `may touch the same files` are details, the last a guess from `laneOverlap`, never a fact), `CHANGES` (the watched PRs), `FILES` (looked at, changed and saved counts, then up to 5 edited paths; only when a file was touched) and `WHERE` (repo, branch, worktree). **Steps**, **Checks** and **Choices** keep the earlier content of Plan, Proof and Decisions: Steps is the task list when it holds a task, else the `brief_set` plan (PRD 5.1), each step `○` to do, `▶` doing, `■` blocked, `✓` done and proven or `!` UNPROVEN, long lists folding finished steps into `✓ N done`; Checks lists done-but-unproven steps, then each proof with its artifact; Choices lists the decision log newest first, then open asks (`recommend:`, `answered?`, `stale` after 24 hours of quiet). **Swarm** (`swarm-tab.ts`): a `SWARM` header with the running, done and failed helper counts of the whole ledger, then one line per workflow run (counts, then phase and name: `1 running, 4 done · phase 2 of 2: Judge · pane-fleet-assess`) and one line per agent under it (running, then failed, then done; a finished run with no failure shows its run line only), then the helpers with no workflow run id under `HELPERS`. Phase and name come from the workflow journal (`journal-model.ts`: the `started` lines of `journal.jsonl`, and the run file `wf_<id>.json` once the run has ended), read only at `/os` open and on a Swarm press, for 8 runs (running runs first, then the newest finished ones), a file over 1,000,000 bytes is skipped, every string redacted and clipped. With no journal the rows show no phase and no name (`a workflow`). In a short pane the Overview keeps whole blocks by rank and ends with `+N more` (N blocks left out). Every tab has an empty-state line, draws no row wider than the pane (20 to 200 columns; a right-hand group goes first), and shows `+N more` when a list does not fit. Text gauges only; every drawn string is redacted again before it is cut. Observer only. Zero model tokens. Elapsed times redraw every 5 s while a turn runs. Interactive sessions only. Not built: Comms and Resources content. Tests: `digest.test.ts` (D1-D18, N1-N8; N1d: the hint of each home tab equals its label, N8: a cut helper ends with a bare `…`), `os-tabs-model.test.ts` (O1-O28, B1-B15), `os-tabs.test.ts` (T1-T12; T10-T12: the Swarm press, its one `agent.list` read, `/clear` and resume), `session-tab.test.ts` (S1-S13), `work-tab.test.ts` (K1-K14), `swarm-tab.test.ts` (SW1-SW18), `journal-model.test.ts` (J1-J9), `workflow-model.test.ts` (F1-F14; F10-F14: `swarmGroups`), `lanes-model.test.ts` (L1-L9), `plain.test.ts` (W9, W10: `swarmRunSentence`; W11: `purposeOf`), `text.test.ts`, `pane.test.ts` (F16-F20: the Swarm rows from the ledger, the journal feed, one read at open and one per press, bad journals, redaction), `review-fixes.test.ts` (R3: twelve open tasks fold to a `+N more` row; R4: six agents in a 12-row body; R5: NOW keeps the call that still runs), `review-round2.test.ts` (RR1-RR6, the round 2 review findings: RR1 a home tab draws an ask, step or proof as one clipped row; RR2 the Session tab throws on a null keeper record; RR3 two keeper records with one time; RR4 a quiet session under 40 columns with the HUD off draws no ctx; RR5 `/clear` or a resume keeps the old keeper records; RR6 the pane ROOM section reads the raw `hud` atom and shows no cost or limits after a resume). |

| `hooks/pr-loop/` | Replaces the old review `/loop` cron. Tools `pr_watch {pr}` (interactive only) and `pr_status {pr}` for the model, commands `/watch` and `/land` for Dave. Every 5 minutes an interactive session runs `scripts/github/review-status.mjs <N> --json` per watched PR (reviewer: Greptile). At READY, merged or closed Dave gets a toast and the model gets nothing; at a review Greptile did not finish (LIMITED), a reviewed head with open threads, a confidence below 4/5 or a failed check (REVIEWED), or no review 60 minutes after the head appeared (STALLED) the model gets one line. REVIEWED and STALLED alert once per head and keep the watch; the REVIEWED line points the model at "When the review lands" in `pr-review-loop.md`. A PR body proof that is missing or wrong (any reason that starts `PR body proof:`) is state PROOF: one author-action line per head ("add or fix the Evidence block, update GREEN to the head"), never PENDING or STALLED; findings on a reviewed head still come first. A STALLED line lists the reasons. A draft is state DRAFT: one toast per head ("waiting on /pathway"), no model line, and leaving DRAFT restarts the 60 minute clock; its status text drops the bot reasons. A `review:none` STALLED line says to re-run the review-router workflow, never to request a review. With a checkpoint record the REVIEWED, LIMITED and STALLED lines give the rounds used, "Dave decides round N in the checkpoint pane" at the budget, or "Dave allowed round N". When the cause of a missing CodeRabbit review is a rate limit or review limit (`coderabbitRateLimited`, else the "CodeRabbit rate limited:" reason), the LIMITED line says not to post `@coderabbitai review`, to check capacity with `@coderabbitai rate limit` (it costs no review), and gives CodeRabbit's "available in N minutes" figure (`coderabbitRetryMinutes`) when the notice has one. The mod holds `PROOF_REASON_PREFIX` and the rate-limit reason by value: `node --test scripts/github/pr-loop-sync.test.mjs` fails when `review-status.mjs` changes them. A READY alert answered No raises its toast only. `CCV3_MOD_PRLOOP_QUIET=1` (exactly `1`) also stops the model line for REVIEWED, PROOF, STALLED and LIMITED; the toast and the PRS row stay. It never merges. The watch list is in `$.store` under `pr-watch:<session-id>`, so a reload re-arms it. An error all PRs share (rate limit, failed spawn, a status script without `prState`) backs the checks off to 15 minutes. An error of one PR alone (404, a list too long) counts against that PR; the third in a row drops it with a toast. `pr_watch` and `/watch N` probe first and refuse a PR whose status cannot be read. The Agentic OS band widget line shows a PRS row; the pane shows the watched PRs under CHANGES on the Work tab. |
| `/watch` (same module) | `/watch` lists the watched PRs. `/watch N` adds one. `/watch N --once` answers with the status and arms nothing. Headless, `/watch N` is `--once`. |
| `/land N` (same module) | Answers without a model call. Shows the status. When READY and interactive it asks `Land #N?` with `Land` or `No`. Pressing Land is Dave's merge yes: it runs `land-pr.ps1 -Pr N` through the PowerShell (else Bash) tool with `consent`. Dismiss, No, an error or a headless run lands nothing. `/land N --when-ready` watches the PR and asks Land/No when it turns READY. With no shell tool, Land hands the model one instruction instead. An aborted Land call (Escape) re-submits nothing. |
| `hooks/pr-checkpoint/` | The PR checkpoint (PR C stage 1). Tool `pr_checkpoint {pr, body}` and command `/pathway [pr] [accept|coderabbit|both|none|wait] [--body f]` and `/pathway grant <pr> <round>` (Dave's typed Yes for a review round: it writes `checkpoint:grant:<pr>` on the record head, clears a round `declined` it covers, drops the queued round ask it covers and posts nothing; `COMMAND` in `pr-checkpoint/model.ts`), both registered in interactive and headless runs. A headless run gets the text plan only (`pr-checkpoint.mjs` in text mode) and records nothing. An interactive run reads `gh pr view` (the PR must be a draft at the checkout's head). The checkout is the worktree that has the PR's head branch checked out (`git worktree list --porcelain` in the session root, `worktreeFor`) when it holds the engine, else the session root: Dave can press `/pathway` from any CCv3 session. A relative body path resolves in that checkout first, then in the session root. The engine code is always the session root's copy (`engineArgv(sessionRoot)`); only its cwd is the checkout, because `pr-checkpoint.mjs` reads every fact from the git toplevel of its cwd. So a session in main never runs another worktree's engine. The record stores that checkout as `root`, and Lock B reads HEAD there. The run calls `pr-checkpoint.mjs --json` with that cwd, stores the pair in `$.store` `checkpoint:pending:<session>` and opens the side pane `pr-checkpoint` with the keys. The pane lists the options with the recommendation first (hotkey `1`, `autoFocus`), a held option as dim text, and `dismiss` (`0`). A press runs `--confirm <pathway> --by default|dave --body <file>` then `--apply <pr>` inline, stores `checkpoint:pr:<n>`, tells the model with one `session.append` row, and closes the pane. `pr_watch` queues questions in the same pane (`checkpoint:asks:<session>`): a round past the budget, an opening review 30 minutes after ready (never while the CodeRabbit commit status is pending), Greptile on a `both` PR. The mod posts a review request only on Dave's Yes. Off: `CCV3_MODS_OFF=1` or `CCV3_PR_CHECKPOINT_OFF=1`. Lock A denies a Write, Edit, MultiEdit or NotebookEdit of `pathway.json`, always, and it denies by its own return when it throws (`.catch` can lose a deny under an outer hook). Lock B reads Bash and PowerShell text: it denies any text that names `pre-pr/pathway.json`, and it asks the built `checkpoint-shapes-cli.mjs` about `gh pr ready`, a `review:` label add and a self-confirm. It denies them only when `checkpoint.enforce` is `true` (else one warn toast per pattern), lets a single label through when a store record matches the PR number, HEAD and label, and denies on any failure of the CLI. Lock B also denies, in both modes and with no CLI call, a gh write shape whose text names `pathway-confirmed`: `gh pr comment`, `gh issue comment`, `gh pr edit` or `gh pr create` with a body, and `gh api` with `-X POST`, `PATCH` or `PUT`, a `-f` or `-F` `body=` field, a GraphQL `mutation`, or `--input` (`namesMarker`). Only `/pathway` posts that marker, from node. A gh read that names the word (`gh pr view`, `gh api` GET, a pipe to `Select-String`) is allowed. A node or PowerShell script, or a body file, that builds the marker apart from the command text is not seen: accepted. A missing or unreadable `review-router.config.json` is warn mode in the mod; with no readable config the PR B gate enforces a command that names CCv3, a self-confirm, and any command run in a CCv3 checkout, so the two layers together deny it. A readable config keeps its own `enforce` value in both layers. A root without `scripts/github/pr-checkpoint.mjs` is left alone. `pr_watch` shows the DRAFT state, the `review:none` re-run line and the round, grant and decline lines. The command is not `/checkpoint`: `claude plugin validate` (2.1.312) reports that as a name Claude Code ships and `$.command.register` refuses it live, while the test kit accepts any name. `validate-mods.mjs` now fails on such a warning (`refusedCommandProblems`). The texts of the engine, the router, the PR B gate and the watcher tell people to run `/pathway`, and tests assert none says `/checkpoint`. A late Yes on an opening or Greptile question first reads `gh pr view --json state,headRefOid` and drops the question when the PR is not open at the asked head. A press that throws frees the pane and shows the error. When the engine recommends a held pathway, no Button is marked Recommended and every press is `--by dave`. `ui.render` has a `.catch`. |
| `hooks/pr-checkpoint/` (auto-confirm, mobile) | Review factory step A (Dave 2026-11-01). The engine prints `auto: { eligible, band, reason }` (`autoOf` in `scripts/github/pr-checkpoint.mjs`): eligible only for band LOW, MID or ELEVATED, recommended `none`, config equal to main, PR labels read, and `checkpoint.autoConfirm` a literal `true` in `review-router.config.json` (the kill switch; false or missing means every checkpoint waits for Dave).   `claude plugin marketplace add ~/.claude/plugins/ccv3-mods` then `claude plugin install ccv3-mods@ccv3 -s user`.

## Diagnostics

Every session start and every desktop attach writes `~/.claude/state/ccv3-mods/last-session.json` (`trigger` start or attach, `isInteractive`, `surface`, `sessionId`): if it isn't fresh after a session opened, the plugin did not load there. `~/.claude/state/ccv3-mods/sessions/<session-id>.<name>.json` keeps one file per session and trigger (`start`, `attach`) and per beacon (`enter`, `turn`, `error`), so a later session never overwrites them. A refused or failed command registration writes `~/.claude/state/ccv3-mods/errors/<time>-<where>.json` and the other modules carry on.
