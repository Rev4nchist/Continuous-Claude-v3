# ccv3-mods

CCv3 function-hook mods for Claude Code 2.1.292+. One plugin, one module per mod. Designs: the "CCv3 Mods" canvas (2026-10-09).
Plan: `.claudedocs/2026-10-07-mods-plan.md` in the primary checkout.

## Mods

| Module | What it does |
|---|---|
| `brief_set` (tool of `hooks/agentic-os/`, `brief.ts`) | The model sets the session brief: title, goal, stop-at, plan, open asks, decisions, proof. Registered in interactive and headless runs, main session only (a subagent call is refused). Writes the `brief` and `chip` keys of the state file; no database row. Plan and ask replace the whole list (`ask: []` clears). A proof joins on task id, subject and kind; no match saves nothing and lists the valid ids. Every string passes `hooks/shared/redact.ts` (a port of `memory_redact.py`) before storage. A prompt from Dave marks open asks `answered?`; an ask goes stale 24 hours after the last activity. A turn-end parser fills goal, stop-at and asks from the model's own restate line and `## Next steps` block when `brief_set` was not called (marked `parsed`, never overrides). The restate parser reads `Restate:`, `Restating the ask:`, `Restated ask:` and `Restate the ask -` lines (label, then the goal up to its stop clause, then the stop-at from `stop at/before/after/there`, also from an `I stop at X` sentence of its own); `Goal:`/`Objective:` and `Stop at:`/`Stop point:` lines still work. In `## Next steps`, `None - waiting on X` (with or without a list marker or bold) is an empty list, `None of ...` is an item; an action line (`Paste ...`, `Run ...`) is a `question`, and only a line with decide, choose, pick or select is a `decision`. The goal and stop-at also come from each main-loop model request, not only the final text: the one `turn.step` hook in `hooks/hud/index.ts` calls `parseStep` (`brief.ts`) and writes the `brief` atom (a subagent request is never read; asks come from the final text only). A labelled restate may replace an older parsed value; an unlabelled `I will ... stop at ...` sentence fills only an empty slot, and a `brief_set` value is never replaced. Tests: `brief.test.ts` (P13-P24, E11-E15b). Chip: working (a tool, the main turn, or a running agent: the same list as the AGENTS rows and NOW), waiting-on-dave (an open ask beats a running run for the chip), blocked (refused tool or blocked step; red gate and peer lane deferred), done (every step proven), idle. A subagent `turn.start` (event has `agentId`) is passed on and never touches the main turn, its clock or the refusal. The pane, NOW and the chip read one agent list: `agent.list` (the `agents` atom) is authoritative for an id it holds, and a running `agentRuns` run is added only when the list lacks it. A subagent `turn.start` reopens a settled run under the same id, and its `turn.complete` removes the id from the atom. The band and the `/os` pane tabs read it (see the core band row and the `/os` row). |
| Steward (`hooks/agentic-os/steward.ts`, wired in `index.tsx`) | Watches the work and shows whether the session brief fell behind. It injects nothing into the session: no `prompt.compose` section, no context on `prompt.submit`, no nudge text to the model, no prompt submitted. The reason is the prompt cache: any text added to the system prompt or the prompt changes the cached prefix, and the cache hit rate comes before a fresher brief. It counts main-loop tool calls and signals since the last `brief_set` (commit with HEAD moved, PR opened, Workflow or Agent run, `resume_handoff`, lane claim, e2e artifact written; a subagent's calls and `brief_set` itself do not count; the turn-end parser does not restart the counts). The counts live in the `steward` state key (`briefAt` and `activity`), reset at session start, `/clear` and resume. Drift: `unset` (work, no goal), `stale` (15 tool calls, or any commit, PR or run), `finished` (every plan step done, work goes on), else `ok`. It only draws: when drift is not `ok`, the pane Overview shows one dim row under GOAL, `brief stale: <plain reason>` (for example `no goal set yet while work started`, `12 tool calls and 1 commit since the brief changed`, `every plan step is done but work continues`). `CCV3_MOD_STEWARD_OFF=1` (read live) stops the counting and hides the row. Observer only: it never denies or rewrites a call; the drawn row passes `redact`. Tests: `tests/steward.test.ts`, `tests/os-tabs-model.test.ts`. |
| `hooks/agentic-os/` | Captures this session's tasks (`TaskCreate`, `TaskUpdate`, `TodoWrite`), plan (`ExitPlanMode`), current step and context %. Draws one band above the prompt. Writes `~/.claude/state/agentic-os/<session-id>.json` after each task, plan or turn change. Observer only: it never denies or rewrites a call. |
| Core band (`hooks/agentic-os/band-model.ts`, `gitinfo.ts`) | Two lines above the prompt, always drawn in an interactive session (PRD 5.3), through the `row-core-1` and `row-core-2` keys. Line 1: chip (WORKING in blue, WAITING ON DAVE in amber, BLOCKED, DONE, IDLE; the same `deriveChip` value the snapshot holds), a project dot and repo, branch, `lane <first lane>`, ctx, cost (the HUD's; `-` when unknown). Line 2: `GOAL` (`not set` in amber when no brief or goal; a dim `working_on` fallback after it only if the state has one, none is wired yet; `[parsed]` marks a goal from the turn-end parser), a block-character plan bar with `done/total` (the task list when it holds a task, else the brief plan steps, never both: PRD 5.1; 10 cells at most; proven, unproven, doing (blue), blocked and to-do in their own tones), `ASK n` (open asks only; amber only on the WAITING ON DAVE chip, red on BLOCKED, dim otherwise; answered ones show dim as `n answered?`; `stale` after 24 hours quiet), `UNPROVEN n` (done steps with no proof). Width: no line is wider than the band; the goal is cut first with an ellipsis, line 1 drops the lane, then the branch, the chip is never cut; under 40 columns one line holds the chip and the goal. With `maxRows` 1 only line 1 draws; below the two core lines come the HUD row (`row-hud`), then the widget line (`row-band`, the earlier band: plan title, task progress, step, PRs, agents), each if rows are left. The core lines never move. Repo, branch and worktree come from `.git/HEAD` (and the `.git` file, `commondir` for a linked worktree) of the session folder: file reads only, at the session start and each turn start, capped at 4 KB, never throwing; the snapshot carries them as `repo`, `branch`, `worktree` (null when unknown). Observer only; every string passes `redact`. Not built: the Fleet reader, project colours, `tones.ts` generated from `tokens.json` (five tones were added to the existing map: `chipDoing`, `doing`, `chipWarn`, `chipOk`, `chipDim`). Tests: `band-model.test.ts` (L1-L12), `gitinfo.test.ts` (Q1-Q14), `agentic-os.test.ts` (C1-C6). |
| `/os` (same module, `os-tabs-model.ts`) | Opens the Agentic OS pane (PRD 5.3) with a tab strip: **Overview**, **Plan**, **Proof**, **Decisions**, then **Comms NEXT**, **Swarm LATER**, **Resources LATER** as plain dim text (not Buttons, so they cannot be pressed or selected). The pane opens on Overview; a press on a tab Button, or its digit `1` to `4` while the pane has the focus (ctrl+x tab), switches the tab. The terminal draws a live tab as `1: Overview`, and the strip wraps with those 3 extra cells counted. The test kit presses a Button by key only and has no keystroke, so a digit press is not tested here; T6 checks that each Button carries the right `hotkey` prop, and the engine turns the digit into the press. The selected tab is the `osTab` atom (types contract), reset to Overview at `/clear` and resume. **Overview**: state chip, `GOAL` (`not set` in amber) and `STOP AT`, repo, branch, worktree, plan bar `done/total`, `ASK n` and `UNPROVEN n`, NOW (tool, step, elapsed; `N agents running` when only a subagent or workflow run is live), ctx and cost, LANE, AGENTS, PRS. In a short pane Overview keeps whole blocks by rank (chip, goal, plan bar, `ASK`/`UNPROVEN`, AGENTS, PRS, NOW, LANE, stop-at, repo, branch, worktree, plan title), draws them in the order above, and ends with a `+N more` row (N blocks left out); AGENTS stays in a pane of 10 rows or more, PRS next to it when its rows fit. `ASK n` does not count answered asks (`n answered?` beside it), an open ask 24 hours quiet reads `ASK n stale` in dim, and a goal or stop-at the turn-end parser filled carries `[parsed]`. **Plan**: the task list when it holds a task, else the `brief_set` plan (PRD 5.1), `N of M done`, each step `○` to do, `▶` doing, `■` blocked, `✓` done and proven (with its artifact) or `!` done and UNPROVEN; a list too long for the pane folds the finished steps into one `✓ N done` row and ends with `+N more`. **Proof**: done-but-unproven steps first, then each proof with its artifact, newest first. **Decisions**: the decision log newest first (text, who, how long ago), then the open asks (kind, text, `recommend:`), answered asks dim with `answered?`, `stale` after 24 hours of quiet. Every tab has an empty-state line, draws no row wider than the pane (20 to 200 columns; a right-hand group goes first), and shows `+N more` when a list does not fit. Text gauges only; every drawn string is redacted again before it is cut. Observer only. Zero model tokens. Reads this session's lanes with `lane.mjs mine --json` from `~/continuous-claude` when present. Elapsed times redraw every 5 s while a turn runs. Interactive sessions only. Not built: Comms, Swarm and Resources content. Tests: `os-tabs-model.test.ts` (O1-O18), `os-tabs.test.ts` (T1-T6), `pane.test.ts`, `review-fixes.test.ts` (R4: six agents in a 12-row body). |

| `hooks/pr-loop/` | Replaces the old review `/loop` cron. Tools `pr_watch {pr}` (interactive only) and `pr_status {pr}` for the model, commands `/watch` and `/land` for Dave. Every 5 minutes an interactive session runs `scripts/github/review-status.mjs <N> --json` per watched PR (reviewer: Greptile). At READY, merged or closed Dave gets a toast; at READY, a review Greptile did not finish (LIMITED), a reviewed head with open threads, a confidence below 4/5 or a failed check (REVIEWED), or no review 60 minutes after the head appeared (STALLED) the model gets one line. REVIEWED and STALLED alert once per head and keep the watch; the REVIEWED line points the model at "When the review lands" in `pr-review-loop.md`. A PR body proof that is missing or wrong (any reason that starts `PR body proof:`) is state PROOF: one author-action line per head ("add or fix the Evidence block, update GREEN to the head"), never PENDING or STALLED; findings on a reviewed head still come first. A STALLED line lists the reasons. When the cause of a missing CodeRabbit review is a rate limit or review limit (`coderabbitRateLimited`, else the "CodeRabbit rate limited:" reason), the LIMITED line says not to post `@coderabbitai review`, to check capacity with `@coderabbitai rate limit` (it costs no review), and gives CodeRabbit's "available in N minutes" figure (`coderabbitRetryMinutes`) when the notice has one. The mod holds `PROOF_REASON_PREFIX` and the rate-limit reason by value: `node --test scripts/github/pr-loop-sync.test.mjs` fails when `review-status.mjs` changes them. A READY alert answered No still gives the model its report line. It never merges. The watch list is in `$.store` under `pr-watch:<session-id>`, so a reload re-arms it. An error all PRs share (rate limit, failed spawn, a status script without `prState`) backs the checks off to 15 minutes. An error of one PR alone (404, a list too long) counts against that PR; the third in a row drops it with a toast. `pr_watch` and `/watch N` probe first and refuse a PR whose status cannot be read. The Agentic OS band and pane show a PRS row. |
| `/watch` (same module) | `/watch` lists the watched PRs. `/watch N` adds one. `/watch N --once` answers with the status and arms nothing. Headless, `/watch N` is `--once`. |
| `/land N` (same module) | Answers without a model call. Shows the status. When READY and interactive it asks `Land #N?` with `Land` or `No`. Pressing Land is Dave's merge yes: it runs `land-pr.ps1 -Pr N` through the PowerShell (else Bash) tool with `consent`. Dismiss, No, an error or a headless run lands nothing. `/land N --when-ready` watches the PR and asks Land/No when it turns READY. With no shell tool, Land hands the model one instruction instead. An aborted Land call (Escape) re-submits nothing. |
| `hooks/pr-checkpoint/` | The PR checkpoint (PR C stage 1). Tool `pr_checkpoint {pr, body}` and command `/checkpoint [pr] [accept|coderabbit|both|none|wait] [--body f]`, both registered in interactive and headless runs. A headless run gets the text plan only (`pr-checkpoint.mjs` in text mode) and records nothing. An interactive run reads `gh pr view` (the PR must be a draft at the checkout's head), runs `pr-checkpoint.mjs --json`, stores the pair in `$.store` `checkpoint:pending:<session>` and opens the side pane `pr-checkpoint` with the keys. The pane lists the options with the recommendation first (hotkey `1`, `autoFocus`), a held option as dim text, and `dismiss` (`0`). A press runs `--confirm <pathway> --by default|dave --body <file>` then `--apply <pr>` inline, stores `checkpoint:pr:<n>`, tells the model with one `session.append` row, and closes the pane. `pr_watch` queues questions in the same pane (`checkpoint:asks:<session>`): a round past the budget, an opening review 15 minutes after ready, Greptile on a `both` PR. The mod posts a review request only on Dave's Yes. Off: `CCV3_MODS_OFF=1` or `CCV3_PR_CHECKPOINT_OFF=1`. Lock A and Lock B (`tool.call` denies for `pathway.json` and the shell shapes) and the DRAFT, `review:none` and budget lines of `pr_watch` are not in this stage. Known clash: Claude Code 2.1.312 ships the name `/checkpoint` (alias of `/rewind`), so `$.command.register` refuses it; the tool and the pane work. |
| `hooks/hud/` (HUD) | A row under the two core band lines: main-loop model and effort (red below `high`, the 2026-09-30 pin), the advisor (on, off, or blocked with the env var that blocks it; `×N` counts its uses), a ctx ring, the session cost, the cache element and the 5h / 7d / spend-limit bars from `session.measure` (the engine's own /cost ledger). Svg ring and bars on desktop, text gauges on the terminal. Interactive only. Off: `CCV3_MOD_HUD_OFF=1`. |
| ctx (same module) | The context figure moves after every main-loop request (`turn.step` reads `$.session.usage()`), not once per turn: the engine raises `session.measure` after a turn, so a turn of many requests held one value. At a compaction of the main conversation the HUD shows no ctx until the next response: the engine has no figure then, and the size it records at the compaction (`tokensAfter`) is far below the next prompt. `/clear` and a resume in the same process clear it. Captured in every run unless `CCV3_MODS_OFF=1`. |
| cache element and `/cache` (same module, `hooks/hud/cache.ts`) | Prompt-cache use of the main loop, summed per request: `cache 98% · 42m` is the share of all input tokens the cache served and the minutes its entry still has, counted from the send of the last request that read or wrote the cache. `MISS 97k` shows while the newest turn holds a request that rewrote prompt the cache held before. The first request of a fresh conversation is not flagged; the first request of a resumed or forked one is (the engine's own `classic.SessionStart` `source`, never the message count). `cache off` shows when no request read or wrote the cache. `cache COLD · next ≈$2.88` shows after the lifetime ran out, with the list-price cost of the next send; after a compaction it is `cache COLD` alone, because the size of the compacted prompt is not known until the next request. `/cache` prints the totals, an estimated saving and each miss with its idle gap, size and cause (session start, resume, expired, compaction, model change, prompt changed); it costs no model turn. The lifetime is a rule, not a reading: 60 minutes when the account reports a `five_hour` or `seven_day` window (a subscription), else 5; `CCV3_CACHE_TTL_MIN` overrides the minutes, not the write rate. Idle, the band redraws once a minute for the countdown. `/clear` and a resume in the same process start the counts over. The counts are captured in interactive and headless runs (not with `CCV3_MODS_OFF=1` or `CCV3_MOD_HUD_OFF=1`) and the snapshot carries them as `cache`; the element and `/cache` are interactive only. Subagents stay in the Agent Ledger. A miss is measured against what the cache held (the last request's cache read plus write), never against uncached input. Limit: a server-side tool loop (the advisor) reports one summed usage, so a miss between two responses of one request is not seen. |
| `hooks/agent-ledger/` (`/ledger`) | One run per subagent from `agent.spawn`: tokens and an estimated cost per model request (`turn.step`, price table in `hooks/shared/price.ts`), settled at each `turn.complete` (a teammate runs again after it). Flags tier drift against the agent's `.md` (`model:`, `effort:`; `inherit` is no tier; a numeric effort is a budget, not compared) and any Haiku run. The band shows `◉ N running · ≈$x`. Records headless too (the snapshot carries `agentRuns`). Off: `CCV3_MOD_LEDGER_OFF=1`. |
| `hooks/touched-files/` (`/files`) | A tree of only the files this session's own tool calls named: read (dim), edited (accent, +/- lines), committed (green). A shell `git commit` counts only if `HEAD` moved, then flips the edited files `git show --name-only HEAD` lists. Never lists a folder. Off: `CCV3_MOD_FILES_OFF=1`. |
| `hooks/compact-keeper/` | Only the person's `/compact` (trigger `manual`; never `auto`, `plugin`, `precompute` or a subagent's). Adds one block to the summarizer's `instructions`, after the person's own text: the plan, the open tasks (finished ones count only), the lane, the watched PRs, then a marker line the summarizer must copy word for word, `KEEPER <session8> open N of M`. At most 1,500 characters; the task list is cut with a `(+N more)` line and the marker always stays. No plan, no open task, no lane and no watched PR add nothing. It reads the Agentic OS atoms in this process: a `--resume` starts with none, so a resumed session has only what it saw since. It never starts a compaction. Off: `CCV3_MOD_KEEPER_OFF=1`. Kill review: if 3 of the next 5 compactions still lose the plan (a transcript's summary without the marker means the keeper did not run), remove it. |
| `hooks/shared/` | Pure helpers the modules share: tiers, price table, Svg glyphs, tone map, diagnostics (`diag.ts`), patch reading (`diff.ts`). |

## Load

- Development, one session, from the repo root: `claude --plugin-dir .claude/plugins/ccv3-mods`
- Every session, terminal and desktop app: install it from the local marketplace `ccv3`, whose `marketplace.json` sits in this plugin's own `.claude-plugin/` (source `./`). Once, after a forward sync:
  `claude plugin marketplace add ~/.claude/plugins/ccv3-mods` then `claude plugin install ccv3-mods@ccv3 -s user`.
  This writes `extraKnownMarketplaces.ccv3` (a `directory` source) and `enabledPlugins["ccv3-mods@ccv3"]` to `~/.claude/settings.json`; the settings template carries both. A directory marketplace loads the plugin in place, so each forward sync takes effect at the next session with no reinstall (proven 2026-10-10: `hooks module ccv3-mods@ccv3 loaded`, `hooks.json` read from the source folder).
- Why not `CLAUDE_CODE_PLUGIN_DIRS`: the desktop app's Code tab runs its own copy of Claude Code, and the docs don't say it reads `env` from settings. On 2026-10-10 the env var loaded the mods in Dave's terminal and nothing in his desktop app. Remove the env var when installing: two plugins named `ccv3-mods` don't both load, and the inline one wins.
- Forward sync (`scripts/sync-to-active.sh`) copies the plugin to `~/.claude/plugins/ccv3-mods` and never touches the engine-written `.claude-plugin/types/`.

## Diagnostics

Every session start and every desktop attach writes `~/.claude/state/ccv3-mods/last-session.json` (`trigger` start or attach, `isInteractive`, `surface`, `sessionId`): if it isn't fresh after a session opened, the plugin did not load there. `~/.claude/state/ccv3-mods/sessions/<session-id>.<name>.json` keeps one file per session and trigger (`start`, `attach`) and per beacon (`enter`, `turn`, `error`), so a later session never overwrites them. A refused or failed command registration writes `~/.claude/state/ccv3-mods/errors/<time>-<where>.json` and the other modules carry on.

## Where it runs

| Run | Capture and snapshots | 5 s pulse, `lane.mjs`, `/os`, band |
|---|---|---|
| Interactive (`isInteractive` true) | Yes | Yes |
| Desktop app (an SDK start, `isInteractive` false, then `session.attach` on `desktop`) | Yes | Yes, from the attach: commands, HUD, pulse. pr-loop's watcher stays REPL-only |
| Headless (`claude -p`, SDK; `isInteractive` false) | Yes, with a limit: a snapshot is written after a task or plan change, and at turn end only when the session holds a task or a plan. A headless run with neither writes no file | No. Nothing is spawned and no timer is armed |
| PR module (`hooks/pr-loop/`) | `/watch` and `/land` answer in both modes; `pr_status` is registered in both | Interactive only: the 5 minute watcher, `pr_watch`, the Land/No dialog and the Land call. Headless `/land` shows the status and lands nothing. |
| `CCV3_MODS_OFF=1` in the process env | No. Every hook passes the event on | No |

Nothing prunes `~/.claude/state/agentic-os/`. The limit above keeps scheduled reports, probes and workflow agents from adding one file per run. Test: `G9 G10 G11` in `tests/gating.test.ts`.

`session.start` sets the mode on each run. A hot reload runs `register` again and fires `session.start` for the changed module (types: `session.start`, "a reload (changed modules only)"). The old environment's timers are dropped and the new `session.start` arms the pulse again. Test: `G5 G8` in `tests/gating.test.ts`.

## Facts proven on 2.1.292 (2026-10-07)

- Mods load in headless `claude -p` runs.
- A mod `tool.call` hook runs outside the `settings.json` PreToolUse hooks. A settings-hook block reaches the mod as a result with `isError: true` and the hook's text, not as `deny`.
- A `command.run` hook that answers its own command makes no model call: `claude -p "/os"` ran 0 turns at $0. Proven before the headless gate: `/os` is now registered in interactive sessions only.
- In `claude plugin test`, op events (`fs.exists`, `process.run`, `agent.list`, `ui.open`, `session.id`) are answered with `{ value }`.
- `e.tool_use_id` in `tool.call` equals the transcript's `tool_use` id.
- In `claude plugin test`, a `Text` element's `key` is not kept. Find band text by `type: 'Text'`.
- The plugin may hold one `session.start` hook without a matcher. A second one fails the whole plugin load. The PR module uses two hooks narrowed by `{ isInteractive: true }` and `{ isInteractive: false }`.
- `$` and atoms cannot cross an import. A helper that takes `$`, or an atom read with `read($, atom)`, must sit in the file of the hook. A pure helper (`model.ts`) may be imported. The `mode` and `prs` atoms are declared in each file that reads them, with the same plugin and key.
- A tool served by a mod answers with a string or a list of content blocks (`[{ type: 'text', text }]`). The MCP result object `{ content, isError }` fails with "result does not match its output shape". `claude plugin test` does not check this: only a live run does (`mcp__ccv3-mods__pr_status` called by the model).
- `$.prompt.submit` inside a `command.run` hook is refused ("it would wait on the turn this hook is holding"). Submit from `$.clock.after(1, ...)`.
- `$.tool.call` with `consent` inside a `command.run` hook works in `claude plugin test`. Live use of Land is not proven: no PR was landed.
- `claude -p "/watch 105"` from Git Bash: Git Bash rewrites a leading `/watch` to `C:/.../Git/watch`, the model gets plain text and spends a turn. Set `MSYS_NO_PATHCONV=1` or run from PowerShell. The E2E script is `.claude/cache/e2e/2026-10-07-pr-loop-run.sh` (gitignored).
- A headless `claude -p --plugin-dir` run writes `.claude-plugin/types/` (seen on 2.1.293, 2026-10-07), so one e2e run is enough to make `tsc -p` work in a fresh worktree.
- A headless snapshot has `lanes: null`: the lane board is never read there.
- Two plugins named `ccv3-mods` (one from `--plugin-dir`, one from `CLAUDE_CODE_PLUGIN_DIRS`) do not both load. The debug log says `hooks module ccv3-mods@inline not loaded: another plugin of that name loads first`. ## Facts proven on 2.1.296 (2026-10-13, ctx and cache)

- `session.measure` does not fire per request. In a headless run of 3 requests it fired at the first response (the first reading) and after `turn.complete`, and not for the second request, whose prompt had grown. Inside a `turn.step` hook, `$.session.usage()` read after `next(e)` already holds that response: `context.tokens` equals its input + cache read + cache write, and `percent` is rounded to the nearest whole number.
- The sums of `turn.step` usage over a run's main-loop requests equal the `usage` in the run's `--output-format json` result (cache read, cache write, input). `e2e-headless.mjs` checks this.
- The API reports the cache lifetime in the transcript (`cache_creation.ephemeral_1h_input_tokens`) and not in `turn.step`'s usage, which holds the four flat counts. On this subscription every write was a 1-hour entry.
- `$.command.register` accepts the name `cache`, and `claude -p "/cache"` answered by a `command.run` hook ran 0 turns at $0. Proven with a probe mod that registers at every start: this plugin registers `/cache` in interactive sessions only.
- In `claude plugin test`, a `session.compact` answer with an empty `messages` list is refused ("a compaction leaves at least one").
- `tokensAfter` of a `session.compact` result is not the next prompt. A headless `/compact` of a 87,220-token prompt reported `tokensBefore` 87,517 and `tokensAfter` 17,863; the next request's prompt was 90,501 (the engine attaches files, memory and hook context again). `$.session.usage()` still held the old 87,220 right after the compaction. Dave's first live session showed the same: `ctx 2%` after `/compact` on an 11% prompt. So no figure is shown until the next response.
- A mod receives `classic.SessionStart`: `source` was `startup` on a fresh run, `resume` on `--resume` (with `context_tokens`), and `compact` after a compaction in the same process. `turn.step`'s `messageCount` cannot tell a resume from a start: 41 on a fresh first request in this repo (hook and memory context), 60 on a resumed one.

## Facts proven on 2.1.296 (2026-10-13, compact keeper)

- A `session.compact` hook with the matcher `{ trigger: 'manual' }` fires on a headless `/compact` (one `claude -p --input-format stream-json` process fed `/compact` as a message) and reads the atoms the process set. `next({ ...e, instructions })` reaches the summarizer.
- A plugin holds one unmatched `session.compact` hook (the HUD's). A second one fails the whole load, so the keeper's matcher is also what lets both load.
- A soft request ("keep these tasks") is not echoed into the summary; a request to copy a line "word for word" is. Only the second is testable.
- The engine keeps a `preservedSegment` of recent messages across a compaction. A question such as "which tasks remain" is answered right with the keeper off, so it proves nothing. The compaction summary is a user message in the session transcript (`~/.claude/projects/<project>/<session>.jsonl`, text starting "This session is being continued"), with `compactMetadata.trigger` on the `compact_boundary` row. It is not in the stream-json output.
- The mod state is in memory: a `--resume` process starts with no tasks.
- A hook without `.catch` that throws is skipped by the engine like one with it; only `scripts/mods/validate-mods.mjs` tells them apart (`gating hook without .catch: ./register.tsx session.compact{trigger=manual}`).

## Facts proven on 2.1.295-2.1.296 (2026-10-09, mod suite)
